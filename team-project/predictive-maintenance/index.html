What is Predictive Maintenance?
🔴

Reactive Maintenance

Fix the equipment after it breaks. Lowest planning cost but highest disruption — unplanned downtime averages $260,000/hour in automotive manufacturing.

🟡

Preventive Maintenance

Scheduled maintenance on a fixed calendar interval regardless of actual equipment condition. Reduces breakdowns but wastes resources on healthy equipment.

🟠

Condition-Based Maintenance

Maintenance triggered by real-time sensor thresholds (e.g., temperature exceeds 80°C). Better than time-based, but still reactive once the threshold is crossed.

🔵

Predictive Maintenance (PdM)

Machine learning predicts when a failure is likely to occur — before it happens. Enables just-in-time maintenance scheduling, reducing costs 10–25% and downtime 35–45% (McKinsey).

Industry Context

Manufacturing industry loses over $50 billion annually to unplanned downtime. PdM shifts strategy from "fix it when broken" to "fix it before it breaks," using sensor data and historical failure patterns. This project implements that strategy with Apache Spark at scale.

AI4I 2020 Dataset — From the Source Paper
Paper Reference

Stephan Matzka. "Explainable Artificial Intelligence for Predictive Maintenance Applications." 2020 Third International Conference on Artificial Intelligence for Industries (AI4I). IEEE. This paper created and published the dataset — it is the primary reference for understanding feature semantics and failure mode definitions.

📊

10,000 Data Points

Synthetically generated to reflect real industrial conditions. Each row is one machine-process observation with 6 sensor/parameter features plus labels.

🔌

6 Input Features

Air temperature [K], process temperature [K], rotational speed [rpm], torque [Nm], tool wear [min], and product quality variant (L/M/H → 50/30/20% split).

⚠

Severe Class Imbalance

Only 339 out of 10,000 records are labeled as machine failure — 3.39% failure rate. A naive "predict no failure always" classifier would achieve 96.6% accuracy. Standard accuracy alone is misleading.

📈

Asymmetric Misclassification Cost

The paper explicitly sets: false negative cost = 30× false positive cost. Missing a real failure is far more costly than a false alarm. This shapes which evaluation metric to prioritize.

Five Failure Modes — Exact Definitions from the Paper
Code Name Trigger Condition Count
TWF Tool Wear Failure Tool wear reaches 200–240 min threshold (randomly sampled per run). Tool is replaced 74 times; fails 46 times. 120 total TWF events. 120
HDF Heat Dissipation Failure Air-to-process temperature difference < 8.6 K AND rotational speed < 1,380 rpm. Both conditions must be true simultaneously. 115
PWF Power Failure Process power = torque × angular velocity (rad/s). Failure if power < 3,500 W or > 9,000 W. Operating outside the nominal power envelope. 95
OSF Overstrain Failure Tool wear × torque exceeds: L-variant > 11,000, M-variant > 12,000, H-variant > 13,000 (min·Nm). Product quality affects threshold. 98
RNF Random Failure Each process has a 0.1% random chance of failure regardless of any sensor readings. Inherently unpredictable by ML — represents unknown failure causes. 19
Key Insight — Failure Overlap

Multiple failure modes can be true simultaneously for a single data point. The machine failure label is set to 1 if any failure mode is active. The ML model must therefore untangle which mode caused the failure — this is the multiclass classification challenge. The RNF class is particularly hard to model because no sensor pattern predicts it.

Feature Importance — From the Paper
📈

Torque (~35%) — Most Important

The highest predictor importance. Both very low torque (<13.2 Nm) and very high torque (>65 Nm) are associated with failures (PWF, OSF, HDF).

🔄

Rotational Speed (~30%) — 2nd Most Important

Low rotational speed combined with high torque is a key failure indicator. Appears in HDF and PWF decision boundaries.

🕐

Tool Wear (~20%)

Critical for TWF and OSF. Cumulative wear accumulates over time — the longer a tool is in use, the higher the failure risk above 141.5 min threshold.

🌡

Temperatures (~10%)

Air and process temperature individually have lower importance. The difference between them (temp delta) is what drives HDF. Absolute temperature values matter less.

XAI Concepts — From the Source Paper
🕒

Explainable Models

Inherently interpretable models like shallow decision trees. The paper shows a 4-node decision tree maintenance personnel can read directly: low torque or high torque + high speed + tool wear = failure.

🔍

Explanatory Interfaces (LIME)

Model-agnostic methods applied post-hoc to black-box classifiers. The paper uses normalized feature deviations (similar to LIME) to explain individual predictions. Provides consistent coverage even when decision trees fail.

⚖

Why XAI Matters for PdM

Maintenance engineers need to trust a model before acting on it. "The machine will fail in 4 hours" is not enough — they need to know why so they can verify and prioritize repair actions.

📋

Explanation Quality Scoring

The paper scores explanations: very useful / partially useful / limited / none. Decision trees give more "very useful" results; normalized feature deviations provide better coverage with fewer "no explanation" outcomes.

Decision Tree Example — From the Paper (Fig. 1)

The paper demonstrates this readable decision tree trained on torque, rotational speed, and tool wear:

• torque < 13.2 Nm → predict failure
• torque ≥ 65 Nm AND rotational speed ≥ 1228 rpm → predict failure
• torque ≥ 65 Nm AND tool wear ≥ 141.5 min → predict failure
• All other combinations → predict normal operation

This is the type of human-readable explanation XAI aims to produce even from complex black-box models like Random Forests.

Team Structure — 4 Members

Each member owns a vertical slice of the project with a distinct deliverable notebook or document. Tasks are designed to run in parallel after the data cleaning step (Member 1) is complete. All members contribute to the final paper.

Environment setup • Data ingestion • Cleaning pipeline

  • 5Cast feature columns to DoubleType. Cast Type column to StringType. Verify with .dtypes.
  • 6Check for null values using .filter(col.isNull()).count() on each column. Document findings.
  • 7Apply StringIndexer to encode the Failure Type target label column. Note the label-to-index mapping.
  • 8Apply .cache() to the cleaned DataFrame after all transformations. Demonstrate cache hit speed-up (Chapter 7).
  • 9Share the cleaned, cached DataFrame reference with Members 2 and 3 via shared notebook or exported Parquet.

M3
ML Pipeline Engineer
Spark ML Pipeline • Hyperparameter tuning • Model evaluation
  • 1Build VectorAssembler stage: assemble all five numeric sensor features (air temp, process temp, rotational speed, torque, tool wear) into a single feature vector.
  • 2Add StandardScaler stage: normalize feature vector to zero mean and unit variance. Required before distance-sensitive algorithms.
  • 3Configure RandomForestClassifier with labelCol pointing to the StringIndexer output from Member 1.

  • 6Wrap in CrossValidator with 5-fold CV and MulticlassClassificationEvaluator (metric: f1). Fit on training split (80%).

  • 8Generate confusion matrix: convert predictions to Pandas, use sklearn.metrics.confusion_matrix to visualize per-class performance. Discuss RNF class (hardest to predict).
  • 9Document the caching strategy: show before/after timing for .cache() on the transformed dataset to demonstrate Chapter 7 optimization.

Project Overview
Abstract

Unplanned equipment failures in manufacturing environments lead to costly downtime, safety risks, and production losses. This project applies Apache Spark MLlib to the AI4I 2020 Predictive Maintenance dataset to build a multiclass classification model predicting the type of machine failure (or no failure) from real-time sensor data. The team builds a full Spark ML Pipeline with feature engineering, model training, and evaluation stages, with emphasis on Chapter 7 performance optimization using caching and configuration tuning.

Success Criteria
✓

Accuracy > 0.90

Overall multiclass accuracy across all 6 classes (no-failure + 5 failure modes) on the held-out test set.

✓

Macro F1 > 0.75

Unweighted average F1 across all classes. Harder to achieve than weighted F1 due to the severe class imbalance and rare failure modes.

✓

Full Pipeline in Spark

All processing stages implemented as a Pipeline object — no raw Python/pandas logic in the training path.

⚠

Dataset Limitation Acknowledged

The paper must explicitly note that AI4I 2020 is synthetic. Results may not generalize to a real production floor without validation on live sensor data.

Known Challenges & Mitigations
Challenge: Class Imbalance

With only 3.39% failure records, the model may achieve high accuracy by mostly predicting "no failure." Mitigation: use macro F1 (not just accuracy) as the primary evaluation metric. Consider class weights in RandomForestClassifier via weightCol if available in your Spark version.

Challenge: RNF Class

Random Failure (19 cases) has no sensor pattern — it is inherently unpredictable. Expect near-zero F1 for this class. Discuss this in the paper as a fundamental limitation rather than a model failure. This validates the domain knowledge from the Matzka paper.

Challenge: CrossValidator Runtime

9 parameter combinations x 5 folds = 45 model fits. This will take several minutes on a local Spark setup. Cache the DataFrame before CrossValidator to avoid recomputing transformations on every fold (Chapter 7 in action).

EDSIG/CONISAR Template Requirements

Paper length: 6–7 pages. Use the EDSIG template (two-column IEEE-style format). Include author names, institution, abstract, keywords, numbered sections, references in IEEE format, and figures with captions. Conference submission is optional and does not affect course grade.

Abstract + Introduction

  • Introduction: Frame predictive maintenance as a Big Data challenge requiring scalable ML. State why Apache Spark is the right tool at industrial scale.
  • Keywords: predictive maintenance, Apache Spark, MLlib, Random Forest, multiclass classification, AI4I 2020

~1 page

Conclusion & Future Work
