What is S.M.A.R.T.?
🔌

Self-Monitoring, Analysis & Reporting Technology

Built into every modern HDD and SSD. The drive's onboard firmware tracks dozens of internal health counters — spin-up time, reallocated sectors, read error rate — and exposes them to the OS daily.

📊

Raw vs. Normalized Values

Each SMART attribute has a raw value (the actual count) and a normalized value (0–253 where 253 = best). Backblaze found raw values are more predictive than normalized for failure detection.

🕑

Daily Snapshot Model

Backblaze records one row per active drive per day. Each row = one "drive-day" observation. A drive that ran for 3 years without failing contributed ~1,095 rows; its final day has failure = 1.

💰

Why It Matters

Unplanned HDD failure in a data center costs thousands in emergency replacement, data recovery, and SLA violations. Predicting failure 7–30 days ahead enables proactive replacement during scheduled windows.

The Backblaze Dataset
Source

Backblaze has published real production drive data from their data centers since 2013 — over 557 million drive-days and 19,890 recorded failures through 2025. Data is freely downloadable by quarter. Download URL pattern: https://f001.backblazeb2.com/file/Backblaze-Hard-Drive-Data/data_Q[1-4]_[YEAR].zip

📅

Coverage: 2013–Present

12+ years of quarterly releases. For a team project, use 1–2 years (e.g., 2024, all 4 quarters) to keep file sizes manageable while still having millions of drive-day records.

🏭

4 Manufacturers

HGST (8%), Seagate (34%), Toshiba (33%), WDC/Western Digital (25%). Failure rates vary significantly by model and manufacturer — a key EDA finding.

📑

Schema Evolves Quarterly

Backblaze adds or removes SMART columns as drives change. Columns present in Q1 may be absent in Q4. The data cleaning step must normalize the schema before unioning quarters.

📈

~1% Annualized Failure Rate

Q4 2025 AFR = 1.13%. Across 30M drive-days, only 943 failures. This is an even more severe imbalance than the AI4I dataset — model accuracy is meaningless; use AUC-ROC and recall.

The Bathtub Curve — HDD Failure Lifecycle
🔴

Early Life (0–6 months)

Elevated failure rate from manufacturing defects. Drives that survive this period typically perform well for years. Known as "infant mortality" in reliability engineering.

🔵

Steady State (6 months–4 years)

Lowest and relatively constant failure rate. Random, unpredictable failures. SMART attributes may not show clear warning signals during this phase.

🟡

Wear-Out (4+ years)

Failure rate rises again as mechanical components fatigue. SMART attributes — especially reallocated sectors and pending sectors — become highly predictive here. Power-On Hours (SMART 9) is the key age indicator.

smart_188_raw Command Timeout Number of commands that timed out. Indicates mechanical sluggishness or intermittent connection problems. High

Backblaze Research Finding

Backblaze has published research showing that SMART 5, 187, 197, and 198 together identify the vast majority of failing drives. A simple rule — "if any of these four attributes is nonzero, flag the drive for replacement" — achieves high recall at the cost of some false positives. Your ML model should aim to beat this simple baseline.

Critical Challenge: Label Engineering
The Labeling Problem

The raw dataset's failure column is 1 only on the day the drive actually failed — a single row out of hundreds or thousands. A model trained this way predicts "will it fail today?" which is not actionable. For a useful predictive model, engineer a forward-looking label: set label = 1 for any drive-day that is within N days of a recorded failure (e.g., N=30). This requires a window function over each drive's history — a perfect use case for Spark SQL window functions with LEAD() or a reverse sort approach.

Temporal Split — Prevent Data Leakage

Do not use a random train/test split on this dataset. Because drives appear on many consecutive days, a random split would allow future drive data to leak into training. Instead, use a temporal split: train on 2022–2023, test on 2024. This mirrors how the model would operate in production.

Team Structure — 4 Members

M1 handles the large-scale data ingestion and schema normalization — the biggest bottleneck. M2 and M3 can begin planning in parallel. The forward-looking label engineering (window function) is M1 & M3 shared responsibility and must be agreed upon before M3 starts training.

Data Engineering Lead
Data ingestion • Schema normalization • Label engineering

  • 2Unzip and load each quarter into a Spark DataFrame. Print schema for each and identify SMART columns that appear or disappear across quarters.

  • 4Keep core columns: date, serial_number, model, capacity_bytes, failure, plus the 6 SMART attributes. Drop all other columns.

  • 7Engineer the forward-looking label: using a Spark window partitioned by serial_number and ordered by date, look ahead 30 days and set label = 1 if any row in the window has failure = 1.

M3
ML Pipeline Engineer
Spark ML Pipeline • GBT classifier • Temporal evaluation
  • 1Load the labeled Parquet from M1. Apply a temporal train/test split: filter date < '2024-10-01' for training, date ≥ '2024-10-01' for testing. Do not use random split.
  • 2Build VectorAssembler combining all 6 SMART raw attributes into a single feature vector.
  • 3Add StandardScaler stage to normalize feature magnitudes across SMART attributes.
  • 4Configure GBTClassifier (Gradient Boosted Trees) with labelCol="label". GBT handles imbalance better than logistic regression and produces feature importances natively.
  • 5Set class weights: compute weight for class 1 as count(label=0) / count(label=1). Add weightCol to the training DataFrame to compensate for the ~99:1 imbalance.
  • 6Build ParamGridBuilder with maxIter in [10, 20] and maxDepth in [3, 5]. Wrap in CrossValidator with 3-fold CV (large dataset — 5 folds may be too slow).
  • 7Cache the training DataFrame before CrossValidator. Document time savings vs. uncached run (Chapter 7 reference).
  • 8Evaluate on test set: report AUC-ROC (BinaryClassificationEvaluator), precision, recall, and F1 at the 0.5 threshold. Also report recall at a 0.3 threshold (catching more failures at cost of more false alarms).
  • 9Extract and rank feature importances from the best GBT model. Confirm SMART 5, 187, 197, 198 rank highest — validating Backblaze research findings.

Project Abstract
Abstract

Hard drive failures in data center environments cause costly unplanned downtime and data recovery operations. This project applies Apache Spark MLlib to the Backblaze Drive Stats dataset — over 30 million drive-days of real production data — to build a binary classifier predicting HDD failure within a 30-day horizon using daily S.M.A.R.T. sensor snapshots. A Spark ML Pipeline incorporates VectorAssembler, StandardScaler, and a Gradient Boosted Trees classifier with class-weighted training to address severe label imbalance (~1% failure rate). A temporal train/test split prevents data leakage. Results are evaluated using AUC-ROC and recall, and compared against Backblaze published baseline rules. Chapter 7 caching strategies are demonstrated to manage the dataset at scale.

Success Criteria
✓

AUC-ROC > 0.85

Area under the ROC curve on the held-out temporal test set. Insensitive to class imbalance — more meaningful than accuracy for a 1% failure rate dataset.

✓

Recall > 0.70

At the 0.5 probability threshold: catch at least 70% of drives that will fail within 30 days. Missing a failure (false negative) is far more costly than a false alarm.

✓

Beat the Baseline Rule

ML model recall must exceed the Backblaze simple rule (flag any drive with nonzero SMART 5/187/197/198) at comparable precision. Demonstrating ML adds value over domain rules is the key finding.

⚠

Scale Demonstrated

The paper must reference specific row counts and file sizes to justify Spark (vs. pandas). A single year of data at ~3 GB/quarter compressed = real Big Data justification for the course.

Known Challenges & Mitigations
Challenge: Extreme Class Imbalance (~1%)

With only ~1% positive labels after the 30-day window expansion (raw failure rate is even lower), the model will converge to "predict 0 always." Mitigation: compute class weights from training data and pass via weightCol; use AUC-ROC as the CrossValidator metric, not accuracy; tune the decision threshold after training.

Challenge: Schema Changes Across Quarters

Backblaze adds or removes SMART columns quarterly. Mitigation: M1 must load each quarter separately, print schema, and select only the intersection of columns present in all quarters. The 6 core SMART attributes listed above are stable across most years.

Challenge: Dataset Size (12+ GB/year uncompressed)

A full year is large for a local Spark setup. Mitigation: use Databricks Community Edition for free cluster compute; OR work with a representative sample (e.g., Seagate drives only, which are the largest manufacturer group). Cache aggressively and repartition by model to minimize shuffle.

Challenge: Label Engineering Complexity

The 30-day forward label requires a Spark window function sorted in reverse: for each serial_number, look N rows ahead for a failure=1. This is the hardest technical step. M1 should test the logic on a single drive before applying to all drives.
