What is S.M.A.R.T.?
🔌

Self-Monitoring, Analysis & Reporting Technology

Built into every modern HDD and SSD. The drive's onboard firmware tracks dozens of internal health counters — spin-up time, reallocated sectors, read error rate — and exposes them to the OS daily.

📊

Raw vs. Normalized Values

Each SMART attribute has a raw value (the actual count) and a normalized value (0–253 where 253 = best). Backblaze found raw values are more predictive than normalized for failure detection.

🕑

Daily Snapshot Model

Backblaze records one row per active drive per day. Each row = one "drive-day" observation. A drive that ran for 3 years without failing contributed ~1,095 rows; its final day has failure = 1.

💰

Why It Matters

Unplanned HDD failure in a data center costs thousands in emergency replacement, data recovery, and SLA violations. Predicting failure 7–30 days ahead enables proactive replacement during scheduled windows.

The Backblaze Dataset
Source

Backblaze has published real production drive data from their data centers since 2013 — over 557 million drive-days and 19,890 recorded failures through 2025. Data is freely downloadable by quarter. Download URL pattern: https://f001.backblazeb2.com/file/Backblaze-Hard-Drive-Data/data_Q[1-4]_[YEAR].zip

The Bathtub Curve — HDD Failure Lifecycle
🔴

Early Life (0–6 months)

Elevated failure rate from manufacturing defects. Drives that survive this period typically perform well for years. Known as "infant mortality" in reliability engineering.

🔵

Steady State (6 months–4 years)

Lowest and relatively constant failure rate. Random, unpredictable failures. SMART attributes may not show clear warning signals during this phase.

🟡

Wear-Out (4+ years)

Failure rate rises again as mechanical components fatigue. SMART attributes — especially reallocated sectors and pending sectors — become highly predictive here. Power-On Hours (SMART 9) is the key age indicator.

SMART # Name What It Counts Predictive Power
smart_5_raw Reallocated Sectors Count Bad sectors the drive remapped to spare area. Any nonzero value is a warning sign; rapid growth = imminent failure. High
smart_9_raw Power-On Hours Total hours the drive has been powered on. Used as a proxy for drive age. Critical for bathtub curve analysis. High
smart_187_raw Reported Uncorrectable Errors Read errors the drive could not correct with ECC. Sharp increases strongly predict failure. High
smart_188_raw Command Timeout Number of commands that timed out. Indicates mechanical sluggishness or intermittent connection problems. High
smart_197_raw Current Pending Sector Count Unstable sectors waiting to be reallocated on next write. Nonzero = sectors the drive suspects are bad but has not yet confirmed. High
smart_198_raw Uncorrectable Sector Count Sectors that could not be read or written during a surface scan. Often zero until very close to failure. High
smart_1_raw Read Error Rate Hardware read error rate. Interpretation differs by manufacturer — Seagate uses a large composite value; others use raw counts. Medium
smart_241_raw Total LBAs Written Lifetime write volume. Useful for SSDs (wear indicator); less critical for HDDs but helps identify heavily-written drives. Context
Backblaze Research Finding

Backblaze has published research showing that SMART 5, 187, 197, and 198 together identify the vast majority of failing drives. A simple rule — "if any of these four attributes is nonzero, flag the drive for replacement" — achieves high recall at the cost of some false positives. Your ML model should aim to beat this simple baseline.

Critical Challenge: Label Engineering
The Labeling Problem

The raw dataset's failure column is 1 only on the day the drive actually failed — a single row out of hundreds or thousands. A model trained this way predicts "will it fail today?" which is not actionable. For a useful predictive model, engineer a forward-looking label: set label = 1 for any drive-day that is within N days of a recorded failure (e.g., N=30). This requires a window function over each drive's history — a perfect use case for Spark SQL window functions with LEAD() or a reverse sort approach.

Temporal Split — Intra-Quarter (Q4 2025 Only)

Do not use a random train/test split — drives appear on many consecutive days, so random splitting allows future drive data to leak into training. Since this implementation uses only Q4 2025 (no multi-year data), use an intra-quarter temporal split:

Train Set: October 1 – November 30, 2025 — Files 1–61 — filter date < "2025-12-01"

Test Set: December 1 – December 31, 2025 — Files 62–92 — filter date >= "2025-12-01"

This mirrors production deployment: train on all history available today, evaluate on the most recent unseen month.

03
Feature Engineering
Lag features • Velocity features • Window analytics • Delta Lake write
  • 1Load from the managed Delta table: spark.read.table("backblaze_master_delta"). This notebook adds time-series features that a point-in-time model misses.
  • 2Define the drive-level window spec: w = Window.partitionBy("serial_number").orderBy("date").
  • 3Add 7-day lag features for the 4 highest-signal SMART attributes: lag("smart_5_raw", 7).over(w) → smart_5_lag7. Repeat for smart_187_raw, smart_197_raw, smart_198_raw. These capture the historical baseline value per drive.
  • 4Add 7-day velocity features (rate of change): (col("smart_5_raw") - col("smart_5_lag7")) → smart_5_delta7. Repeat for smart_187, 197, 198. Rapid growth in reallocated sectors is far more alarming than a stable nonzero count.
  • 5Fill nulls in all lag and velocity columns with 0 — the first 7 days of each drive history will have no lag available. This is acceptable for a Q4 dataset where drives have prior history.
  • 6Verify total column count: 6 original SMART features + 4 lag features + 4 velocity features = 14 engineered features for the model. Print schema to confirm.
  • 7Cache the feature-engineered DataFrame in memory: df_features.cache(). Run a .count() to materialize the cache. This avoids recomputing window functions every time the next notebook reads the data.
  • 8Write to a managed Delta table: df_features.write.format("delta").mode("overwrite").saveAsTable("backblaze_features_delta"). Notebook 04 loads it with spark.read.table("backblaze_features_delta").

04
Model Training & Evaluation
Temporal split • GBTClassifier • Class weighting • AUC-ROC + Recall
  • 1Load from the managed Delta table: spark.read.table("backblaze_features_delta").
  • 2Apply intra-quarter temporal split: train = df.filter(col("date") < "2025-12-01") (files 1–61, Oct–Nov); test = df.filter(col("date") >= "2025-12-01") (files 62–92, December only). Never use random split.
  • 3Compute class weights from training data: n0 = train.filter(col("label")==0).count(), n1 = train.filter(col("label")==1).count(). Weight for class 1 = n0 / n1. Add weightCol column to training DataFrame using when(col("label")==1, weight).otherwise(1.0).
  • 4Free-Tier Guardrail: run train.cache() then train.count() to materialize before the Pipeline fit. Without this, CrossValidator re-reads and re-executes all window functions on every fold — this will crash or time out on Community Edition.
  • 5Build Spark ML Pipeline: VectorAssembler (all 14 features → "features") → StandardScaler → GBTClassifier(labelCol="label", weightCol="weight", featuresCol="scaled_features").
  • 6Free-Tier Guardrail: keep ParamGridBuilder to exactly 2–3 combinations: maxIter=[10, 20] and maxDepth=[3] (2 combos) or add maxDepth=[3, 5] (4 combos max). More than 4 param combinations with 3-fold CV will likely exhaust Community Edition memory.
  • 7Wrap in CrossValidator with exactly 3 folds (not 5) and BinaryClassificationEvaluator(metricName="areaUnderROC"). Fit on training set. This step will take several minutes — do not interrupt the cluster.
  • 8Evaluate best model on test set. Report: AUC-ROC (primary), Recall at threshold 0.5 (secondary), Precision at 0.5, Recall at threshold 0.3 (to show the precision-recall tradeoff). Do not report Accuracy — it is not a valid metric for a 1% failure rate dataset and must be explicitly omitted in the paper.
  • 9Extract feature importances from the best GBT model: bestModel.stages[-1].featureImportances. Map back to feature names. Confirm that lag and velocity features for SMART 5, 187, 197, 198 rank higher than the raw point-in-time values — this validates the feature engineering contribution.
  • 10Compare final ML Recall vs. the Backblaze simple rule Recall (from Notebook 02). This comparison is the headline result of the paper: does the ML model identify more failing drives at a comparable or lower false positive rate?

Genie Code Guide — How NB03 Was Actually Built
Why point-in-time snapshots are not enough

Hard drives rarely fail out of nowhere. A drive with 50 reallocated sectors that has been stable for two years is far safer than a drive that had 0 yesterday and jumped to 45 today. Point-in-time SMART values alone cannot distinguish these two scenarios. Project Abstract
Abstract

Hard drive failures in data center environments cause costly unplanned downtime and data recovery operations. This project applies Apache Spark MLlib to the Backblaze Q4 2025 Drive Stats dataset — 92 daily CSV files comprising approximately 30 million drive-days of real production data — to build a binary classifier predicting HDD failure within a 30-day horizon using daily S.M.A.R.T. sensor snapshots. A Spark ML Pipeline incorporates lag and velocity feature engineering (7-day lookback window functions), VectorAssembler, StandardScaler, and a Gradient Boosted Trees classifier with class-weighted training to address severe label imbalance (~1% failure rate). An intra-quarter temporal split (October–November train, December test) prevents data leakage. Intermediate datasets are persisted to Delta Lake on Databricks Community Edition with explicit caching to manage free-tier compute constraints. Results are evaluated using AUC-ROC and Recall — Accuracy is explicitly omitted — and compared against the Backblaze published simple-rule baseline. Chapter 7 caching strategies and a 3-fold CrossValidator with a constrained parameter grid are documented as free-tier optimization guardrails.

Known Challenges & Mitigations
Challenge: Extreme Class Imbalance (~1%)

With only ~1% positive labels after the 30-day window expansion (raw failure rate is even lower), the model will converge to "predict 0 always." Mitigation: compute class weights from training data and pass via weightCol; use AUC-ROC as the CrossValidator metric, not accuracy; tune the decision threshold after training.

Challenge: Free-Tier Compute Limits (Community Edition)

Databricks Community Edition has limited RAM and no autoscaling. Three guardrails are mandatory: (1) call .cache() then .count() on the training DataFrame before fitting CrossValidator — without this, every fold re-executes all window functions from scratch; (2) limit ParamGridBuilder to 2–3 combinations max (4 is the hard ceiling before memory exhaustion); (3) use numFolds=3 in CrossValidator, not 5.

Challenge: Label Engineering Complexity

The 30-day forward label requires a Spark window function that looks ahead: for each serial_number, flag the row as label=1 if any of the next 30 rows contains failure=1. Use max(col("failure")).over(w.rowsBetween(0, 30)). Test the logic on a single drive (filter to one serial_number) before applying to all ~30M rows.

Challenge: Lag Features & Null Handling

The first 7 drive-days of each drive history will have no lag values available (not enough prior rows within Q4 2025). These will be null. Fill all lag and velocity nulls with 0 after computing them. This is a safe imputation — a new drive entering the quarter with no prior SMART growth history should default to "no change."

Model Evaluation
~0.75 pages

  • Report Recall at threshold 0.5 and at a lower threshold (e.g., 0.3) to show the precision-recall tradeoff. In this domain, higher recall at lower precision is operationally preferable.

Conclusion & Future Work
~0.5 pages
  • State whether success criteria were met (AUC-ROC > 0.85, recall > 0.70, beats Backblaze simple rule).
  • Limitations: single operator (Backblaze only), single quarter (Q4 2025), SMART columns vary by drive model, 30-day window is a design choice, Community Edition compute required reduced CV grid.
  • Future Work (high-impact suggestions): (1) Extend to multi-year data (2022–2025) with a multi-year temporal split for stronger generalization.
