HDD Failure Prediction

Backblaze Q4 2025 — Solo implementation on Databricks Community Edition

📋 The Business Problem

Hard drive failures in enterprise data centers cause unplanned downtime, data loss, and emergency hardware costs. The industry standard is reactive replacement — swap the drive after it fails. This project asks: can we predict which drives will fail 30 days before they do, enabling proactive replacement during scheduled maintenance windows?

🌠 The Core Design Choices

Dataset scope: Q4 2025 only (one quarter, uniform schema, no cross-quarter normalization needed).
Storage: Databricks managed Delta tables — no DBFS path management, serverless-compatible.
Label strategy: 30-day forward window — a drive is “failing” today if it dies within the next 30 days.
Evaluation priority: Recall over Precision — missing a real failure (FN) is far more costly than a false alarm (FP).

NB01

Data Ingestion

01_Data_Ingestion.ipynb → saves backblaze_master_delta

❓ Why wildcard path ingestion?

Backblaze releases one CSV file per day. Q4 2025 = 92 separate files. Looping with 92 separate reads would be slow and fragile. A wildcard glob pattern tells Spark to discover and load all matching files in a single distributed read — Spark automatically parallelizes across files and handles schema inference once.

Key code — 01_Data_Ingestion.ipynb › Cell 2
# Load all 92 daily CSV files from the shared directory
workspace_path = "/Workspace/Shared/DS625_Team_Z/backblaze_drive_data_Q4_2025"

raw_df = spark.read.format("csv") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load(workspace_path + "/*.csv")   # <-- wildcard discovers all 92 files
❓ Why only 6 SMART columns out of 100+?

Backblaze publishes 100+ SMART attribute columns, but most are rarely populated or model-specific. Based on Backblaze’s own published research, SMART 5, 9, 187, 188, 197, and 198 are the strongest predictors of impending failure across all manufacturers. Using only these columns reduces the feature matrix from 100+ dimensions to 6, dramatically cutting memory usage on the free-tier cluster and preventing the curse of dimensionality.

❓ Why a 30-day forward label, not a same-day failure flag?

If the label only marks the exact day a drive fails, the model learns to detect drives that are already dying — too late to act. A 30-day forward window labels a drive as “1” for every day in the 30 days before its actual failure date. This teaches the model to recognize early warning patterns while there is still time to schedule a replacement during a maintenance window.

Key code — 01_Data_Ingestion.ipynb › Cell 6 (Label Engineering)
from pyspark.sql.window import Window
from pyspark.sql.functions import max as spark_max, col

# For each drive, look forward 30 rows (days) and check if any = 1
w = Window.partitionBy("serial_number").orderBy("date").rowsBetween(0, 30)

labeled_df = clean_df.withColumn(
    "label",
    spark_max(col("failure")).over(w)   # 1 if failure happens in next 30 days
)
❓ Why Delta Lake (managed table) instead of Parquet files?

On Databricks Community Edition (serverless compute), calling .cache() or .persist() on write is forbidden — the cluster will throw an error. Delta Lake’s managed table format provides transaction logging, schema enforcement, and O(1) read access from any downstream notebook via spark.table("backblaze_master_delta") with no path management required. It also supports .mode("overwrite") safely, which raw Parquet does not guarantee.

Key code — 01_Data_Ingestion.ipynb › Cell 8 (Write to Delta)
# Write directly as a managed Delta table (no .cache() on serverless)
labeled_df.write.format("delta") \
    .mode("overwrite") \
    .saveAsTable("backblaze_master_delta")

print("Master dataset saved as managed Delta table.")

NB03

Feature Engineering

03_Feature_Engineering.ipynb → saves backblaze_features_delta

❓ Why add lag features?

A raw SMART value is a snapshot in time. It tells us the current state of the drive, but not how it got there. A drive with smart_5_raw = 50 looks the same today whether it had 50 last week (stable) or 0 last week (rapidly deteriorating). The 7-day lag captures the historical context — what the drive looked like one week ago — making the recent value meaningful.

❓ Why add velocity (delta) features?

The rate of change is often more predictive than the absolute value. A drive that has steadily accumulated 2,000 reallocated sectors over 3 years is less alarming than one that went from 0 to 500 in 7 days. The delta feature (smart_5_delta_7 = smart_5_raw − smart_5_lag_7) directly encodes this deterioration rate. A sudden positive spike is a strong failure precursor that the GBT model can learn to weight heavily.

❓ Why only SMART 5 and SMART 187 for lag/delta (not all 6)?

EDA confirmed that SMART 5 (49x spike) and SMART 187 (74x spike) have the clearest and most consistent signal across all manufacturers. SMART 197 and 198 also spike, but their relationship is highly correlated with SMART 5 — adding lag/delta for all four would introduce multicollinearity without meaningful information gain. We get 2 additional features per attribute = 4 new features total.

Key code — 03_Feature_Engineering.ipynb › Cells 4 & 6
from pyspark.sql.window import Window
from pyspark.sql import functions as F

w = Window.partitionBy("serial_number").orderBy("date")

# 7-day lag features (coalesce handles null on first 7 days of drive history)
lag_df = base_df \
    .withColumn("smart_5_lag_7",   F.coalesce(F.lag("smart_5_raw", 7).over(w),   F.col("smart_5_raw"))) \
    .withColumn("smart_187_lag_7", F.coalesce(F.lag("smart_187_raw", 7).over(w), F.col("smart_187_raw")))

# Velocity (delta) features = current - lag
engineered_df = lag_df \
    .withColumn("smart_5_delta_7",   F.col("smart_5_raw")   - F.col("smart_5_lag_7")) \
    .withColumn("smart_187_delta_7", F.col("smart_187_raw") - F.col("smart_187_lag_7"))

engineered_df.write.format("delta").mode("overwrite").saveAsTable("backblaze_features_delta")

Model Training & Evaluation

04_Model_Training_and_Evaluation.ipynb

❓ Why temporal split instead of random split?

In time-series data, a random 80/20 split would put drive records from October and December in both the training and test sets. This causes data leakage: the model “sees” future behavior of the same physical drive during training, leading to inflated test scores that collapse in production. The temporal boundary (December = test set) exactly mimics real deployment: train on past data, predict on future data the model has never seen.

Key code — 04_Model_Training_and_Evaluation.ipynb › Cell 4
# Strict chronological split — no shuffling, no random seeds
train_df = feature_df.filter(feature_df.date < '2025-12-01')   # Oct + Nov
test_df  = feature_df.filter(feature_df.date >= '2025-12-01')  # December

print(f"Train rows: {train_df.count()}")  # 20,453,101

❓ Why dynamic class weights?

With ~1,539 healthy rows for every failing row in the training set, a standard GBT would learn to always predict “healthy” — it minimizes loss by ignoring the rare class. Dynamic class weights (count_0 / count_1) assign a penalty of ~1,539× to each misclassified failure. This mathematically forces the model to treat every missed failure as a catastrophic loss, not a minor statistical blip.

Key code — 04_Model_Training_and_Evaluation.ipynb › Cell 6
count_0 = train_df.filter(train_df.label == 0).count()
count_1 = train_df.filter(train_df.label == 1).count()
weight_factor = count_0 / count_1   # ~1,539x weight on failing class

weighted_train_df = train_df.withColumn(
    "weight",
    F.when(F.col("label") == 1, F.lit(weight_factor)).otherwise(F.lit(1.0))
)
❓ Why GBTClassifier, and why package it in a Pipeline?

GBT vs. Random Forest: Gradient Boosted Trees build each tree to correct the residual errors of the previous tree. With extreme class imbalance, this iterative error-correction mechanism is more effective than a Random Forest’s simple voting majority. GBT can also natively use the weightCol parameter. Pipeline: Wrapping VectorAssembler + GBT in a single Pipeline object ensures the exact same feature assembly steps are applied consistently at fit and transform time — critical for reproducibility and future deployment.

❓ Why is 0.25% precision acceptable?

This is the Base Rate Fallacy at work. With only 1,567 actually-failing drive-days in December but over 10 million healthy ones, even a 4.5% false positive rate on healthy drives produces 450,000+ false alarms. The math: Precision = 1,167 / (1,167 + 458,638) = 0.25%. This is mathematically unavoidable at this class ratio — not a model defect. In production, the cost of a false positive is a scheduled drive swap (cheap), while the cost of a false negative is unplanned downtime and data loss (catastrophic). The asymmetric cost structure justifies optimizing for recall.

⚠ Why we excluded Accuracy from all metrics

A model that predicts “healthy” for every single drive-day achieves 99.93% accuracy with 0% recall. Accuracy is a misleading metric for any imbalanced dataset. We report AUC-ROC (ranking quality across all thresholds) and Recall (what fraction of real failures we caught).

📊 Why Recall is the right primary metric

The business question is: “Did we catch the drive before it failed?” — not “Were we right every time we raised an alert?” Recall = TP / (TP + FN) = fraction of actual failures caught. The GBT model caught 74.47% of December failures — meaning for every 100 drives that were going to fail, we flagged 74 of them in advance. The baseline only caught 66.
