The Promise of Instant Communication

When Stewart Butterfield and his team launched Slack in August 2013, they were building what seemed like a simple product: a chat application for teams. Under the hood, however, real-time messaging is one of the hardest problems in distributed systems. Every message typed by any user needs to appear on the screens of every other user in that channel within milliseconds. At small scale, this is trivial. At Slack scale, it becomes an engineering challenge that touches every layer of the stack.

The early architecture was straightforward. A user opened Slack in their browser, which established a WebSocket connection to one of several application servers. When a user sent a message, the server wrote it to a MySQL database, then fanned it out to every other connected user in the channel by iterating through all active WebSocket connections. For a few thousand users, this worked beautifully. For a few hundred thousand, cracks began to appear.

The Fan-Out Problem

The fundamental challenge of real-time messaging is fan-out: when one user posts a message in a channel with 10,000 members, that single write must be delivered to 10,000 open connections, each potentially on a different server. In the early days, Slack handled this by having each application server maintain a list of connected users and their channel memberships. When a message arrived, the server published it to a Redis pub/sub cluster, and every application server that had connected members in that channel would pick it up and push it to the relevant WebSocket connections.

This worked until it did not. As the user count climbed past a million daily actives, the Redis pub/sub layer became a bottleneck. Large channels with thousands of members caused thundering herd problems: a single message would trigger thousands of near-simultaneous writes across dozens of servers. CPU usage would spike, message delivery would lag, and users would see the dreaded "reconnecting" indicator.

Flannel: The Edge Cache That Changed Everything

By 2017, Slack had identified the core insight that would reshape their architecture: messaging is overwhelmingly read-heavy. For every message sent, there are dozens or hundreds of reads. Users scroll through history, load channels, search for old conversations. The write path was well-optimized, but every read was hitting the same backend services, creating contention with the real-time delivery pipeline.

The solution was Flannel, an edge caching layer that sat between clients and the backend. Flannel maintained a lazy-loaded, eventually consistent copy of workspace data — channel lists, user profiles, message history — close to the connection layer. When a client needed data that had not changed recently, Flannel served it directly without touching the backend at all. This reduced backend load by roughly 50 percent for some workspaces and dramatically improved perceived latency for common operations like switching channels.

Flannel also handled the tricky problem of initial connection state. When a user opened Slack, the client needed to know about every channel the user belonged to, the last read position in each, unread counts, and the current presence status of teammates. Before Flannel, this "boot" sequence required dozens of API calls and could take several seconds for users in large workspaces. Flannel collapsed it into a single, pre-computed payload.

The Connection Gateway Rewrite

Even with Flannel reducing backend pressure, the WebSocket layer itself was struggling. Each application server maintained thousands of WebSocket connections and was responsible for both business logic and connection management. These two concerns had very different scaling characteristics: connection management is I/O-bound and benefits from many lightweight processes, while business logic is CPU-bound and benefits from fewer, more powerful processes.

In 2019, Slack undertook a major architectural change: they separated the connection gateway from the application logic. The new gateway servers were purpose-built to handle WebSocket connections at scale. Written to be as lightweight as possible, each gateway server could handle an order of magnitude more connections than the old application servers. The gateway knew nothing about business logic — it was purely a message router that accepted connections, authenticated them, and forwarded messages between clients and the backend services.

This separation had cascading benefits. Gateway servers could be scaled independently of application servers. Connection management code could be optimized without risking business logic regressions. And most importantly, a bug in message processing could no longer crash the connection layer, which meant that even during backend incidents, clients stayed connected and could see a "degraded" state rather than losing their connection entirely.

Presence: The Sneaky Hard Problem

One of the most technically challenging features in any messaging system is presence — the green dot that tells you whether a teammate is online. It seems trivial: a user connects, mark them online; they disconnect, mark them offline. But at scale, presence is a distributed consensus problem. A user might have Slack open on their laptop, phone, and desktop simultaneously. They might lose network connectivity for a few seconds. Their phone might go to sleep. Each of these transitions needs to be tracked, debounced, and aggregated into a single presence state.

Slack solved this with a dedicated presence service that maintained a time-windowed view of user activity. Rather than treating presence as a binary online/offline state, the service tracked the last activity timestamp for each connection and each device. A user was considered "active" if any device had reported activity within a configurable window (typically two minutes). This approach was more tolerant of brief connectivity interruptions and produced fewer spurious presence toggles, which users found distracting.

The presence service also had to handle fan-out: when a user's presence changed, every workspace member who had that user visible in their sidebar needed to be notified. For users in large organizations, a single presence change could trigger notifications to tens of thousands of connections. The service batched these updates and used a priority system to ensure that changes for users you were actively chatting with were delivered instantly, while changes for peripheral contacts could be slightly delayed.

Lessons from the Trenches

Slack's journey from a simple chat tool to a platform handling millions of concurrent connections offers several universal lessons. The first is that real-time systems have fundamentally different scaling characteristics than request-response systems. Traditional web scaling wisdom — add more servers behind a load balancer — breaks down when every server needs to know about the state of every connected user. The second is that separating concerns is not just good software engineering — it is an operational necessity. Mixing connection management with business logic created failure modes that were nearly impossible to debug.

Perhaps most importantly, Slack discovered that optimizing for the read path is almost always more impactful than optimizing for the write path. In a messaging system, reads outnumber writes by a wide margin. By investing in Flannel and reducing unnecessary backend calls, Slack improved the experience for every user without needing to change the write pipeline at all. This insight — that caching and pre-computation can transform the performance of read-heavy systems — applies far beyond messaging.

What Would You Do?

Your messaging app has 100K concurrent users. Messages are delayed by 2-3 seconds. Redis pub/sub is at capacity and large channels cause thundering herd spikes. How do you fix it?

A) Add more Redis instances and shard pub/sub by channel name to distribute the fan-out load.
B) Switch from WebSockets to HTTP long-polling so you can use standard load balancers and CDN caching.
C) Separate the connection gateway from application logic, add an edge cache for read-heavy data, and batch presence updates.
D) Limit channel size to 500 members and force large groups to use multiple smaller channels.
Slack chose C — architectural separation with edge caching. Simply sharding Redis (option A) would have helped temporarily, but the fundamental problem was that connection management and business logic were co-located, creating coupled failure modes. Switching to long-polling (B) would have dramatically increased latency and server load. Limiting channel sizes (D) would have crippled the product for enterprise customers. By separating the connection gateway, adding Flannel as an edge cache, and batching presence updates, Slack addressed the root causes rather than symptoms. The gateway rewrite let connection servers scale independently, Flannel eliminated redundant backend reads, and batched presence reduced the thundering herd effect on large channels.

Lessons Extracted

Separate connection management from business logic. WebSocket servers and application servers have different scaling needs. Mixing them creates coupled failure modes where a business logic bug can disconnect all users on that server.
Edge caching transforms read-heavy workloads. Flannel reduced backend load by 50% by serving frequently-accessed data from a cache layer close to the connection tier. Most real-time systems are far more read-heavy than write-heavy.
Presence is a distributed systems problem. Tracking online/offline status across multiple devices and intermittent connections requires careful debouncing, time windows, and priority-based fan-out.
Graceful degradation preserves user trust. By keeping users connected even during backend incidents, Slack avoided the anxiety-inducing "reconnecting" state. A degraded experience is far better than a disconnected one.
Batch and prioritize fan-out. Not all notifications are equally urgent. Delivering messages from active conversations instantly while slightly delaying peripheral updates reduces peak load without hurting perceived performance.

Key Takeaways

Real-time systems scale differently than request-response systems — every server needs awareness of shared state.
Caching and pre-computation on the read path often delivers more impact than optimizing the write path.
Separating infrastructure concerns (connections vs. business logic) enables independent scaling and fault isolation.
User-facing features like presence indicators can be surprisingly expensive at scale and deserve dedicated architecture.
