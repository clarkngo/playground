What Is a Leap Second?

Earth does not rotate at a perfectly constant speed. Tidal forces, earthquakes, and changes in the planet's core cause tiny variations in the length of a day. Over time, these small discrepancies accumulate, and astronomical time (based on Earth's rotation) drifts away from atomic time (measured by cesium clocks). To reconcile the two, the International Earth Rotation and Reference Systems Service occasionally inserts an extra second — a "leap second" — at the end of June 30 or December 31.

On December 31, 2016, at 23:59:59 UTC, clocks counted an extra beat: 23:59:60. Then midnight struck. For most people, this was invisible. For Cloudflare's DNS infrastructure, it was catastrophic.

Inside RRDNS

Cloudflare runs a custom DNS server called RRDNS (round-robin DNS) that handles billions of DNS queries every day. RRDNS uses weighted round-robin to distribute queries across healthy upstream servers. To make routing decisions, it calculates how long each upstream takes to respond. The latency measurement was simple: record a timestamp when the query goes out, record another when the response comes back, subtract to get the duration.

The code used Go's time.Now() function for both timestamps. Under normal conditions, subtracting two sequential time.Now() values always produces a positive duration. The code asserted this with a check: if the duration was negative, something had gone terribly wrong, and the program should panic.

The Bug

When the leap second was applied, some NTP-synchronized clocks jumped backward by one second. If an RRDNS instance had recorded the outgoing timestamp at 23:59:60.5 and received the response at 00:00:00.1 (after the clock adjusted), the subtraction produced a negative duration: the response appeared to have arrived before the request was sent.

// Simplified version of the bug
start := time.Now() // 23:59:60.500
// ... DNS query happens ...
end := time.Now() // 00:00:00.100 (clock jumped back!)
elapsed := end.Sub(start) // = -0.4 seconds (NEGATIVE!)

if elapsed < 0 {
    panic("impossible negative duration") // CRASH
}

The panic brought down RRDNS processes across Cloudflare's network. As processes restarted, many hit the same condition again because the clock adjustment window lasted for a period around the leap second. The result: a rolling wave of crashes that degraded DNS resolution for a significant portion of Cloudflare's customers.

The Fix: Monotonic Clocks

The fix was conceptually simple but revealed a deep lesson about time in computers. Operating systems maintain two kinds of clocks. The "wall clock" (what time.Now() returns) tells you what time it is — but it can jump forward or backward when NTP adjusts it or when leap seconds are applied. The "monotonic clock" only ever counts forward, regardless of NTP adjustments, and is designed specifically for measuring elapsed time.

Cloudflare replaced time.Now() with a monotonic clock source for all duration measurements. They also removed the panic-on-negative-duration assertion and replaced it with a graceful fallback that treated impossible durations as zero. The Go programming language itself was later updated (Go 1.9) to make time.Now() transparently use monotonic clocks for duration calculations, preventing this entire class of bug.

Broader Impact

Cloudflare was not the only company affected by the 2016 leap second. Several other services experienced degraded performance. But Cloudflare's incident was especially instructive because the bug was so subtle: the code was correct in all normal circumstances. Only the interaction of a rare astronomical event with a specific clock behavior could trigger it.

The incident contributed to a broader industry conversation about eliminating leap seconds entirely. In November 2022, the General Conference on Weights and Measures voted to abolish leap seconds by 2035, citing the growing risks they pose to digital infrastructure.

Architecture: The Clock Problem

What Would You Do?

Your distributed system uses wall clock timestamps to measure request latency. A colleague points out that NTP can cause clocks to jump. You need a fix before the next leap second. What approach do you take?

A) Add a check that clamps negative durations to zero — if the clock jumps back, just report 0ms latency.
B) Switch all duration measurements to monotonic clocks, which only count forward and are immune to NTP adjustments and leap seconds.
C) Disable NTP on your servers so clocks never jump. Use your own internal time synchronization.
The correct answer is B — use monotonic clocks for duration measurement. Wall clocks answer "what time is it?" while monotonic clocks answer "how much time has passed?" These are fundamentally different questions, and using the wrong clock type is a classic distributed systems bug. Option A (clamping) is a band-aid that hides real issues. Option C (disabling NTP) would cause your clocks to drift, creating far worse problems. Most modern languages now default to monotonic clocks for duration calculations — Go added this in 1.9 specifically because of this class of bug.

Lessons Extracted

Wall clocks are not monotonic. Never subtract two wall clock readings to measure elapsed time. Wall clocks can jump forward, backward, or repeat values. Use monotonic clocks for duration measurement.
Assertions that panic are dangerous in production. An assertion that triggers a crash is appropriate in development but catastrophic in production. Graceful degradation — logging the anomaly and using a safe default — is almost always better than crashing.
Rare events compound in distributed systems. A leap second happens roughly once every 18 months. But when it does, it hits every server simultaneously. Events that are rare for one machine become certain for a fleet.
Test your time assumptions. Mock clock jumps, NTP steps, and leap seconds in your test suite. If your code does arithmetic with timestamps, it needs to handle non-monotonic behavior.
Post-mortems drive industry-wide improvement. Cloudflare's transparent post-mortem helped the Go team add monotonic clock support and contributed to the global decision to phase out leap seconds.

Key Takeaways

Use monotonic clocks for measuring durations; use wall clocks only for knowing the current time.
A single line of code (a subtraction) can take down millions of websites if it makes wrong assumptions about time.
Crash-on-assertion is a development tool, not a production strategy. Prefer graceful degradation.
Transparent post-mortems benefit the entire industry and can drive language-level fixes.
