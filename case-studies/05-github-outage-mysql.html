The 43 Seconds That Broke GitHub

At 22:52 UTC on October 21, 2018, a routine maintenance operation was underway to replace a failing 100G optical networking device in one of GitHub's data centers. The maintenance was planned, reviewed, and expected to be transparent to the application. At 22:54, the network change triggered a brief connectivity loss between the US East Coast data center hub and a primary MySQL database cluster. The partition lasted just 43 seconds.

Forty-three seconds is barely noticeable in human time. But in distributed systems time, it was an eternity. During those 43 seconds, GitHub's topology management system — Orchestrator — detected that the primary MySQL server was unreachable from multiple vantage points. Orchestrator was designed to handle exactly this scenario: when a primary becomes unavailable, promote a replica to take its place and minimize downtime. It did exactly what it was configured to do.

The Automated Response

Orchestrator operated under a design principle that made perfect sense in isolation: if the primary is unreachable, promote a replica to primary so that writes can continue. This is standard failover behavior, and for most scenarios — a crashed server, a hardware failure, a kernel panic — it is the correct response. The problem was that a network partition is not the same as a server failure.

When Orchestrator promoted replicas in the East Coast facility, the original primaries in a separate facility were still running, still accepting writes, and still perfectly healthy. They just could not communicate with the monitoring system that had declared them dead. The result was split-brain: two independent MySQL servers both believing they were the primary, both accepting writes from different application servers, and both accumulating data that the other did not have.

The Discovery

At 23:02 UTC — just eight minutes after the partition began — GitHub engineers detected the split-brain condition. Internal monitoring showed two primaries accepting writes for the same database clusters, with replication broken between them. The writes were diverging: commits, pull requests, issues, and other data were being written to one primary or the other depending on which application server handled the request.

The scope of the problem became clear quickly. This was not a single database — it affected multiple MySQL clusters that stored core GitHub data. Every second that both primaries continued accepting writes increased the complexity of eventual reconciliation. The team needed to make a decision fast.

The Critical Decision: Data Integrity First

At 23:19 UTC, GitHub engineering leadership made the decision that would define the next 24 hours: data integrity trumps availability. For a platform that hosts the source code and collaboration history of millions of developers and organizations worldwide, losing or corrupting data was unacceptable. Even the possibility of a single lost commit or a corrupted pull request was worse than extended downtime.

The team deliberately degraded service — restricting GitHub to read-only mode and blocking new writes — while they assessed the divergence between the two primaries. They needed to understand exactly which writes had gone to which primary, identify all conflicts, and develop a reconciliation plan that would preserve every piece of data from both sides of the split.

The Long Recovery

The recovery process took the rest of the night and most of the following day. Engineers worked through the night building tooling to compare the write streams from both primaries, identify rows that existed on one side but not the other, and merge the divergent data without introducing inconsistencies. Some of this tooling had to be written from scratch under pressure, because the specific failure mode — two MySQL primaries with partially overlapping but divergent write sets — was not something their existing recovery tools were designed to handle.

By the afternoon of October 22, GitHub had reconciled the divergent data and restored full read-write service. Approximately 5% of writes during the incident window were affected. No data was lost — every commit, every issue, every pull request from both sides of the split was preserved. The team had succeeded in their primary objective: complete data integrity, even at the cost of extended downtime.

The Post-Mortem

GitHub published one of the most detailed and transparent post-mortem reports in the industry. They did not blame individuals. They did not minimize the impact. They described the full sequence of events, the decisions they made and why, and the specific changes they would implement to prevent recurrence. Among the changes: modifying Orchestrator to require cross-datacenter confirmation before promoting during network events, implementing improved split-brain detection, and adding manual confirmation gates for failover during maintenance windows.

The post-mortem became a widely studied reference in the infrastructure community. It demonstrated that even the most sophisticated organizations — running well-tested automation, with experienced on-call engineers — can be caught by the gap between what automated systems are designed for (server failure) and what actually happens (network partition with all servers healthy).

What Would You Do?

Split-brain MySQL detected: two primaries have been accepting divergent writes for several minutes. Millions of developers depend on this platform. What do you do?

A) Pick the primary with more writes, discard the other — accept some data loss to restore service quickly.
B) Stop all writes, assess the divergence, and reconcile manually — prioritize data integrity over availability.
C) Let both primaries continue and merge the data later — keep the service running and sort it out afterwards.
GitHub chose B — stop writes and reconcile manually. For a source code hosting platform, data integrity is paramount. Discarding writes (option A) means potentially losing commits, issues, or pull requests — unacceptable for a platform developers trust with their code. Letting both continue (option C) would only increase the divergence and make reconciliation exponentially harder, while risking data corruption from conflicting writes. By stopping writes immediately and carefully reconciling, GitHub preserved every piece of data from both sides of the split, even though it took 24 hours of degraded service to accomplish.

Lessons Extracted

Automated failover can cause split-brain. Orchestrator did exactly what it was designed to do — promote a replica when the primary was unreachable. But it could not distinguish between a dead server and a network partition, and the correct response to each is fundamentally different.
Data integrity must trump availability for source code. For a platform that developers trust with their most valuable digital assets, losing even a single commit is worse than hours of downtime. This trade-off must be explicit in your architecture.
Network partitions happen to everyone. GitHub runs sophisticated infrastructure with experienced engineers. A 43-second partition during routine maintenance was enough to trigger a 24-hour incident. No organization is immune.
Post-mortems must be blameless and public. GitHub's transparent post-mortem built trust with their community and provided invaluable learning material for the entire industry. Blame-free analysis of failures produces better systemic improvements than finger-pointing.

Key Takeaways

Automated failover systems must distinguish between server failure and network partition.
Data integrity must be the non-negotiable priority for platforms that store irreplaceable user data.
Network partitions happen to everyone — even during routine, well-planned maintenance.
Blameless, public post-mortems build trust and drive better systemic improvements than any other response.
