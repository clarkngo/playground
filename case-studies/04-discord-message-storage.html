The MongoDB Beginning

When Discord launched in 2015, MongoDB was the natural choice for message storage. It was flexible, developer-friendly, and perfectly adequate for a startup finding its product-market fit. Messages were stored as documents with channel IDs, timestamps, and content. For the first year, this worked well enough.

But Discord grew faster than anyone anticipated. Gamers adopted it voraciously, and by late 2015, the message volume was climbing toward 100 million stored messages. MongoDB began running out of memory as the working set exceeded available RAM. The single-writer architecture could not keep up with the write throughput, and read latency was becoming unpredictable as the dataset grew. Discord needed a database designed for horizontal scaling.

The Cassandra Era

In 2016, Discord migrated their message storage to Apache Cassandra. The choice made sense on paper: Cassandra offered linear horizontal scaling, tunable consistency, and excellent write throughput. Messages were partitioned by channel ID and bucketed by time, ensuring that messages for the same channel were co-located on the same nodes for efficient retrieval.

For two years, Cassandra performed admirably. Discord scaled from millions to billions of messages without fundamental issues. The distributed architecture handled node failures gracefully, and the write performance was excellent. Cassandra seemed like the right long-term solution.

The Hot Partition Crisis

By 2018, certain Discord servers had grown enormous — communities with hundreds of thousands of members generating tens of thousands of messages per day in a single channel. These channels became hot partitions: single Cassandra partitions receiving disproportionate read and write traffic. Hot partitions caused localized latency spikes that affected other channels sharing the same nodes.

The team worked to mitigate this through partition splitting strategies and more granular time bucketing, but the underlying issue persisted. Some channels were simply orders of magnitude more active than others, and Cassandra did not natively load-balance within a partition key.

The GC Pause Cascade

The real breaking point came in 2020. Cassandra runs on the JVM, and as the data volume grew into the hundreds of billions of messages, garbage collection pauses became a critical problem. During compaction — the process where Cassandra merges and cleans up SSTables on disk — the JVM would allocate large amounts of temporary memory, triggering long GC pauses that could last hundreds of milliseconds or even seconds.

When a node paused for GC, it stopped responding to requests. Other nodes in the cluster would mark it as potentially down. Requests would be rerouted, increasing load on healthy nodes and pushing them closer to their own GC thresholds. This created a cascade effect: one node pausing could trigger a chain reaction of GC pauses across the cluster, causing P99 latencies to spike from 40 milliseconds to hundreds of milliseconds or more.

The team spent months tuning JVM garbage collection parameters, experimenting with different GC algorithms, and adjusting Cassandra compaction strategies. Each tuning effort brought temporary relief, but the fundamental problem was structural: the JVM garbage collector was not designed for the allocation patterns that a distributed database with trillions of messages generates during compaction.

The ScyllaDB Migration

In 2022, Discord made the decision to migrate from Cassandra to ScyllaDB. ScyllaDB is a drop-in replacement for Cassandra written in C++ instead of Java. It uses the same CQL query language, the same data model, and the same SSTable format, but it eliminates the JVM entirely. No JVM means no garbage collector. No garbage collector means no GC pauses.

ScyllaDB also uses a shard-per-core architecture where each CPU core owns a specific subset of data and handles all operations for that data independently. This eliminates cross-core coordination overhead and provides predictable, low-latency performance regardless of cluster load or compaction activity.

The results were dramatic. P99 latency dropped from 40 milliseconds to 4 milliseconds — a 10x improvement. The cascading GC pause problem vanished entirely. The cluster required fewer nodes to handle the same workload because ScyllaDB used hardware more efficiently without JVM overhead. Discord could now store and serve trillions of messages with consistent, predictable latency.

What Would You Do?

Your Cassandra cluster is experiencing cascading GC pauses during compaction on hot partitions. P99 latency is spiking to hundreds of milliseconds. How do you fix it?

A) Tune JVM GC parameters — switch to ZGC or Shenandoah, increase heap size, adjust GC thresholds.
B) Reshard the data — split hot partitions into smaller chunks and redistribute across more nodes.
C) Migrate to ScyllaDB — a C++ Cassandra-compatible database with no JVM or garbage collector.
Discord chose C — migrating to ScyllaDB. They had already spent months tuning JVM GC parameters (option A) with diminishing returns — the problem was structural, not configurational. Resharding (option B) helped with hot partition issues but did nothing about GC pauses during compaction, which affected all nodes regardless of data distribution. ScyllaDB eliminated the root cause entirely by removing the JVM. The Cassandra-compatible API meant Discord could migrate without rewriting their application layer, and the results were immediate: P99 dropped from 40ms to 4ms with zero GC pauses.

Lessons Extracted

Database selection is not permanent. Discord changed databases twice as their scale and requirements evolved. The best database at 100 million messages is not the best at 4 trillion.
JVM GC is a real bottleneck at scale. Garbage collection pauses that are imperceptible at small scale can become system-threatening at large scale, especially during compaction of large datasets.
Hot partitions require partition-aware data modeling. Uneven access patterns will always exist. The data model and the database must be designed to handle them gracefully rather than assuming uniform distribution.
Sometimes the best fix is a platform change. When you have exhausted tuning options and the problem is structural, changing the underlying platform can provide step-function improvements that no amount of optimization can match.

Key Takeaways

Database selection is not permanent — revisit as scale and requirements evolve.
JVM garbage collection becomes a real bottleneck at extreme scale, especially during compaction.
Hot partitions require partition-aware data modeling, not just more nodes.
Sometimes the best fix is a platform change rather than endless tuning of the current one.
