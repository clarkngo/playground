The Naive Beginning: Pull on Read

When Twitter launched in 2006, the timeline was simple. When a user opened their home feed, the system would query the database for every account that user followed, fetch recent tweets from each, merge them by timestamp, and return the result. This is the fan-out-on-read approach: do all the work at read time.

For a small social network, this was perfectly adequate. But Twitter grew explosively. By 2010, users were requesting hundreds of millions of timeline views per day. Each view triggered dozens of database queries — one per followed account. The database was buckling under the read load, and timeline latency was climbing into seconds rather than milliseconds.

The Redis Revolution: Fan-Out-on-Write

Twitter engineers realized they could invert the problem. Instead of assembling timelines at read time, they could pre-compute them at write time. When a user posted a tweet, the system would immediately push that tweet into the Redis-cached timeline of every follower. When a user opened their feed, the pre-computed timeline was already sitting in Redis, ready to serve in under 5 milliseconds.

This was fan-out-on-write, and it was transformative. Read latency dropped dramatically. The user experience became snappy and responsive. Twitter invested heavily in a massive Redis cluster — thousands of nodes holding hundreds of millions of pre-computed timelines in memory. For the average user with a few hundred followers, this was elegant and efficient.

The Celebrity Problem

Then came the thundering herd. When a celebrity with 50 million followers posted a tweet, the fan-out system needed to write that single tweet into 50 million separate Redis timelines. This created enormous write amplification — a single tweet generating tens of millions of write operations. The fan-out for a single celebrity tweet could take minutes to propagate, during which some followers would see the tweet and others would not.

Worse, when multiple celebrities tweeted in rapid succession, the write queues would back up catastrophically. The fan-out workers would fall behind, timelines would go stale, and the entire system would degrade. The very optimization that made normal timelines fast was causing systemic instability when applied to accounts with massive follower counts.

The Hybrid Solution

Twitter settled on a hybrid architecture that combined the best of both approaches. For normal users — those with fewer than roughly 500,000 followers — fan-out-on-write continued as before. Their tweets were pre-computed into follower timelines at write time, keeping read latency low for the vast majority of timeline requests.

For celebrity accounts exceeding the follower threshold, the system switched to fan-out-on-read. Celebrity tweets were not pushed into individual timelines. Instead, when a user opened their feed, the system would fetch their pre-computed timeline from Redis and then merge in recent tweets from any celebrity accounts they followed, queried at read time. This added a small amount of read latency but eliminated the catastrophic write amplification.

The threshold was not arbitrary. Twitter engineers analyzed the cost curves: below 500,000 followers, the write cost of fan-out was cheaper than the read cost of merging. Above that threshold, the economics flipped. The hybrid approach optimized for the common case while providing an escape hatch for the extreme case.

Engineering at the Edge

The hybrid timeline architecture required sophisticated engineering beyond the basic push/pull split. The merge operation at read time had to be fast enough that users could not perceive the difference between a fully pre-computed timeline and one that included celebrity merges. Twitter built custom merge algorithms that could combine sorted streams from Redis and the celebrity tweet cache in constant time relative to the number of celebrities a user followed.

The system also needed to dynamically reclassify accounts as they crossed the follower threshold. An account going viral could jump from thousands to millions of followers in hours. The fan-out system had to detect these transitions and seamlessly switch the account from write-path to read-path distribution without losing any tweets or creating duplicates in follower timelines.

What Would You Do?

A celebrity with 30 million followers just posted a tweet. Your system uses fan-out-on-write. How do you deliver this tweet to all followers?

A) Fan-out to all 30 million follower timelines — push the tweet into every Redis timeline as usual.
B) Fan-out-on-read for this user — skip the write fan-out and merge this celebrity's tweets at query time when followers load their timelines.
C) Delay delivery and batch the writes — queue the fan-out and process it gradually over several minutes to reduce write pressure.
Twitter chose B — fan-out-on-read for celebrity accounts. Writing a single tweet into 30 million Redis timelines creates massive write amplification that can destabilize the entire cluster. Instead, celebrity tweets are stored separately and merged into follower timelines at read time. The slight increase in read latency is far preferable to the catastrophic write storms that fan-out-on-write causes for accounts with tens of millions of followers. Batching (option C) only delays the problem without solving it.

Lessons Extracted

Hybrid approaches beat pure strategies. Neither fan-out-on-write nor fan-out-on-read was optimal for all cases. The best solution combined both, applying each where it was most cost-effective.
Hot-key problems require special handling. Celebrity accounts are hot keys in disguise. Any system that treats all keys uniformly will eventually be brought down by extreme outliers.
Pre-computation trades write cost for read speed. Fan-out-on-write is a classic example of shifting work from the read path to the write path. This trade-off only makes sense when write amplification remains bounded.
Real-world systems need escape hatches for edge cases. The 500K follower threshold is an escape hatch — a pragmatic acknowledgment that no single strategy handles the full distribution of user behavior.

Key Takeaways

Hybrid approaches beat pure strategies when workload distributions have extreme outliers.
Hot-key problems require special handling — treating all entities uniformly breaks at scale.
Pre-computation trades write cost for read speed, but only works when write amplification is bounded.
Real-world systems need escape hatches for edge cases that violate baseline assumptions.
