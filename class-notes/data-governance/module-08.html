01 What Is Integration?
Definition
Integration
The practice of connecting disparate applications, systems, and data sources so they can exchange information and work together as a cohesive whole — without requiring each system to be rewritten or exposed internally.

Every organization runs multiple systems: a CRM, an ERP, a data warehouse, a streaming platform, legacy mainframes, and SaaS tools. None of these were designed to work together. Integration is the bridge that establishes communication between these heterogeneous applications — treating each system as a black box, interacting only through its external interface.

Integration also solves the legacy-to-modern communication problem: a decades-old COBOL mainframe needs to send transactions to a cloud-native microservice. The integration layer translates, routes, and mediates without requiring either system to change.

The Two Core Integration Challenges
🔗 Connectivity
Can two systems physically exchange data? This is a protocol problem — HTTP vs SOAP vs MQ vs file transfer. Integration middleware handles protocol translation so each system speaks in its own language while still communicating.
📊 Semantic Alignment
Can two systems understand each other's data? A "customer ID" in the CRM may differ from "client code" in the ERP. Integration must map, transform, and validate data so the receiving system interprets it correctly.
💡 Integration as a Governance Problem
Poor integration creates shadow data flows — undocumented point-to-point connections that bypass governance controls. Every integration point is a potential data quality, security, and compliance risk. This is why integration governance is as important as the integration technology itself.
02 Integration Pattern Taxonomy

Integration is not one-size-fits-all. Different patterns suit different communication needs. Choosing the wrong pattern leads to latency, data loss, tight coupling, or unnecessary complexity.

API / Request-Response
Synchronous · HTTP
Client sends a request and waits for a response. Suited for small data, real-time queries, and CRUD operations. The consuming system must be available.
Streaming / Pub-Sub
Asynchronous · Continuous
Producers publish events to a channel; all subscribers receive them. Suited for high-volume, continuous flows like telemetry, feeds, and CDC.
Event-Driven
Asynchronous · Decoupled
Components react to events without direct coupling. Workflows emerge from event reactions rather than direct calls. Suited for complex, decoupled business processes.
Service-Based (RPC / Messaging)
Sync or Async · Service
Services communicate via remote procedure calls or message queues. Used in microservices and SOA architectures to coordinate distributed capabilities.
Batch / Data Integration
Scheduled · Bulk
Large volumes of data transferred at scheduled intervals. Suited for ETL pipelines, reporting, and analytics loads where near-real-time is not required.

03 Service-Oriented Architecture (SOA)
Definition
Service-Oriented Architecture (SOA)
An architectural style where software capabilities are packaged as discrete, interoperable services — each with a well-defined interface — that can be discovered, composed, and reused across the enterprise regardless of the underlying platform or language.

SOA emerged in the 2000s as a response to monolithic enterprise applications that were impossible to reuse or integrate. The core idea: instead of building point-to-point integrations between every pair of systems, define a common service interface so any authorized consumer can call any service.

SOA Design Principles
1
Standardized Service Contract
Services express their purpose and capabilities through a formal contract (WSDL, OpenAPI) that any consumer can read and use.
2
Loose Coupling
Services minimize dependencies on each other's internals. A change to a service implementation must not break its consumers.
3
Abstraction
The service hides its internal logic. Consumers interact only with the published interface — the underlying technology is invisible.
4
Reusability
A "Customer" service built once can be called by CRM, billing, support, and analytics — no per-integration rewrites.
5
Composability
Complex processes are assembled by orchestrating or choreographing simpler services — the "LEGO brick" model of software.
6
Discoverability & Statelessness
Services are registered in a directory so they can be found. Ideally, each call is self-contained — the service does not retain session state between calls.
💡 SOA vs Microservices
SOA is often described as "services sharing a common platform and ESB" while microservices are "independently deployable services with their own data stores." SOA tends toward larger, coarser-grained services; microservices are fine-grained and autonomous. Both apply the same service contract principle — the scale and deployment model differ.
04 Enterprise Service Bus (ESB)
Definition
Enterprise Service Bus (ESB)
A centralized middleware infrastructure — the "bus" — through which all services in a SOA communicate. The ESB handles message routing, protocol translation, data transformation, security enforcement, and monitoring so services do not need to know how to reach each other directly.

Without an ESB, every system that needs to talk to another must build a custom adapter: System A talks to B in XML over FTP, to C in JSON over HTTP, to D via JDBC. With an ESB, every system connects to the bus once, and the bus handles the translation and routing. This replaces an N-squared web of point-to-point connections with a hub-and-spoke topology.

ESB Capabilities

  • Protocol translation: HTTP ↔ SOAP ↔ JMS ↔ MQ ↔ FTP ↔ JDBC
  • Data transformation: XML ↔ JSON, field mapping, schema conversion
  • Security enforcement: authentication, authorization, encryption at the bus level

⚠ ESB Anti-Pattern: Smart Pipes, Dumb Endpoints
An over-engineered ESB with too much business logic embedded in routing rules becomes a bottleneck and a single point of failure. Governance principle: keep the bus as infrastructure (dumb pipes) and keep business logic in the services (smart endpoints).
05 Service Orchestration
Definition
Service Orchestration
A pattern in which a central orchestrator coordinates the sequence of service calls to fulfill a business process. The orchestrator knows the full workflow — it calls services, handles responses, manages errors, and decides what to do next. Services themselves are unaware of the larger process.

Orchestration is analogous to a conductor directing an orchestra: the conductor knows the full score and signals each section when to play. Each instrument plays its part without knowing the others' parts. In software, the orchestrator is a process engine or workflow service that calls Service A, waits for the result, then calls Service B with that result.

Where Should the Orchestrator Live?

This is a critical architectural decision. There are three options — each with trade-offs:

✕
Consumer-Level Orchestration
The consuming application manages the workflow inline. Problem: the consumer becomes tightly coupled to the internal mechanics of every service it coordinates. Any change to a downstream service breaks the consumer's orchestration logic.
✕
Producer-Level Orchestration
A producing service coordinates downstream delivery. Problem: the producer now knows too much about its consumers — violating the principle of loose coupling. The producer becomes responsible for a workflow it should not own.
✓
Dedicated Orchestration Layer (Recommended)
A separate orchestration service or workflow engine manages the process independently. Producers and consumers are unaware of each other. Examples: AWS Step Functions, Temporal, Apache Airflow, Camunda BPM, Azure Logic Apps.

06 Service Choreography
Definition
Service Choreography
A decentralized coordination pattern where each service reacts to events and decides independently what to do next. There is no central coordinator — services communicate through published events, and the overall process emerges from these local decisions.

Choreography is analogous to a flash mob or a dance troupe where each dancer knows their steps and reacts to the others' cues without a conductor. In software: Service A completes its work and emits an "OrderValidated" event. Service B, which subscribes to that event, picks it up and processes payment. Service C subscribes to "PaymentConfirmed" and initiates shipping — without A or B knowing C exists.

Orchestration vs Choreography
🎭 Orchestration — Central Conductor
  • One entity (orchestrator) knows and controls the entire workflow
  • Services are called explicitly in sequence
  • Easy to visualize and debug — the orchestrator has the full state
  • Single point of control and potential failure
  • Good for: complex multi-step workflows with conditional branching, compensating transactions, auditability
  • Tools: Step Functions, Temporal, Camunda, Airflow
💃 Choreography — Distributed Dancers
  • No central coordinator — each service reacts to events
  • Services publish events; others subscribe and react
  • Highly decoupled — adding a new participant means subscribing to an event
  • Harder to trace overall workflow — state is distributed across services
  • Good for: simple event chains, high-autonomy teams, adding consumers without changing producers
  • Tools: Kafka, RabbitMQ, AWS EventBridge
💡 Choosing Between Them
Use orchestration when you need to see and control the entire process — e.g., an order fulfillment workflow with payments, inventory, and shipping. Use choreography when services should be autonomous and the process is a simple chain of reactions — e.g., a new user signup triggers a welcome email, a CRM update, and a Slack notification, each independently.
07 API Architecture
Definition
API (Application Programming Interface)
A contract that defines how external systems can interact with a service — specifying the available operations, the format of requests and responses, authentication requirements, and error behavior. The API is the public face of a service; the implementation behind it is opaque.

In integration, APIs operate at two OSI model layers, each with different capabilities and use cases:

Layer 7
Application
HTTP-based APIs (REST, GraphQL, gRPC) — content-aware; can inspect request headers and body to make routing, auth, and throttling decisions. The vast majority of modern APIs operate here. API gateways, load balancers, and WAFs typically work at Layer 7.
Layer 3
Network
IP-based routing — operates on packet headers (source/destination IP and port) without reading the payload. Used for low-level TCP/UDP services and network-based load balancing. Not content-aware — cannot distinguish one API call from another based on path or method.
Request-Response Model (Synchronous)

API architecture is fundamentally request-response: the client sends a request and blocks (waits) until the server returns a response. This is the dominant integration style for:

  • CRUD operations — Create, Read, Update, Delete actions on resources (e.g., GET /users/123, POST /orders)
  • Small amounts of data — a discrete object or list, not a continuous data stream
  • Real-time lookups — the caller needs the answer immediately before proceeding
  • Service-oriented integrations — calling a downstream microservice during a request lifecycle
REST vs GraphQL vs gRPC

⚠ Synchronous APIs Are Not Always Right
If the consuming system does not need the result immediately — or if the producing system is slow or unreliable — a synchronous API call creates a temporal coupling: both systems must be up and responsive at the same moment. For fire-and-forget operations, or processes that take more than a few seconds, an asynchronous pattern (queue, event, streaming) is more resilient.
08 API Gateway
Definition
API Gateway
A managed reverse proxy that serves as the single entry point for all API traffic. It enforces cross-cutting concerns — authentication, rate limiting, routing, SSL termination, logging, and caching — so individual services do not have to implement them independently.
Core Functions of an API Gateway
  • Authentication & Authorization: validate JWT tokens, OAuth 2.0 access tokens, or API keys before any request reaches a backend service
  • Rate Limiting & Throttling: enforce per-consumer quotas to prevent abuse and protect downstream services
  • Request Routing: direct traffic to the appropriate microservice based on path, header, or method
  • SSL Termination: decrypt HTTPS at the gateway; internal traffic may run over plain HTTP within a trusted network
  • Response Caching: cache frequent GET responses at the gateway to reduce backend load
  • Observability: centralized access logs, latency metrics, and distributed trace injection
Single Gateway vs Nested Domain Gateways

As the number of services grows, a single gateway hits practical limits — both technical (configuration size, routing rule management) and organizational (one team controls all routes).

Single API Gateway
  • All traffic enters through one gateway instance
  • Simpler to manage at small scale
  • Becomes a bottleneck and configuration nightmare at scale
  • Practical limit: ~1,000 routes/interfaces — beyond this, route management complexity and memory footprint cause issues
  • One team owns all route configurations — slows down teams
Nested / Domain Gateways
  • A top-level gateway routes to domain-specific child gateways
  • Each domain team owns and manages its own gateway
  • Aligns with Data Mesh and domain-driven design
  • Each domain gateway can scale independently
  • Slightly more network hops — but dramatically better governance isolation
Internal vs External Consumers Through the Gateway
  • Internal consumers (within the same domain): access domain-specific APIs directly or through the domain gateway. Contracts are tighter, versioning is managed within the team, governance overhead is lower.
  • External consumers (cross-domain, inter-domain): access published APIs through the top-level gateway. Stricter contracts, mandatory versioning, schema registries, and SLA agreements required.

Note: intra-domain means within a domain; inter-domain means across domains. External consumers cross a domain boundary, making the correct term inter-domain.

Scenario
When to Use Nested Gateways
A financial services company has domains: Payments, Accounts, Fraud, and Reporting. Each domain has 50–100 microservices. A single gateway would accumulate 400+ route configurations maintained by one platform team — a change request backlog measured in weeks. Switching to nested gateways lets each domain team deploy routes independently, with the top-level gateway simply routing /payments/* to the Payments gateway, /accounts/* to the Accounts gateway, and so on.
09 Microservices
Definition
Microservices Architecture
An architectural style where a large application is structured as a suite of small, independently deployable services — each owning a single bounded capability, its own data store, and its own deployment lifecycle — communicating via APIs or messages.

Microservices are the contemporary evolution of SOA, pushed to finer granularity. Where an SOA "Order Management Service" might handle everything related to orders, a microservices architecture might split that into an Order Creation Service, an Order Status Service, a Fulfillment Service, and a Cancellation Service — each deployable and scalable independently.

✅ Microservices Benefits
  • Independent deployment: release one service without touching others
  • Independent scaling: scale only the services under load
  • Technology heterogeneity: each service can use the best language/stack for its job
  • Fault isolation: a failure in one service does not cascade if circuit-breakers are in place
  • Team autonomy: small teams own services end-to-end
⚠ Microservices Challenges
  • Distributed systems complexity: network failures, partial failures, retries
  • Data consistency: no shared database — eventual consistency across services
  • Observability: a single user request may span 20 services — tracing is essential
  • Operational overhead: hundreds of services to deploy, monitor, and upgrade
  • Not suitable for small teams: the overhead outweighs the benefits at low scale
💡 The Key Rule: Each Service Owns Its Data
Microservices must not share a database. If two services share a database, they are coupled at the data layer — a schema change in one breaks the other. Each service owns its own data store (which may be a different technology: PostgreSQL, Redis, DynamoDB, etc.). Cross-service data access happens only through APIs, never through direct DB queries.
10 Functions as a Service (FaaS)
Definition
Functions as a Service (FaaS) / Serverless
An execution model where individual functions are deployed as the unit of compute. The cloud platform manages all infrastructure — provisioning, scaling, and teardown. Functions are stateless, ephemeral, and triggered by events. Developers pay per invocation, not for idle servers.
FaaS Characteristics
  • Trigger-driven: functions run in response to HTTP requests, queue messages, database change events, scheduled timers, or file uploads
  • Stateless: each invocation is independent — no in-memory state persists between calls (use a database or cache for state)
  • Auto-scaled: the platform scales from zero to thousands of concurrent executions automatically
  • Per-invocation billing: cost is proportional to the number and duration of function executions
When to Use vs Avoid FaaS
Use FaaS WhenAvoid FaaS When
Workloads are infrequent or unpredictable in volumeHigh-throughput, continuous processing is required
Event-triggered processing (file upload, queue message)Workload is latency-sensitive (cold start adds 100–3000 ms)
"Glue code" between services — lightweight transformationsStateful workflows — FaaS functions cannot persist state
Cost optimization: spiky workloads with long idle periodsLong-running processes — functions time out (15 min on Lambda)
📷 Case Study: Amazon Prime Video
Real-World Case Study Amazon Prime Video — Moving Away From FaaS (2023)

Prime Video built a video quality monitoring tool (the Defect Detection system) using a fully serverless architecture: AWS Step Functions orchestrated a pipeline of AWS Lambda functions that analyzed each video frame for artifacts, encoding errors, and audio sync issues.

Before — Serverless Architecture
  • AWS Step Functions orchestrated multiple Lambda functions per frame
  • Each state transition in Step Functions incurred a per-transition cost
  • Processing millions of frames per day meant billions of state transitions
  • Hitting AWS Step Functions account limits at scale
  • Intermediate results stored in Amazon S3 between Lambda calls — network I/O overhead
After — Monolithic Service on ECS
  • Consolidated all processing into a single containerized service on Amazon ECS
  • In-process function calls replaced distributed Lambda invocations
  • Shared in-memory buffers replaced S3 for intermediate results
  • No state-transition pricing — one long-running container per stream
  • Simpler architecture, easier debugging and local development
Result: ~90% infrastructure cost reduction. Simpler codebase. Better performance. The team noted that microservices and serverless are powerful tools — but for high-throughput, compute-intensive, continuous workloads, a well-architected monolith can be dramatically more cost-effective.
💡 The Lesson: Match Pattern to Workload
FaaS is not universally superior to traditional services. It excels at event-driven, sporadic, low-duration workloads. For continuous, compute-heavy, or latency-critical workloads, the overhead of cold starts, per-invocation cost, and distributed coordination can make FaaS more expensive and more complex than a containerized monolith or a small set of dedicated services.
11 Service Mesh
Definition
Service Mesh
A dedicated infrastructure layer that manages service-to-service communication within a microservices deployment. It handles traffic management, mutual TLS (mTLS), load balancing, circuit breaking, retries, and observability — without requiring application code changes, by injecting a sidecar proxy alongside every service.

As the number of microservices grows, managing network concerns inside each service becomes unscalable. Every team must independently implement retries, timeouts, circuit breakers, and mTLS — leading to duplication and inconsistency. A service mesh moves all of this to the infrastructure layer using the sidecar pattern.

Sidecar Proxy Pattern
Service A
Envoy Proxy
↔
Service B
Envoy Proxy
↔
Service C
Envoy Proxy

Each service pod gets an Envoy proxy injected as a sidecar container. All inbound and outbound traffic flows through the proxy — the application itself never makes raw network calls. The control plane (Istio, Linkerd) pushes configuration to all proxies centrally.

Service Mesh Capabilities
  • Mutual TLS (mTLS): every service-to-service call is encrypted and both sides authenticate — zero-trust networking within the cluster
  • Traffic management: canary releases, A/B traffic splits, blue-green deployments at the proxy level without code changes
  • Circuit breaking: automatically stop sending requests to a failing service; prevent cascading failures
  • Retries and timeouts: configurable per route — enforce SLA behavior without embedding it in application code
  • Observability: automatic metrics (latency, error rate, request volume), distributed traces, and access logs for every service-to-service call
Scenario — When to Add a Service Mesh
10+ microservices, inconsistent retry logic, no mTLS
A platform team discovers that 12 microservices each implement retry logic differently — some retry 3 times, some once, some not at all. mTLS is implemented in 4 out of 12 services. Introducing Istio with Envoy sidecars enforces consistent retry policies and mTLS cluster-wide from a single control-plane configuration — no service code changes required.
12 Data Integration vs Data Interoperability

These two terms are often used interchangeably but represent fundamentally different goals with different governance implications.

Definition
Data Integration
The technical process of combining data from multiple sources into a unified view. Integration moves, copies, or links data — it is a pipeline problem. The result is consolidated data in one place or format, accessible to consumers.
Definition
Data Interoperability
The ability of systems to exchange and meaningfully use data without custom integration work. Interoperability is a standards problem — when systems share a common vocabulary and format, they can communicate directly.
Dimension Data Integration Data Interoperability
Primary goalUnified access — get data into one placeSeamless exchange — systems understand each other
ApproachTechnical pipelines (ETL, CDC, federation)Standards and semantics (schemas, ontologies, formats)
ResultConsolidated or synchronized datasetSystems that can communicate without custom adapters
Healthcare exampleETL from hospital EHR to data warehouseAll EHRs speak FHIR — direct exchange without adapters
Finance exampleAggregating trades from 5 brokers into a risk DBAll participants use the FIX protocol — direct messaging
Governance needPipeline ownership, lineage, quality controlsSchema standards, ontology governance, certification
💡 The Goal Is Interoperability; Integration Is the Workaround
Every custom ETL pipeline built to connect two systems that use different data models is a symptom of missing interoperability. The more systems adopt common standards — JSON-LD, FHIR, AsyncAPI schemas, ISO date formats — the less bespoke integration work is required. Governance teams should invest in semantic standards first to reduce long-term integration debt.
13 Streaming Architecture
Definition
Streaming Architecture
An asynchronous integration pattern in which data is produced continuously as an ordered sequence of events or records — and consumed by subscribers in near-real time. Unlike request-response, the producer does not wait for a consumer acknowledgement; unlike batch, there is no collection period — data flows as it arrives.

Think of streaming like television broadcasting: a TV station (producer) transmits on a channel continuously. Any viewer (subscriber) who tunes in receives the broadcast. A viewer who is not watching misses what aired. The station does not know — or care — who is watching. This is the publish-subscribe model at its core.

All subscribers receive a copy of every message published to the topic. The broker (mediator) is essential — it manages subscriptions, buffers messages, and ensures delivery. Without a mediator, the producer would need to know every consumer and push to each directly, creating tight coupling.

Delivery Guarantees

Not all streaming platforms deliver messages the same way. The guarantee chosen affects reliability, performance, and cost:

At-Most-Once
Fire-and-forget. Messages may be lost if the broker or consumer fails. Packets are not guaranteed. Lowest overhead. Acceptable for telemetry where missing one in a thousand readings is tolerable.
At-Least-Once
Messages are retried on failure — guaranteed delivery, but duplicates may appear. Consumers must be idempotent. Most common default in Kafka, RabbitMQ, and SQS.
Exactly-Once
Each message is processed exactly one time. Most complex and costly. Required for financial transactions and inventory changes. Supported by Kafka Transactions and Apache Flink.
💡 Once Broadcast, It Is Difficult to Rebroadcast
In a pure broadcast model, a consumer that was offline during a message misses it permanently — like missing a live TV show. Log-based streaming platforms (Kafka, Pulsar) solve this by retaining messages for a configurable period — consumers can replay from any offset. This turns the stream into a replayable log, enabling backfill, reprocessing, and multiple independent consumers at different offsets.

Streaming Use Cases by Data Type
🔌 Sensor / IoT Data
  • High-frequency, small payloads (temperature, pressure, vibration readings)
  • Time-windowing required: aggregate readings over 1-minute or 5-minute windows

  • Edge processing (on-device filtering) before streaming to reduce bandwidth

📊 Stock Market Data

  • Strict ordering: event sequence must be preserved for trade-time reconstruction
  • Complex event processing (CEP): detect patterns across multiple instruments (e.g., arbitrage signals)
  • Exactly-once critical: a duplicate tick price can trigger incorrect trades
  • Often uses specialized protocols (FAST, FIX) rather than general-purpose Kafka
15 Apache Flink
Definition
Apache Flink
An open-source distributed stream processing framework designed for stateful computations over unbounded (streaming) and bounded (batch) data. Flink provides exactly-once processing guarantees, sub-second latency, and fault-tolerant stateful operations at massive scale.

Flink distinguishes itself from most stream processors by being a true stream-first engine. Batch processing in Flink is modeled as a special case of streaming over a finite dataset — not the reverse. This means the same code handles both real-time and historical data.

Core Flink Concepts
1
DataStream API
The primary API for processing unbounded streams. Supports transformations (map, filter, flatMap), aggregations, joins across streams, and custom operators.
2
State Management
Flink maintains stateful operators — a running count, a session window, a running average. State is stored in Flink state backends (RocksDB for large state, heap for small) and is automatically checkpointed.
3
Time Concepts
Event time: when the event actually occurred (from the record timestamp) — used for correct out-of-order handling. Processing time: when Flink processes the record — simpler but inaccurate for late data.
4
Windowing
Groups events for aggregation: Tumbling windows (fixed, non-overlapping, e.g., 1-minute buckets), Sliding windows (overlapping, e.g., last 5 minutes updated every 1 minute), Session windows (grouped by activity gaps).
5
Exactly-Once via Checkpointing
Flink periodically snapshots the full operator state to durable storage (S3, HDFS). On failure, it restores from the last checkpoint and replays input from the corresponding offset — guaranteeing exactly-once output without duplicates.

Flink Use Cases
Real-time fraud detection, CDC processing, IoT analytics
  • Fraud detection: a Flink job maintains a stateful model of each user's recent transaction history; when a new transaction arrives, it is evaluated against the pattern in real time
  • CDC processing: Debezium publishes database changes to Kafka; Flink consumes and applies transformations before writing to the data lake — with exactly-once guarantees
  • IoT analytics: 10,000 sensors emit temperature readings; Flink computes per-device 5-minute averages and emits alerts when thresholds are exceeded
16 Event-Driven Architecture
Definition
Event-Driven Architecture (EDA)
An architectural pattern in which components communicate by producing and consuming events — immutable, timestamped records of something that happened. Producers emit events without knowing who consumes them; consumers react without knowing who produced them. The architecture is inherently asynchronous and decoupled.

An event is not a command. A command says "do this." An event says "this happened." This distinction matters: a command fails if the recipient is unavailable; an event is recorded and the consumer reacts when ready. EDA enables resilience and decoupling that direct-call architectures cannot achieve.

The Two Topologies

EDA is implemented through two distinct routing topologies, each suited to different levels of workflow complexity:

🎭 Mediator Topology
Centralized event orchestration
  • A central event mediator receives all incoming events and routes them to the correct event processors in the correct sequence
  • The mediator knows the workflow — it manages conditional routing, parallel execution, and error handling
  • Event processors send results back to the mediator, which decides the next step
  • When to use: complex workflows with conditional branching, parallel steps, or compensation (rollback) logic
  • Tools: Apache Camel, MuleSoft, WSO2 ESB, AWS Step Functions
  • Pros: visible, auditable workflow; centralized error recovery
  • Cons: mediator is a bottleneck and single point of failure
📰 Broker Topology
Decentralized event routing
  • Events are published to a message broker; there is no central coordinator — the broker just routes by topic
  • Event processors subscribe to topics they care about and react independently, often emitting new events that trigger further processing
  • The overall workflow is implicit — it emerges from the chain of reactions
  • When to use: high-throughput, simple event chains, maximum decoupling, adding consumers without changing producers
  • Tools: Apache Kafka, RabbitMQ, AWS EventBridge, Google Pub/Sub
  • Pros: highly scalable, decoupled, no single point of failure
  • Cons: difficult to trace the full workflow; no centralized error handling
Mediator vs Broker — Decision Guide
Dimension Mediator Topology Broker Topology
Workflow visibilityHigh — mediator has full stateLow — distributed across processors
CouplingProcessors coupled to mediatorProducers and consumers fully decoupled
Error handlingCentralized — mediator manages retries and compensationPer-processor — each handles its own failures
ScalabilityLimited by mediator capacityScales independently per topic / consumer group
Complexity of workflowBetter for complex, conditional flowsBetter for simple, linear event chains
Adding new consumersMust update mediator routing rulesNew consumer subscribes to topic — no change to producers
💡 Choose Topology by Workflow Complexity
If you can draw your event workflow as a simple linear chain — A triggers B, B triggers C — use the broker topology. If your workflow has conditions ("if payment fails, route to refund processor; if it succeeds, route to fulfillment and notification in parallel"), use the mediator topology. Many production systems use both: a broker for high-throughput event ingestion and a mediator for complex business process workflows triggered by those events.
17 Integration Governance Model

Integration without governance creates integration debt: undocumented connections, inconsistent schemas, unknown data flows, and brittle pipelines that nobody dares change. An integration governance model applies the same ownership, standards, and lifecycle management to integration points that data governance applies to data assets.

Ownership: Who Owns the Interface?
Producer-Owned Contracts
The producing team defines and publishes the interface. Consumers adapt to what the producer offers. Simpler for the producer, but consumers may get fields they do not need and miss fields they do. Risk: producer changes break consumers silently.
Consumer-Driven Contracts (CDC Testing)
Consumers specify what they need from the producer; the producer's test suite verifies it satisfies all consumer contracts. Tools: Pact, Spring Cloud Contract. Risk: coordination overhead. Benefit: no breaking changes reach consumers.
Security Standards for Integration
  • OAuth 2.0 / OIDC at the API Gateway: all external API consumers must present a valid access token; the gateway validates before forwarding to the backend service
  • mTLS within the service mesh: service-to-service calls inside the cluster are encrypted and mutually authenticated — both client and server prove identity
  • Schema registry enforcement for streams: Kafka producers must register their schema; consumers validate incoming messages against the registered schema — preventing malformed data from propagating
  • IP allowlisting for partner integrations: B2B integrations may combine OAuth with network-level IP restrictions for defense-in-depth

⚠ Integration Anti-Patterns to Avoid
  • Spaghetti integrations: point-to-point connections between every pair of systems — grows as O(N²), impossible to govern
  • Undocumented APIs: if it is not in the API catalog with an owner, it does not officially exist — and cannot be governed or monitored
  • Shared mutable databases: two services writing to the same database table — coupling that defeats service independence
  • No versioning strategy: breaking API changes without a deprecation period destroys consumer trust and causes production outages
  • Missing schema evolution rules: a Kafka producer adding a required field without a migration plan breaks all downstream consumers
💡 Treat Every Integration as a Governed Asset
An integration point — whether an API endpoint, a Kafka topic, or a CDC pipeline — is a data delivery contract. It has an owner, a schema, a versioning policy, a security posture, and an SLA. Registering every integration in a catalog and assigning an owner is the difference between a governed integration landscape and an undocumented web of hidden dependencies.
