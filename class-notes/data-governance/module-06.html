01 Architecture Fundamentals
Definition
Architecture
The logical and physical interrelationships between the components of a computing system. Architecture defines what exists, how components connect, and where they live — from the highest business overview down to individual server configurations.

Architecture operates at three levels simultaneously. Each level answers a different question and serves a different audience.

📊
High-Level Overview
How business capabilities map to systems. The view a CTO or enterprise architect uses to communicate strategy. Boxes represent systems; arrows represent data or control flows.
🌐
Network Level
Topology, switches, load balancers, firewalls, VPNs, DNS, and bandwidth constraints. Governs how data physically moves between systems and users.
⚙
Systems Level
Applications, databases, APIs, middleware, and message queues. The layer where engineers implement business logic and data storage.
Logical vs Physical Architecture
📄 Logical Architecture
Describes what components exist and how they relate conceptually — independent of technology or infrastructure choices. A logical diagram shows services, their responsibilities, and communication patterns without specifying which cloud provider or database product is used.
  • Technology-agnostic
  • Focused on responsibilities and relationships
  • Used for design discussions and governance decisions
🖥 Physical Architecture
Describes where components actually live — specific servers, cloud regions, data centers, containers, pods, or edge nodes. Physical architecture drives infrastructure cost, latency, and regulatory compliance (data residency).
  • Technology-specific (AWS us-east-1, Azure West Europe)
  • Includes hardware specs, replication zones, network paths
  • Used for capacity planning and disaster recovery
Key Insight
Logical and physical architectures must stay aligned. A logically elegant design can fail in production if the physical constraints — network latency, bandwidth limits, cloud egress costs — were not considered during design.
02 Data Architecture
Definition
Data Architecture
The design of data applications and the logical and physical interrelationships between their components. Data architecture governs how data flows through an organization — how it is collected, stored, transformed, governed, and made available to consumers.

Data architecture bridges business requirements and technical implementation. It answers: Where does data come from? Where does it live? Who can access it? How does it move? Every governance policy, every SLA, and every data contract is grounded in architectural decisions.

Scaled Architecture: Centralized + Distributed

Pure centralized architectures — a single database serving everything — are easy to govern but become bottlenecks at scale and create single points of failure. Pure distributed architectures — each service owning its own data — are resilient but make cross-domain queries difficult and governance inconsistent. Scaled architecture combines both approaches:

Source Systems
Distributed ownership
→
Central Governance Layer
Policies, metadata, contracts
→
Distributed Execution
Domain-local compute
→
Consumers
Analytics, ML, APIs
Design Rule
Centralize governance; distribute execution. Policies, contracts, and metadata live in one place. Compute and storage are distributed to where data originates or is consumed. This avoids the bottleneck of a single monolithic store while maintaining organizational control.
03 Data Design Principles

Good data design is not just about storage efficiency — it is about building a system that is trustworthy, usable, and adaptable over time. A poorly designed data layer creates technical debt that compounds: bad schemas propagate into downstream reports, incorrect defaults silently corrupt analytics, and rigid structures block future business pivots.

✅
Quality
Accurate, complete, consistent, and timely. Every dataset should meet defined quality thresholds before it reaches consumers.
⚡
Efficient
Minimize redundancy. Optimize storage and query patterns for the expected workload — a design optimized for writes differs from one optimized for reads.
🔒
Reliable
Fault-tolerant, recoverable, and predictable. Consumers must be able to depend on the data being there and being correct when they need it.
🔎
User-Intuitive
Consumers should understand and use the data without decoding internal technical identifiers. Design with the consumer in mind.
Consumer-First Denormalization

A core data design principle is to provide full data for the consuming application. In a normalized golden source, related data is split across tables linked by foreign keys. Consumers are expected to perform joins to assemble a complete record — but this is expensive, error-prone, and often unnecessary. Instead, denormalize your data based on your consumer: pre-join and embed the data that each consumer needs.

Real-World Example
ServiceNow API — ID Resolution Problem
When extracting experiment data from the ServiceNow API, the JSON response contains experiment_id, assignee_id, and group_id — but not the human-readable names or details behind those IDs. To get meaningful data, you must make additional API calls for each ID to resolve the full record. A well-designed data layer would pre-resolve all foreign key IDs and return an enriched, denormalized record in a single call — eliminating the N+1 lookup problem.
  • Bad: consumer receives assignee_id: "abc123" and must call /users/abc123
  • Good: consumer receives assignee: { id: "abc123", name: "Jane Lee", team: "Data Platform" }
Principle
Agility and scalability are also design goals. A data model that cannot accommodate a new field without breaking downstream consumers, or that cannot handle 10x data volume without a redesign, is not truly well-designed. Plan for change from the start: use versioned schemas, support additive changes, and avoid hard-coding assumptions about data volume.
04 OLTP & Transactional Systems
Definition
OLTP — Online Transaction Processing
Systems designed for high-frequency, low-latency read and write operations that represent business events — placing an order, updating an account balance, booking a seat. OLTP is the operational heartbeat of a business: every customer interaction, every workflow step, every status change flows through it.
OLTP Characteristics
  • Row-based storage — optimized for fetching entire rows quickly
  • ACID compliance — Atomicity, Consistency, Isolation, Durability
  • Normalized schema (3NF or higher) — minimizes redundancy, maximizes write integrity
  • High concurrency — many users performing small operations simultaneously
  • Short transactions — millisecond-level operations, not long-running queries
  • Delete operations are rare — usually soft-deleted (status flag) or retained for audit
Why OLTP Is a Poor Analytics Platform
  • Full table scans for analytics compete with live transactions, causing lock contention
  • Normalized schema requires complex multi-table JOINs — slow for large aggregations
  • Row storage is inefficient for column-level aggregations (SUM, AVG, COUNT)
  • Schema is optimized for writes, not reads — wrong access pattern for analytics
  • Analytics workloads spike unpredictably and can overwhelm transactional capacity

This is why data is extracted from OLTP systems into analytical stores (data warehouses, lakes, or RDS).

05 Data Stores, Warehouses & Data Marts
Definition
Data Store
A repository for persistently storing and managing collections of data in a structured or semi-structured form. The term is broad — it encompasses relational databases, document stores, object stores, key-value caches, and more.
Data Warehouse Model

A data warehouse is a centralized, integrated store designed for analytical queries. Data from operational systems is extracted, transformed, and loaded (ETL) into the warehouse, where it is organized into subject-oriented schemas optimized for querying large volumes of historical data.

Centralized Data Warehouse
CRM System → ETL Pipeline → Data Warehouse → BI / Reports
ERP System → ETL Pipeline → → Analytics Tools
OLTP DB → ETL Pipeline
Data Mart

A data mart is a subject-specific subset of a data warehouse, scoped to a single domain (e.g., Sales, Finance, HR). Data marts give domain teams faster, simpler queries without navigating the full warehouse schema. However, ungoverned data marts risk becoming silos with inconsistent definitions of shared metrics.

📊 Data Warehouse (Operational Model)
  • Normalized schema — reduces redundancy, supports frequent writes
  • Optimized for transaction speed (row-based storage)
  • Reflects current state of business operations
  • Source of truth for transactional systems
📊 Data Warehouse (Analytical Model)
  • Star or snowflake schema — denormalized for query performance
  • Optimized for read-heavy analytical workloads
  • Contains historical data (time-variant, non-volatile)
  • Subject-oriented: organized around business topics, not application functions
06 Operational Read-Only Data Store (RDS / ORDS)
Definition
RDS — Read-Only Data Store (also: ORDS)
A read-optimized copy of operational data aggregated from multiple golden sources, designed to serve query workloads without impacting the transactional source systems. The RDS does not replace the golden source — data flows to the RDS from upstream providers. It enables cross-domain querying across bounded contexts that would otherwise be inaccessible to one another.

The core challenge the RDS solves: as organizations grow, data becomes fragmented across many systems — CRM, ERP, billing, logistics, customer support. No single system has a complete view. Joining across these systems requires touching live transactional databases, which creates load, coupling, and security risk. The RDS provides a safe, read-only surface that aggregates the golden records from each domain.

Data Flow: Golden Sources → RDS → Consumers
CRM (Golden Source) → Read-Only Data Store (RDS) → Analytics
Billing (Golden Source) → → ML Platform
Logistics (Golden Source) →
Industry Example
Vanguard ORDS on Amazon Redshift
Vanguard (one of the world's largest investment firms) built an Operational Read-Only Data Store on Amazon Redshift to bridge data silos across bounded contexts. Each business domain (funds, accounts, clients, transactions) owns its golden source. The ORDS aggregates records from each domain, enabling analysts to run cross-domain queries — for example, linking a client account to their fund holdings and recent transactions — without touching any live transactional system. See: AWS Big Data Blog — "Bridging Data Silos: Cross-Bounded Context Querying with Vanguard ORDS."
07 Why RDS Matters & Its Trade-offs
Why RDS Matters
1
Protects source systems
Heavy read queries from analysts and ML pipelines are redirected away from live OLTP databases, eliminating lock contention and protecting transactional performance.
2
Enables cross-domain querying
A consumer can query data from multiple bounded contexts (CRM + Billing + Logistics) in a single query, without coupling those systems to each other or building fragile point-to-point integrations.
3
Single governance enforcement point
Access control, data masking, row-level security, and audit logging are enforced at the RDS layer for all consumers, rather than having each source system implement its own policies.
4
Supports diverse consumer types simultaneously
Real-time dashboards, batch analytics, ML feature extraction, and API consumers can all query the RDS using the access pattern most appropriate for their workload.
How RDS Handles Large Read Requests
Scaling Strategies
  • Read replicas — additional copies of the database serving read traffic
  • Sharding / partitioning — split data by date, region, or ID range across nodes
  • Columnar storage — scans only relevant columns for aggregations
  • Materialized views — pre-computed aggregates refreshed on a schedule
  • Query caching — return stored results for repeated identical queries
Trade-offs and Cons
  • Eventual consistency — data in the RDS lags behind the golden source; not suitable for real-time decisions
  • Synchronization complexity — each source has different schemas, schedules, and failure modes
  • Infrastructure cost — maintaining a separate cluster adds compute and storage expense
  • Schema drift — source schema changes break the ingestion pipeline
  • Operational overhead — replication lag monitoring, failure recovery, and freshness SLAs
Critical Trade-off
The RDS is never the source of truth. If a consumer needs real-time accuracy (e.g., checking current account balance before approving a transaction), it must query the golden source directly. The RDS is for analytical and operational read workloads where slight data lag is acceptable.
08 CQRS — Command & Query Responsibility Segregation
Pattern
CQRS — Command and Query Responsibility Segregation
An architectural pattern, rooted in Domain-Driven Design, that separates the model used to write data (commands) from the model used to read data (queries) into two distinct databases. Each side is optimized independently for its workload, and data is replicated from the write side to the read side via events or change streams.

✍ Commands
Operations that change application state. Commands pass through business rule validation before being persisted to the write database. Examples: PlaceOrder, UpdateCustomerAddress, CancelSubscription. A command either succeeds entirely or fails entirely (ACID).
📊 Queries
Operations that retrieve data without side effects. Queries read from the optimized read database, which may be a denormalized view, a columnar store, or an in-memory cache. Because the read model is separate, it can be shaped exactly for each consumer without impacting the write model.
In-Memory Databases for Queries
For frequently-read, rarely-changed data, the query side can be served entirely from an in-memory database like Redis or Memcached. Sub-millisecond response times are achievable. The write side persists to disk (Postgres, MySQL); the read side materializes into memory. Replication from write to read happens via event streams. This is the CQRS pattern at its most extreme.
09 CQRS at Scale

At enterprise scale, the CQRS read layer must handle a wide variety of consumers, query sizes, latency requirements, and data transformation needs — simultaneously, without degradation. A single read database is no longer sufficient.

Multi-Technology Data Layer
⚡
Large / Batch Queries
Full-scan aggregations, historical trends, bulk exports. Served by columnar stores (Redshift, BigQuery, Snowflake) or MPP (Massively Parallel Processing) engines.
⚡
Single-Point Queries
Lookup by ID, user profile fetch, real-time status check. Served by key-value stores (Redis, DynamoDB) with sub-millisecond latency.
🔁
Streaming Queries
Continuous event processing, real-time dashboards, alerting. Served by stream processors (Kafka Streams, Flink, Spark Streaming).
Consumer-Specific Optimization
🤖 ML Consumers
Machine learning models often need raw, untransformed features — the original values before any business logic is applied. Transformation can introduce bias or information leakage. The data layer should be able to serve unmodified records directly from the ingestion point, bypassing the business-rule transformation layer when the consumer explicitly requests it.
📊 Analytics Consumers
Business analysts need data that has been denormalized, enriched, and business-rule-applied — customer segments calculated, revenue recognized per accounting policy, dates localized. The data layer transforms and shapes the record based on the consumer domain before delivery.
Syntactic Translation Engine (Semantic Layer)
Concept
Syntactic Translation Engine
An abstraction layer that translates business terminology and logic into technical queries, bridging the gap between how business users express needs and the underlying technical storage format. It handles dialect differences (SQL vs NoSQL vs REST API) and denormalization for each consumer type.
Example
Business Logic → Technical Query
Business user asks: "Show active customers who purchased in Q3."

Translation engine resolves:
WHERE customer_status = 'A' AND purchase_date BETWEEN '2024-07-01' AND '2024-09-30'

The golden source may be heavily normalized — customer status lives in one table, purchases in another. The translation engine handles the JOIN, applies the business definition of "active," and returns results shaped for the consumer without the consumer needing to know the physical schema.
Design Requirement
The data layer must support all delivery modes simultaneously: real-time, streaming, event-driven, and batch. A consumer should not be forced into batch because the architecture only supports scheduled extracts. Conversely, the system should not force streaming overhead onto consumers who only need daily snapshots. Design for mode flexibility from the start.
10 RDS Components — Metadata, Validation & Integrity
Enterprise Metadata Functions
Governance Metadata
  • Ownership — who is accountable for each dataset
  • Data classification — sensitivity level (public / internal / confidential / restricted)
  • Retention policy — how long data is kept before archival or deletion
  • Compliance tags — GDPR, HIPAA, SOX applicability
  • Steward assignment — the domain expert responsible for quality
Technical Metadata
  • Schema — column names, data types, nullability, constraints
  • Lineage — source system → transformation → target (full provenance)
  • Refresh schedule — when data was last updated and how frequently
  • Record count & size — volume metrics for capacity planning
  • Partition info — how data is physically organized (date, region, ID range)
Validation Rules & Service Contracts

Validation rules define the expected schema, format, range, and cardinality for each field. They are enforced at ingestion time — records that fail validation are rejected or quarantined for remediation rather than silently corrupting the RDS. Validation rules are the technical implementation of a service contract — the formal agreement between a data provider and the RDS about what data will be delivered, in what format, and at what frequency.

Design Question: What if data trends change and validation rules no longer catch anomalies?
This is handled through versioned service contracts. When the business definition of a field changes (e.g., a field that was always positive can now be negative after a financial restatement), the contract is updated to V2. The provider communicates the change, a new validation rule set is authored, and both V1 and V2 consumers can be supported in parallel during a migration window.
  • Rules should be reviewed quarterly even when no errors are found — absence of errors is not proof that the rule is still meaningful
  • Never delete old rules — archive them with a version number and deactivation date for audit purposes
  • If no errors are found over a long period, keep the rule: it serves as documentation and insurance against regressions
  • Anomaly detection (statistical) complements validation (static) — it catches trend shifts that static rules miss

Data enters through providers, is validated and transformed in the incoming tier, made accessible through the access tier, and consumed by downstream teams. 12 Data Ingestion
Definition
Data Ingestion
The process of importing, loading, and bringing data into a target store from one or more providers. Ingestion design determines freshness, throughput, reliability, and the ability to recover from failures. The right ingestion pattern depends on the source system, data volume, latency requirements, and downstream consumer needs.
Ingestion Modes
  • Batch — large volumes at scheduled intervals (hourly, daily). Efficient but introduces lag equal to the batch interval.
  • Streaming — continuous real-time flow via Kafka, Kinesis, or Pub/Sub. Low latency but higher infrastructure complexity.
  • Event-driven — triggered by a specific event (file landed in S3, webhook received). Efficient for sparse, irregular data.
  • CDC (Change Data Capture) — reads the database write-ahead log to capture only changed rows, minimizing load on the source and enabling near-real-time sync.
Ingestion Design Considerations
  • Schema evolution — how does the pipeline handle a new column or renamed field from the source?
  • Late-arriving data — records that arrive after their expected processing window (e.g., a transaction timestamped yesterday arrives today)
  • Idempotency — re-processing the same batch must not create duplicate records
  • Backfill — loading historical data when onboarding a new dataset or recovering from failure
  • Error handling — quarantine invalid records; alert stewards; never silently drop data
13 Integrating COTS, External APIs & SaaS
Definition
COTS — Commercial Off-The-Shelf
Pre-built software products purchased and deployed rather than developed in-house. Examples: Salesforce (CRM), Workday (HR), SAP (ERP), ServiceNow (ITSM). COTS systems are data providers whose APIs and export formats you do not control.
Vendor Lock-in Risk

Tightly coupling your data architecture to a vendor-specific format, API version, or proprietary schema creates vendor lock-in: the cost of switching vendors becomes so high that organizations are trapped. Minimize lock-in by:

1
Use abstraction / adapter layers
Isolate vendor-specific API calls behind an internal interface. If the vendor changes their API, only the adapter changes — the rest of the pipeline is unaffected.
2
Standardize on open formats
Convert vendor-proprietary formats (XML exports, custom CSV) to open standards (Parquet, JSON, Avro) at the ingestion boundary. Downstream consumers work with the standard format, not the vendor format.
3
Define data contracts at the boundary
Specify what fields you require, their types, and expected ranges — independently of how the vendor exposes them. Validate against your contract on every extract.

14 Historical Data Service
Definition
Historical Data Service
A service that provides access to historical snapshots of data, enabling consumers to query the state of a record at any point in the past — not just its current value. Essential for auditing, trend analysis, regulatory compliance, and debugging production data issues.

Temporal queries ask "what was the state of X at time T?" This requires the data store to preserve prior versions of records rather than overwriting them. The approach chosen determines storage cost, query complexity, and the granularity of historical access.

Slowly Changing Dimensions (SCD)
TypeHow History Is HandledTrade-off
Type 1 — OverwriteOld value is replaced. No history is preserved.Simple but loses all history. Only current state visible.
Type 2 — New RowA new row is inserted with a start/end date range. The old row is closed. Full history is preserved.Most common in data warehouses. Enables point-in-time queries. Increases table size.
Type 3 — Previous ColumnA "previous value" column is added next to the current value column.Only one prior state preserved. Simple queries but limited history depth.
Immutability Principle
Historical records should be append-only. Once a record is written for a past event, it should never be modified or deleted (except under an explicit retention policy). This guarantees auditability — the historical store tells exactly what the system knew at each point in time. Corrections are recorded as new entries with an effective date, not as edits to existing rows.

Retention policies define how long historical data is kept before archival or deletion — governed by regulation (GDPR requires right-to-erasure for personal data; HIPAA requires 6-year retention for medical records; financial regulations often require 7 years). Data that cannot be deleted under retention policy must be appropriately secured even after it is no longer operationally needed.

15 Design Variations — Row, Column & Document Stores

There is no universally optimal storage model. The right choice depends on the access pattern, data structure, and workload type. Enterprises typically use multiple storage models simultaneously — one for transactions, another for analytics, another for flexible semi-structured data.

📈
Row-Based
Data stored row by row. Optimal for OLTP: fetching full records by ID, frequent inserts and updates. Inefficient for column aggregations across millions of rows.
📉
Column-Based
Data stored column by column. Optimal for OLAP: aggregating a single metric across millions of rows. Scans only relevant columns. Excellent compression.
📄
Document-Based
Data stored as JSON/BSON documents with flexible schema. Optimal for nested, variable, semi-structured data. No rigid schema enforcement.

16 Data Replication
Definition
Data Replication
The process of creating and maintaining synchronized copies of data across multiple locations, systems, or storage tiers. Replication enables high availability, geographic distribution, read scaling, and disaster recovery. In the RDS context, it is the mechanism by which golden source data reaches the read layer.

Provider Responsibilities

The data provider (the golden source team) bears primary accountability for ensuring the replicated RDS stays synchronized. This includes:

✅ Provider Must
  • Define and honor a replication SLA (e.g., data available in RDS within 15 minutes of commit)
  • Trigger a re-sync when source data is corrected or retroactively updated
  • Notify the RDS team of schema changes before they are deployed
  • Maintain a delivery log so failures can be identified and replayed
📄 Metadata Must Also Be Replicated
When data is replicated, the metadata repository must also be updated:
  • Freshness timestamp — when did data last arrive?
  • Record count — did the expected volume arrive?
  • Lineage — which version of the source schema produced this replica?
  • Replication lag — how far behind is the RDS from the golden source?
17 Access, File Manipulation & Intelligent Delivery
Access Layer — Security for Consumers

The access layer enforces what each consumer is permitted to see. Access is not binary (all-or-nothing) — it is fine-grained and policy-driven:

Access Control Dimensions
  • Column-level — consumer sees only permitted columns (PII columns masked or hidden)
  • Row-level — consumer sees only rows matching their org code, region, or role
  • Time-period — consumer can only query data within an authorized date range (e.g., last 90 days)
  • Volume limits — rate limiting and query cost caps prevent runaway queries
Access Types in the Integration Layer
  • Direct SQL query — consumer runs queries via JDBC/ODBC against the RDS
  • REST API — consumer calls a standardized endpoint; server enforces access policies
  • File export — scheduled extract delivered to the consumer in CSV, Parquet, or JSON
  • Data subscription — consumer subscribes to a change feed (CDC) for near-real-time updates
File Manipulation Service

Before data reaches a consumer as a file, a file manipulation service may apply format conversion, masking, encryption, and splitting/merging. This ensures that the output file matches the consumer contract regardless of the internal storage format.

File Manipulation Pipeline
Raw Extract (Parquet) → Data Masking → Format Conversion → Consumer Delivery (CSV)

Masking replaces sensitive values with tokens, hashes, or synthetic values. Format conversion changes encoding without altering content. Each step is logged in the metadata repository for lineage.

Intelligent Consumption Service

Rather than every consumer querying the RDS directly, an intelligent consumption service sits between the access tier and consumers. It routes requests to the most appropriate underlying store, applies consumer-specific transformations, caches frequent results, and can surface AI-powered recommendations.

What It Does
  • Routes a small point-lookup to the key-value cache instead of the columnar store
  • Routes a large aggregation to the MPP cluster
  • Caches the result of a commonly-repeated query and serves subsequent requests from cache
  • Applies consumer-specific transformation rules (denormalization, currency conversion, timezone)
Populating RDS on Demand
Instead of pre-loading all data, low-frequency datasets can be loaded only when first requested:
  • Reduces storage cost for rarely-accessed data
  • Risk: first request has high latency ("cold start" problem)
  • Hybrid approach: frequently-accessed data is always pre-loaded; rare data is loaded on demand and cached after first access
Data Delivery Contracts

A data delivery contract is a formal, versioned agreement between a data provider and one or more consumers specifying exactly what data will be delivered, how, and when. Contracts enable independent evolution of provider and consumer systems.

Contract ElementDescription
SchemaField names, data types, nullability, key constraints — versioned (V1, V2)
Delivery FrequencyReal-time, near-real-time (5 min), hourly, daily — agreed SLA
FormatJSON, CSV, Parquet, Avro — including encoding (UTF-8) and compression
Quality SLAMinimum completeness %, maximum allowed error rate, freshness guarantee
Access ControlsWhich fields are accessible to which consumer roles
Change ManagementHow breaking changes are communicated; deprecation notice period; migration support window
RetentionHow long the RDS retains data on behalf of the consumer
