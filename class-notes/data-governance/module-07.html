Governance & Security in Scaled Architecture

How data governance and data security evolve from centralized to scaled architectures — ownership, authorization, classification, authentication, and consumption controls
Scaled Architecture Data Security ABAC / RBAC Authentication
01 From Centralized to Scaled Architecture

As organizations grow, their data architecture passes through three distinct stages. Each stage introduces new governance and security challenges that the previous model could not anticipate. Understanding where your organization sits on this spectrum determines what governance processes are realistic to implement today.

Centralized
One database, one team
→
Distributed
Each service owns data
→
Scaled
Central governance + distributed execution
🏛
Centralized
Single database, single team, single governance policy. Easy to control but creates a bottleneck. One breach or outage affects everything. Governance is straightforward because there is only one place to enforce rules.
🌐
Distributed
Each service or team owns its own database. Resilient and independently scalable, but governance becomes inconsistent — every team implements their own access controls, schemas, and quality rules with no coordination.
⚙
Scaled
Governance, policies, and metadata are centralized. Data storage and processing are distributed. Each domain operates independently within guardrails defined by the central governance body. This is the target state for enterprise data organizations.

Key Shift
In a scaled architecture, governance cannot rely on physical proximity to data. You cannot govern what you cannot see, and you cannot see everything in a distributed world. The answer is metadata as the control plane: every dataset is registered, tagged, and tracked centrally, even if the data itself lives in distributed stores.
02 From App-Based to Data-Based Ownership
🖥 App-Based Ownership (Legacy)
The application team owns the data as a byproduct of their system. The CRM team owns customer records because they built the CRM. The ERP team owns financial records because they maintain the ERP.
  • Data is locked inside the application schema
  • Application changes break downstream consumers without notice
  • Governance is an afterthought — data structure serves the app, not the business
  • No portability — moving to a different CRM means rebuilding all data integrations
  • Multiple apps may hold overlapping copies of the same entity with no reconciliation
📊 Data-Based Ownership (Target State)
Domain teams explicitly own datasets, independent of which application stores them. The Customer domain owns all customer data — whether it lives in Salesforce, a data lake, or a microservice database.
  • Data is treated as a first-class product with its own lifecycle, quality SLA, and contract
  • Application changes do not break data consumers — the data contract is the interface
  • Data can be moved between systems without breaking downstream consumers
  • Aligns with the Data Mesh philosophy: domain teams publish data as governed products
  • Governance accountability is clear: the domain data team is answerable for accuracy and security
Why This Shift Matters for Security
Under app-based ownership, security policies are embedded in application logic — access controls live inside each app, making them inconsistent and hard to audit. Under data-based ownership, security policies travel with the data as metadata tags and contracts. A dataset classified as Restricted carries that classification into every system it touches, regardless of which application stores it.
03 Governance Processes in Scaled Architecture

Moving to scaled architecture does not automatically improve governance — it must be designed in. Several processes must be put in place and maintained collaboratively across domain teams, the governance body, and technology teams.

1
Data Cataloging
Every dataset, field, and transformation is inventoried in a central catalog. Without a catalog, data consumers do not know what data exists, where it is, or who to contact. The catalog is the foundation of discoverability and governance.
2
Policy Definition
The governance body defines rules: who can access what, under what conditions, for how long, and for what purpose. Policies are explicit, versioned, and tied to data classification levels.
3
Policy Enforcement
Technical controls (RBAC, ABAC, column masking, row-level security) implement the governance policies automatically. Manual enforcement at scale is impractical — controls must be embedded in the data platform.
4
Data Quality Monitoring
Continuous automated checks validate completeness, accuracy, timeliness, and consistency. Quality failures trigger alerts to the data steward and are tracked over time to identify systemic issues.
5
Access Provisioning
A formal request-and-approval workflow controls who gains access to each dataset. Requests capture purpose, duration, and data sensitivity. Approvals are logged for audit. Access is automatically revoked at expiry.
6
Cross-Team Collaboration
Federated data stewards represent each domain in the central governance forum. Regular cadences (monthly governance reviews, quarterly policy audits) ensure alignment across teams without creating a central bottleneck.
7
Incident Response
When data is misused, breached, or incorrectly shared, a defined escalation process must exist. Audit logs enable forensic investigation. Consequences must be clear and consistently enforced.
04 Authorization Models — The Shift to ABAC

Authorization defines what an authenticated user is permitted to do. As data architectures have scaled, authorization models have evolved from simple, coarse-grained approaches toward fine-grained, context-aware controls. The industry has progressively shifted from DAC through RBAC and is now moving toward ABAC.

ModelFull NameHow It WorksBest ForLimitation
DAC Discretionary Access Control The data owner decides who can access their resources and grants permissions at will Small teams, simple sharing (file systems, spreadsheets) Inconsistent — each owner sets different rules; no organization-wide policy enforcement
MAC Mandatory Access Control System assigns classification labels (Top Secret, Secret, Unclassified); access is enforced by the system, not the owner Government, defense, high-security environments Very rigid; difficult to adapt for complex business rules; poor user experience
RBAC Role-Based Access Control Permissions are assigned to roles (Analyst, Manager, Admin); users inherit permissions from their role Enterprise applications, ERP, standard business systems Coarse-grained; role explosion as business rules get complex; cannot handle contextual conditions (time, location, device)
ABAC Attribute-Based Access Control Access decisions evaluate attributes of the user, the resource, the action, and the environment simultaneously against a policy Scaled enterprise data platforms, cloud-native systems, multi-domain governance More complex to design and audit; requires a mature policy engine; attribute data must be accurate
ABAC in Practice — Fine-Grained Access Scenarios

ABAC policies express access rules as conditions combining multiple attributes. This is what makes it powerful for scaled governance:

1
Personal device access — restricted to masked data only
IF device.type = "personal" THEN grant access to masked columns only. A managed corporate laptop may see full PII; a personal device only sees tokenized values.
2
Non-office hours — read-only access
IF environment.time NOT IN office_hours THEN allow READ only, deny WRITE and DELETE. Prevents bulk deletions or data exports during off-hours when oversight is minimal.
3
Outside office region — MFA required or access denied
IF environment.ip_region != user.home_region THEN require MFA or deny access. Blocks access attempts from unexpected geographic locations unless re-authenticated.
4
Purpose-limited access
IF access.purpose = "audit" THEN allow READ on finance data for 30 days. An external auditor receives time-boxed, purpose-scoped access that automatically expires.
05 Data Ownership, Stewardship & Custodianship

Clear accountability is the foundation of data governance. Without knowing who is responsible for each dataset — who defines policy, who maintains quality, who secures it — governance becomes aspirational rather than operational. Three roles form the core accountability structure:

👑
Data Owner
Senior leader accountable for the dataset. Defines access policy. Approves data sharing agreements. Accountable to the organization for data accuracy and appropriate use. The entire management chain beneath the owner is responsible under them.
📋
Data Steward
Domain expert who implements org policies and data owner policies. Maintains the business glossary for their domain. Approves data definitions. Ensures data quality. Reviews and approves cross-domain data sharing requests.
🛠
Data Custodian
Technical team (DBA, platform engineer) that manages the physical storage, backup, encryption, and security infrastructure. Implements the technical controls defined by the governance body. Does not define policy — executes it.
Who Answers What?
QuestionAnswered By

Where is this data stored and backed up?Data Custodian

DSAA — Data Sharing Agreement Layer
A Data Sharing Agreement (DSA) is a formal contract between a data owner and a consumer (internal team or external organization) specifying what data is shared, under what conditions, for what purpose, and for how long. The DSAA layer is the organizational and technical infrastructure that manages, enforces, and audits these agreements at scale. Without a DSAA layer, data sharing is informal — driven by personal relationships and ad-hoc email approvals — creating audit, compliance, and security exposure.
06 Data Accuracy, Lifecycle Ownership & Purpose-Based Access
Principle
Data must always be accurate
Accuracy is not an aspirational quality — it is a governance requirement. Inaccurate data propagates through every downstream system that trusts it, compounding errors at each step. Governance ensures accuracy through validation rules, quality monitoring, and clear accountability for corrections. An inaccurate golden source is more dangerous than no data at all, because it gives consumers false confidence.

If any lifecycle stage lacks an assigned owner, data lingers in systems past its retention window, is never archived, or is duplicated without any record of where copies exist. This creates compliance exposure (GDPR right-to-erasure cannot be fulfilled if no one knows where all copies live) and security risk (forgotten databases with stale access credentials).

Duration-Based and Purpose-Based Access
⌛ Duration-Based Access
Access is not permanent. It is granted for a specific time window aligned to a business need:
  • A project team needs access for 90 days — automatically revoked at day 91
  • An auditor needs access for the audit period (e.g., January 1–31)
  • A vendor needs access during a contract term — revoked on contract end
Duration-based access reduces the standing privilege problem: access that was once granted and never revoked, long after the need expired.
🎯 Purpose-Based Access
Access is scoped to a declared purpose. The consumer must state why they need the data, and access is limited to what is required for that purpose:
  • "Access for audit purposes only" — read-only, no export to external systems
  • "Access for ML model training" — anonymized records only, no PII
  • "Access for patient care" — records for named patient only
This is the data minimization principle from GDPR: collect and expose only what is necessary for the stated purpose.
07 Data Governance Body & Responsibilities
Definition
Data Governance Body
A cross-functional group of people responsible for defining, maintaining, and enforcing the policies, standards, and processes that govern how data is created, managed, shared, and retired across the organization. This is not an IT committee — it includes business leaders, legal, compliance, security, and domain data owners.
Core Questions the Governance Body Must Answer
1
Which application is responsible for creating, updating, and moving data?
Each dataset must have one authoritative source of creation. If two systems both create customer records, which one is the golden source? The governance body assigns this and communicates it through the enterprise data dictionary.
2
Do we trust this data? Is it a golden source or a derived copy?
Not all data is equally trustworthy. The governance body rates and communicates the trust level of each dataset. Derived or modified data is flagged accordingly. Consumers must know whether they are reading a golden record or a transformed copy.
3
What tools are approved for data management?
The Enterprise Architect is responsible for standardizing which tools are approved for cataloging, quality monitoring, access control, ETL, and backup. Without this, different teams purchase incompatible tools, creating integration complexity and governance gaps.
4
How is the enterprise data dictionary maintained?
The governance body owns the enterprise dictionary: the authoritative definitions of all business terms, field names, and data standards. Every team must align to these definitions. Divergence from the dictionary must be explicitly approved and versioned.
5
What are the retention and archival schedules by dataset?
Different datasets have different legal retention requirements. The governance body defines and communicates these. Without centralized retention policy, database teams may apply arbitrary schedules or none at all, creating compliance liability.
08 Standard Interfaces, Trust & Consequences
Standard Interfaces for Data Exchange

Without agreed-upon interfaces, every integration between teams becomes a custom negotiation. One team uses REST, another SFTP, another a direct database connection. The result is a web of brittle, undocumented point-to-point connections — the Big Ball of Mud at the data layer. Standard interfaces define:

🔌 What Must Be Standardized
  • Protocols: REST, gRPC, or event streams — pick one per integration pattern
  • Data formats: JSON with ISO 8601 dates, Parquet for batch, Avro for streaming
  • Authentication: OAuth 2.0 + JWT for all service-to-service calls
  • Error formats: consistent error code structure so consumers handle failures uniformly
  • Versioning: v1, v2 path prefixes; deprecation notice period defined in the contract
🔎 Clarity on Approved Tools
The governance body (working with the Enterprise Architect) publishes an approved tool list:
  • Cataloging: Apache Atlas, Collibra, Azure Purview
  • Quality monitoring: Great Expectations, Monte Carlo, Soda
  • ETL / orchestration: dbt, Apache Airflow, Informatica
  • Access control: AWS Lake Formation, Apache Ranger
Teams that want to use a non-approved tool must submit a justified request to the governance body.
Trust Levels: Golden Source vs Modified Data
Trust LevelDescriptionConsumer Guidance
⭐ Golden SourceAuthoritative, original record from the domain system of record. No transformation beyond normalization.Trust this record. Raise a defect if it is wrong.
⚠ Derived DataProduced by applying business rules or aggregations to a golden source. May introduce interpretation.Understand the transformation rules before using for critical decisions.
❌ Modified / UnverifiedCopied from a source with unknown transformation history, or manually edited without audit trail.Do not use as a golden source. Trace lineage before trusting.
Consequences for Data Misuse

Governance policies without enforcement are suggestions. The governance body must define and communicate consequences for policy violations — and enforce them consistently. Without consequences, policies erode: teams take shortcuts, share data informally, and bypass controls when they are inconvenient.

⚖ Internal Consequences
  • Immediate access revocation pending investigation
  • Formal written warning and mandatory governance training
  • Escalation to HR and legal for repeat violations
  • Inclusion in the employee performance record
  • Audit trail ensures accountability is traceable
⚖ Regulatory Consequences
  • GDPR: fines up to 4% of global annual revenue or €20M (whichever is higher)
  • HIPAA: civil penalties up to $1.9M per violation category per year; criminal charges for willful violations
  • CCPA: $100–$750 per consumer per incident for unintentional violations
  • Reputational damage and loss of customer trust are often more costly than the fine itself
09 Metadata, Business Glossary & Lineage
Definition
Business Glossary
A centrally maintained dictionary of agreed business term definitions that eliminates semantic inconsistency across the organization. Without a glossary, "active customer" means different things to Sales, Finance, and Marketing — and each builds dashboards that contradict each other.
Definition
Data Lineage
The end-to-end record of where data originated, what transformations were applied, and where it traveled. Lineage answers: "Why does this number look wrong?" by allowing engineers to trace a value from the dashboard back to the source row that produced it.

Internal vs External Consumers
👤 Internal Employees
Access data through internal tools (BI platforms, data catalogs, internal APIs). Subject to corporate policies, employment agreements, and data governance training requirements. Access is provisioned through identity management systems (LDAP, Active Directory, Entra ID). Role-based and attribute-based controls apply.
🌏 External Customers / Partners
Access data through public APIs, portals, or data exports under explicit data sharing agreements. Subject to terms of service, privacy policy, and contractual obligations. Data shared must be minimized to what is necessary. Separate authentication tier (OAuth / API keys) with stricter rate limits and audit requirements.
10 Dataset Activities, Profiling & Classification

Data governance is not only about who can access data — it also specifies what activities are permitted on a dataset and how that dataset should be classified. Activities and classifications are linked: a dataset classified as PII has a different permitted activity set than a dataset classified as General Purpose.

Process-Related Activities on a Dataset
📊
Profile
Generate a statistical summary: row count, null %, min/max/mean, value distribution, uniqueness. Profiling reveals quality issues before they reach consumers.
🏷
Classify
Apply data class labels (PII, PHI, financial, public). Attach security classification (Confidential, Restricted). Classification drives which downstream controls apply.
🔑
Mask / Anonymize
Replace sensitive values with tokens, hashes, or synthetic data. Only authorized roles can unmask. Masking must be consistent across all copies of the dataset.
♻
Archive / Delete
Move to cold storage per the retention policy. Delete only under explicit authorization. Log every deletion for audit. Deletion must cover all copies and backups.
Data Classes & Their Policy Implications

General Purpose Non-sensitive, publicly shareable within the organization Broad internal access; no special masking required Product catalog, office locations, published exchange rates
Private / Internal For internal use only; not for external sharing without approval Role-based; must not leave the organization without DSA Internal headcount reports, project plans, system architecture diagrams
Masked Data Sensitive field is present but replaced with a token or hash; real value stored separately Most consumers see the masked value; unmasking requires elevated privilege Credit card numbers (tokenized), SSN (hashed), email (pseudonymized)

11 Dataset-Specific Metrics & Quality Rules
Core Principle
Metrics and quality rules for one dataset are not automatically applicable to another. A generic quality rule ("zero is an error") can be correct for one dataset and disastrously wrong for another. Data stewards must define quality thresholds at the dataset and field level, not globally.

More Examples of Dataset-Specific Rules
NULL Rate Rules
  • customer_id: 0% NULL allowed — required field, always populated
  • middle_name: up to 40% NULL is normal — many people have no middle name
  • phone_number: up to 15% NULL acceptable — optional contact field
  • email: 0% NULL for digital customers; may be higher for walk-in records

The threshold must reflect the business reality of each field — not a one-size-fits-all percentage.

Range & Sign Rules
  • product_quantity: must be > 0 — negative quantity is a data error
  • financial_adjustment: may be negative — credits and debits are valid
  • age: 0–120 is valid; outside this range is an error
  • appointment_date: future dates valid; birthdate must be in the past
  • transaction_amount: negative valid for refunds; zero is suspicious
Governance Implication
If quality rules are not defined per-dataset, automated quality checks will either generate too many false positives (alerting on valid zeros) or too many false negatives (missing real errors because the threshold was set too loosely). Data stewards must author and maintain quality rule profiles for each dataset they own — this is an active, ongoing responsibility, not a one-time configuration.
12 Backup, Retention & Enterprise Tool Governance
Multiple Backups — The 3-2-1 Rule
Best Practice
3-2-1 Backup Rule
  • 3 copies of data (1 primary + 2 backups)
  • 2 different storage media types (e.g., SSD + cloud object storage)
  • 1 copy offsite or in a different geographic region / cloud availability zone
No single failure (hardware failure, ransomware, accidental deletion, regional outage) should be able to destroy all copies simultaneously.

What Happens Without Defined Retention Policies
  • Database teams purchase incompatible tools with different retention capabilities — some keep data forever, some delete too aggressively
  • Inconsistent storage costs — teams retain everything indefinitely "just in case," inflating cloud storage bills
  • Compliance exposure — data retained past its legal window creates liability; data deleted before its required window destroys audit evidence
  • GDPR right-to-erasure failures — if no one knows where all copies live, erasure requests cannot be fulfilled
Enterprise Architect Role
The Enterprise Architect is responsible for standardizing which tools are approved across the organization for backup, archival, cataloging, quality monitoring, and access control. Without this authority, different teams independently evaluate, purchase, and implement different tools — creating a fragmented technology landscape that is difficult to govern, secure, or support. Tool standardization is a prerequisite for consistent policy enforcement.
13 Data Classification vs Security Classification

These two classification systems are often confused but serve different purposes. They are orthogonal: any combination of data class and security class is possible. Both must be attached to physical data objects as metadata tags, and both travel with the data as it moves through systems.

Classification Type 1
Security Classification
Defines the sensitivity / clearance level required to access the data. Governs who can see it based on their authorization level. Applies regardless of what the data is about.
Classification Type 2
Data Classification
Defines the subject matter domain of the data — HR, Sales, Finance, Customer. Governs what the data is about and which steward owns it. Applies regardless of how sensitive it is.
How They Interact — Classification Matrix

Additional Classification Dimensions
Purpose Classification
Why is this data collected and used? Purpose classification is required by GDPR and guides how long data is retained and who can access it:
  • Analytics — aggregate insights, typically anonymized
  • Operations — day-to-day business processes
  • Compliance — audit, regulatory reporting
  • ML Training — model development; PII must be removed or consented to
Decoupling Labels from Systems
Classification labels must be attached to the physical data objects (tables, files, API responses), not just documented in a spreadsheet. Tools like AWS Glue, Azure Purview, and Apache Atlas tag data at the schema and column level. Labels travel with the data: when a table is copied to a new system, its classification tags replicate with it, ensuring controls apply everywhere the data lives.
14 Enterprise Dictionary & Standardization
Definition
Enterprise Dictionary
A centrally maintained, authoritative registry of standard field definitions, formats, and semantics that all systems must conform to. The enterprise dictionary eliminates the "format war" problem: when every system stores the same type of information in a different format, downstream integration becomes a chain of custom translators.

Real-World Pattern
Hardcoded Format Translation vs Metadata-Driven Standardization
Old approach: when ingesting APIs with different date formats, format conversion logic was written directly inside the backend code — a brittle hardcoded mapping per API source. Adding a new API source required code changes and testing.

Better approach: infuse format metadata into the API response itself. The response includes a content-format field describing the format of each value:
{ "created_at": "05/18/2026", "created_at_format": "MM/DD/YYYY" }
Consumers can auto-detect and standardize without hardcoding. Alternatively, the API contract defines that all dates are ISO 8601 — format normalization happens at the API gateway, invisible to consumers.
Gathering Metadata from Diverse Sources

Enterprises typically have hundreds of data sources — APIs, databases, files, SaaS platforms — each with its own schema. A metadata catalog must be able to scan and infer schemas from these diverse sources automatically, then map them to the enterprise dictionary. This is the foundation of interoperability: once every source is mapped to the standard, any two systems can exchange data without custom translation code.

15 Authentication Standards — SSO, OAuth, JWT & JIT

Authentication verifies who you are. Authorization determines what you can do. These are distinct — authentication is always the first gate. In enterprise data systems, authentication has evolved through several generations, each addressing limitations of its predecessor.

Legacy
Kerberos
Ticket-based protocol used in Windows Active Directory. Users authenticate once to a Key Distribution Center (KDC) and receive tickets for each service. Solid for on-premises Windows environments but poorly suited for cloud-native or cross-organization scenarios.
Enterprise (Older Standard)
SAML 2.0
Security Assertion Markup Language. XML-based protocol for exchanging authentication data between an Identity Provider (IdP) and a Service Provider (SP). Common in legacy enterprise SSO. Verbose XML makes it heavy for modern REST APIs.
Modern Standard
OAuth 2.0
An authorization framework (not authentication) that allows a user to grant a third-party application limited access to their resources without sharing credentials. The foundation of modern API security. Commonly paired with OIDC for authentication.
Modern Standard
OIDC
OpenID Connect — an identity layer built on top of OAuth 2.0. Adds authentication to OAuth by issuing an ID token (a JWT) that confirms who the user is. Used by Google, Microsoft, and most modern IdPs.
Token Format
JWT
JSON Web Token — a compact, self-contained token for transmitting identity claims. Contains a header, payload (user ID, roles, expiry), and a cryptographic signature. Used by OAuth 2.0 / OIDC. Stateless — the server validates the signature without a database lookup.
Access Pattern
JIT Access
Just-In-Time Access — credentials are provisioned only when needed and automatically revoked after use. Can be restricted to a specific IP, device, time window, or purpose. Implements least privilege dynamically. No standing access = no credential to steal.
No System Is 100% Secure
The goal of authentication and authorization is not to achieve perfect security — it is to reduce risk to an acceptable level. Every additional control (MFA, JIT access, device restriction, IP allowlisting) raises the cost and complexity for an attacker. Layering multiple controls (defense in depth) means a single compromised component does not result in full access. JIT access ensures that even if credentials are stolen, they expire before the attacker can use them effectively.
AWS + Microsoft Entra ID

AWS uses Microsoft Entra ID (formerly Azure Active Directory) as an Identity Provider for federated access. Organizations that already manage users in Entra ID can enable SSO across AWS services without maintaining a separate AWS IAM user database. Users authenticate once against Entra ID and receive short-lived AWS credentials via SAML or OIDC federation.

16 SSO — Benefits, Disadvantages & Mitigations
Definition
Single Sign-On (SSO)
An authentication mechanism that allows a user to authenticate once and gain access to multiple systems without re-entering credentials. A central Identity Provider (IdP) holds user credentials and issues tokens that downstream applications trust. The user never shares their password with individual applications.
✅ Benefits of SSO
  • Single user database — one source of truth for all identities; onboarding and offboarding touch one system
  • Instant access revocation — disable one account and access to all connected systems is immediately cut
  • Reduced password fatigue — users remember one credential instead of dozens; fewer forgotten passwords and helpdesk tickets
  • Enhanced user experience — seamless single login across all internal tools
  • Centralized audit trail — all authentication events flow through one system; easy to detect anomalous logins
  • Consistent MFA enforcement — apply MFA once at the IdP layer rather than per-application
  • Faster onboarding — new employees get access to all provisioned systems in one step
❌ Disadvantages of SSO
  • Single point of failure — if the IdP is unavailable, users cannot log in to any connected application
  • Single point of compromise — stolen SSO credentials give an attacker access to every integrated system simultaneously
  • Implementation complexity — configuring SAML/OIDC federation, certificates, and attribute mapping requires expertise
  • Vendor dependency — organizations become reliant on the IdP vendor (Okta, Entra ID, Ping Identity)
  • Legacy app incompatibility — older applications that do not support SAML/OIDC require workarounds or remain excluded
  • Token theft risk — if a JWT is intercepted before expiry, it provides valid access without the original password
Mitigating SSO Disadvantages
RiskMitigation
IdP unavailability (single point of failure)Deploy IdP in active-active HA configuration across multiple availability zones. Maintain break-glass accounts for emergency access that bypass SSO.
Credential theft (single point of compromise)Enforce MFA on all SSO logins. Implement conditional access (block logins from unknown devices or locations). Use short JWT expiry windows (15–60 minutes).
Vendor lock-inUse standard protocols (OIDC, SAML) so IdP can be swapped without changing integrated applications. Evaluate multi-IdP federation for critical systems.
Token theftShort token lifetimes + refresh token rotation. Bind tokens to device fingerprint. Revoke tokens immediately on logout or suspicious activity.
Legacy app incompatibilityUse an SSO proxy/gateway that sits in front of legacy apps and translates modern OIDC tokens to the authentication format the legacy app understands.
17 Security Reference Architecture & Data Consumption
Security Reference Architecture — Defense in Depth

No single control is sufficient. A security reference architecture layers multiple controls so that a failure in any one layer does not result in a full breach. Each layer independently enforces its controls, and all layers are monitored continuously.

Layered Security Controls
Perimeter → Firewall, WAF, DDoS protection, network segmentation
Identity → SSO + MFA, JIT access, conditional access policies, device compliance
Data Access → RBAC / ABAC, row-level security, column masking, data classification enforcement
Data at Rest → AES-256 encryption, key management (AWS KMS, Azure Key Vault), envelope encryption
Data in Transit → TLS 1.3 minimum, mTLS for service-to-service, certificate rotation
Monitoring → SIEM, audit logs, anomaly detection, data access alerts, threat intelligence
Securing Data Consumption at Scale

When multiple users or applications need the same data, naive approaches create both security and performance problems. A consumer that runs SELECT * FROM customer_table without a WHERE clause retrieves far more data than needed — exposing PII unnecessarily and stressing the source system.

High Read Throughput: The RDS Answer
When many consumers need the same data simultaneously, the Read-Only Data Store (RDS/ORDS) is the answer. Rather than every consumer hitting the transactional golden source directly, they query the RDS — a read-optimized copy that can be scaled independently. This isolates the source from read load, allows fine-grained access controls at the RDS layer, and enables consumer-specific views without modifying the source.
Efficient Partitioning — Logical vs Physical
📊 What Partitioning Is
Partitioning is logically one database or table, but physically split across different storage locations, servers, or nodes. The split is transparent to consumers — they query a single table and the database routes the request to the correct partition.
  • Date partitioning: data for each month stored in a separate partition; queries filtered by date only scan the relevant partition
  • Region / country-code partitioning: HR data for each country stored separately; a query scoped to country = US never touches EU data
  • Tenant partitioning: in multi-tenant systems, each customer partition is isolated
🔒 Security & Efficiency Benefit
Partitioning serves both performance and security goals simultaneously:
  • Performance: queries scan only the relevant partition instead of the entire table — orders of magnitude faster on large datasets
  • Security: row-level access policies can be tied to partition boundaries. A consumer with access to region = APAC physically cannot reach region = EU data
  • Example: HR department in the Philippines queries employee records — they are automatically scoped to country_code = PH partitions only
Anti-Pattern: SELECT * Without WHERE
Running SELECT * FROM large_table without a WHERE clause is both a security failure and a performance failure:
  • Returns all rows including those the consumer is not authorized to see
  • Returns all columns including PII that the consumer does not need
  • Performs a full table scan, consuming enormous I/O and compute resources
  • Creates unnecessary data transfer costs in cloud environments
Filtering and cleaning logic must live in the access layer — not in each consumer application. The data platform enforces column masking, row-level filters, and partition scoping automatically so that consumers cannot accidentally or intentionally access more than they are authorized for.
