Section 2: Requirements Gathering

Now that you have read the conversation, extract the requirements. Use AI (Gemini, Claude, or Cursor) to help, but make sure you understand and can explain every item.

Task 2.1: Identify Actors and Their Goals
List every person or system involved in the app.
For each actor, write one sentence: what do they want from the system?
Hint: There are at least 3 actors mentioned (end user, the AI, the database). Look for more.
Prompt to try in Gemini/Claude:
"Based on this Slack conversation [paste conversation], list all actors and their goals for a software requirements doc."
Task 2.2: Extract Functional Requirements
A functional requirement describes what the system must DO.
Write each requirement in the format: "The system shall [action]."
Aim for at least 8 functional requirements from the conversation.
Example: "The system shall allow users to submit a text query through a chat interface."
Example: "The system shall return only data that exists in the MongoDB records collection."
Prompt to try:
"Extract functional requirements from this conversation. Format each as: The system shall [action]."
Task 2.3: Extract Non-Functional Requirements
A non-functional requirement describes HOW the system behaves (performance, privacy, usability).
Find at least 3 non-functional requirements hidden in the conversation.
Hint: Look for statements about privacy, speed, user experience, and data freshness.
Task 2.4: Identify Open Questions
No conversation is ever complete. List at least 3 questions you still have that are NOT answered in the chat.
These are things you would ask in a follow-up meeting.
Example: "What happens when no records match the query - should the AI say it does not know, or should it guess?"

Section 3: Creating the Design Doc with AI

Your design doc is a Markdown file named DESIGN_DOC.md. It lives in the root of your project repository. Think of it as your blueprint before you write a single line of code.

Why a Design Doc First?

Professional developers write design docs before coding - especially for AI features.

A design doc forces you to think through architecture before you are deep in code.

It gives AI tools (Cursor, Gemini) the context they need to generate better, more relevant code.

It serves as documentation for anyone who reviews your project.

3.1 Required Sections in DESIGN_DOC.md

Your design doc MUST include all of the following sections:

# Design Doc: AI-Powered Employee Record Chat

## 1. Problem Statement

## 2. Goals

## 3. Non-Goals (what you are NOT building)

## 4. Actors

## 5. Functional Requirements

## 6. Non-Functional Requirements

## 7. Architecture Overview

- System diagram (describe in text or ASCII art)

- Component list with responsibilities

## 8. API Design

- Endpoints with method, path, request body, response

## 9. Data Model

- MongoDB collection schema

## 10. Tech Stack Justification

## 11. Open Questions

Section 4: Architecture Overview

Before writing code, you need to understand how the pieces connect. This section maps out the system architecture you will build.

System Architecture: React + Express + MongoDB + Ollama (RAG) 
[ React Frontend ]
        |
        | HTTP POST /api/chat { content: "Who is a senior engineer?" }
        v
[ Express.js Backend ]
        |
        |-- 1. Text search MongoDB records
        |     { name: "text", position: "text", level: "text" }
        |
        |-- 2. Build augmented prompt:
        |     Context: [retrieved records]
        |     Question: [user message]
        |
        |-- 3. POST http://localhost:11434/api/generate
        |     { model: "gemma2:2b", prompt: augmented_prompt, stream: true }
        |
        |-- 4. Stream response via SSE back to frontend
        v
[ React Frontend ]
        |
        | Renders tokens as they arrive
        v
[ User sees answer ]

Component Responsibilities

Component Responsibility Key Concept
React (frontend) Send user messages, render streamed response tokens, route /record and /chat React Router, useState, EventSource
Express.js (backend) Receive chat request, query MongoDB, build prompt, call Ollama, stream response SSE, Axios, RAG pattern
MongoDB Atlas Store employee records, enable full-text search on name/position/level fields Text index, $text operator
Ollama + Gemma 2 Run LLM locally, receive augmented prompt, generate grounded response Local inference, streaming API

5.3 Using Cursor to Build the Backend /chat Endpoint

Open the project in VS Code with the Cursor extension active. Use your DESIGN_DOC.md as context.

Cursor Workflow

1. Open Cursor chat (Cmd+L or Ctrl+L)

2. Paste your API design section from DESIGN_DOC.md

3. Ask: "Based on this API design, implement the /chat route in record.mjs using Express SSE and Axios to call Ollama"

4. Review the generated code - do NOT accept it blindly

5. Ask Cursor to explain any line you do not understand

6. Ask Cursor: "What edge cases are missing from this implementation?"

The /chat endpoint must:

  • Accept POST /chat with body { content: "user message" }

  • Set SSE headers: Content-Type: text/event-stream

  • Query MongoDB using $text search on name, position, level fields

  • Build an augmented prompt with retrieved records as context

  • POST to Ollama at http://localhost:11434/api/generate with stream: true

  • Stream each token back to the client as SSE data: events

  • Send data: [DONE] when the stream ends

5.7 Configure MongoDB Text Index

Without a text index, the $text search in the /chat endpoint will fail. Set this up in MongoDB Atlas:

  • Go to your MongoDB Atlas collection (the one from HOS08)

  • Click "Indexes" -> "Create Index"

  • In the Fields input, enter exactly (do not copy-paste, type manually):

{

"name": "text",

"position": "text",

"level": "text"

}

  • Click "Create" and wait for the index to finish building

APPENDIX: HOS10 Threat Model Extension

Apply threat modeling using pytm after building the application

This extension applies AFTER completing the main HOS10 build. You will use pytm - a Pythonic framework for threat modeling - to analyze the security of the RAG application you just built.

What is pytm?

pytm (Python Threat Modeling) is an open-source framework that lets you define your system in code and automatically generates threat reports and data flow diagrams (DFD).

Instead of drawing boxes on a whiteboard, you write Python code that describes your components, data flows, and trust boundaries.

pytm then applies STRIDE analysis automatically.

GitHub: https://github.com/izar/pytm

A.1 Install pytm

# In your Codespaces terminal

pip install pytm

# Verify installation

python -c "import pytm; print(pytm.__version__)"

A.2 Write Your Threat Model

Create a file named threat_model.py in your repo root. Model the components from your design doc:

from pytm import TM, Server, Datastore, Dataflow, Boundary, Actor

tm = TM("HOS10 RAG Application")

tm.description = "Threat model for the AI-powered employee record chat app"

tm.isOrdered = True

# Trust Boundaries

internet = Boundary("Internet")

app_server = Boundary("App Server")

db_zone = Boundary("Database Zone")

# Actors

user = Actor("Employee User")

user.inBoundary = internet

# Components

react_app = Server("React Frontend")

react_app.inBoundary = internet

react_app.isEncrypted = False # HTTP in dev - flag this

express_api = Server("Express.js Backend")

express_api.inBoundary = app_server

express_api.isEncrypted = True

mongodb = Datastore("MongoDB Atlas")

mongodb.inBoundary = db_zone

mongodb.isEncrypted = True

mongodb.isSQL = False

ollama = Server("Ollama LLM Server")

ollama.inBoundary = app_server

ollama.isEncrypted = False # local only

# Data Flows

Dataflow(user, react_app, "User submits chat query")

Dataflow(react_app, express_api, "POST /api/chat { content }")

Dataflow(express_api, mongodb, "Text search query")

Dataflow(mongodb, express_api, "Matching employee records")

Dataflow(express_api, ollama, "Augmented prompt POST /api/generate")

Dataflow(ollama, express_api, "Streamed token response")

Dataflow(express_api, react_app, "SSE stream to client")

tm.process()

A.3 Generate the Threat Report

# Generate DFD (requires graphviz)

pip install graphviz

python threat_model.py --dfd | dot -Tpng -o dfd.png

# Generate full threat report

python threat_model.py --report

A.4 STRIDE Analysis Task

After running pytm, review the generated threats. For each threat category, answer the question using AI assistance:

STRIDE Threat Type Question to Answer for This App
S Spoofing Can an attacker impersonate a legitimate user in the chat interface?
T Tampering Can an attacker modify employee records to manipulate AI responses?
R Repudiation Is there a log of who submitted which chat queries?
I Information Disclosure Could the AI leak employee data to unauthorized users?
D Denial of Service What happens if an attacker floods the /api/chat endpoint?
E Elevation of Privilege Can a regular user trigger admin-level MongoDB operations?

Learning Goal of the Threat Model Extension

Security is not an afterthought - it is part of architecture.

By running pytm AFTER you build, you experience first-hand what threats you introduced.

The goal is not to fix everything - it is to RECOGNIZE what the risks are and articulate mitigations.

This is the same process used in professional security reviews.
