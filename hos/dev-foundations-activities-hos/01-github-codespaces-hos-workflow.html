Key Concepts

GitHub Codespaces

  • Cloud Development Environment: GitHub Codespaces provides a cloud-based development environment that allows developers to code directly from their browsers or VS Code. It offers a fully configured environment with necessary dependencies pre-installed.
  • Fast Setup: Codespaces reduces setup time by providing pre-built environments, eliminating the need for manual configuration.
  • Integration: Seamlessly integrates with GitHub repositories, enabling developers to start coding immediately with complete version control support.

Python

  • Programming Language: Python is a high-level, general-purpose programming language known for its readability, versatility, and strong community support.
  • Use Cases: Commonly used in web development, data science, machine learning, and automation due to its extensive library ecosystem.
  • Dynamic and Interpreted: Python executes code line by line, making debugging and prototyping applications easy.
  • Cross-Platform Compatibility: Runs on various operating systems without modification, making it ideal for developing scalable applications.

Jupyter

  • Interactive Computing: Jupyter Notebook is an open-source web application that allows users to create and share documents containing live code, equations, visualizations, and text.
  • Multi-Language Support: Supports various programming languages, with Python being the most widely used.
  • Data Science and Research: Frequently used in data analysis, machine learning, and research due to its ability to execute code in cells and display output instantly.
  • Extensibility: Supports plugins and extensions, allowing integration with different libraries and tools.

Docker File

  • Automated Image Building: A Dockerfile is a script containing a series of instructions for building a Docker image.
  • Reproducibility: Ensures consistent environments by defining dependencies, configurations, and installation steps.
  • Layered Structure: Each instruction in a Dockerfile creates a new layer in the image, making it efficient for caching and updates.
  • Customization: Users can define environment variables, network settings, and commands to tailor container behavior.

Docker Image

  • Executable Package: A Docker image is a lightweight, standalone package containing everything needed to run an application, including code, runtime, libraries, and dependencies.
  • Template for Containers: Acts as a blueprint from which containers are instantiated.
  • Portability: A Docker image can be shared via container registries like Docker Hub, making deployment easier across different environments.
  • Immutable: Once built, images remain unchanged, ensuring consistency across deployments.

Docker Container

  • Runtime Instance: A Docker container is a running instance of a Docker image, providing an isolated execution environment.
  • Lightweight and Efficient: A Docker container uses the host OS kernel, making it more resource-efficient than traditional virtual machines.
  • Scalability: Containers can be easily scaled up or down based on application demand.
  • Isolation: A Docker container ensures that applications run independently without affecting the host system or other containers.

Section 3: Using Docker

1) Installing Docker

  1. Click on Extensions in the left panel.
  2. Search Docker in the marketplace.
  3. Click on the Install button.
Docker extension in the VS Code marketplace ready to install.

2) Adding a Dockerfile

A Dockerfile is a specification for building a Docker image. We will write a Dockerfile, use the Dockerfile to make a custom image, create a container using the image, shell into the container, and start the Lisp REPL (Read-Eval-Print Loop).

  1. Click on New File and name Dockerfile.
  2. Note: Dockerfile does not have an extension. It should be named as Dockerfile.
  3. Write the code below in Dockerfile (as shown in the course handout):
# Dockerfile

FROM ubuntu:20.04

RUN apt update && apt install -y sbcl

WORKDIR /usr/src
Dockerfile appearing in the file explorer after creation.
Dockerfile open in the editor showing Ubuntu base image and SBCL install instructions.

3) Adding a Dockerfile (build)

To build our image, use the Docker build command in the terminal (View → Terminal). Ensure that you are in the working directory containing your new Docker file.

The -t lisp part says, “Give the resulting image a tag of lisp.” The dotted part (.) says, “When you look for the Dockerfile to build the image in the current directory.”

  1. In your Terminal, type the following command:
    docker build -t lisp .
  2. The output will match the successful build shown in the handout.
  3. Take a screenshot of your ‘02 Adding a Dockerfile’ as 02_adding_dockerfile_firstname_lastname.png by using your first and last name.
Terminal output showing a successful docker build -t lisp . run.

4) Confirming the image is created

Use the docker image ls command to list all existing images, which should now include the image.

  1. In your Terminal, type the following command:
    docker image ls
  2. The output will show your tagged image.
  3. Take a screenshot of your ‘03 Confirm image’ as 03_confirm_image_firstname_lastname.png by using your first and last name.
docker image ls output confirming the lisp image was created.

5) Running the container

Run the following command. The command accesses the command line inside the container based on your image. Replace <image id> with the image id you see when you run docker image ls.

  1. In your Terminal, type the following command:
    docker run --interactive --tty <image id> /bin/bash
  2. The docker run command creates a container from the image. The /bin/bash argument says, “the thing you should run on this container is the /bin/bash program.”
  3. The output will show a shell inside the container as in the handout.
  4. Take a screenshot of your ‘04 Running container’ as 04_running_container_firstname_lastname.png by using your first and last name.
Terminal prompt inside the running container after docker run.

6) Viewing containers

Open a separate terminal and run docker container ls.

  1. Open a new terminal.
  2. In your Terminal, type the following command:
    docker container ls
  3. The output will list running containers as in the handout.

Why This Matters
Codespace = provisioned compute node

A GitHub Codespace is an on-demand cloud VM tied directly to a repository. It abstracts the local machine entirely — the execution environment is provisioned, not installed. Nothing else in the workflow runs until this node exists.

Image vs container — blueprint vs running instance

A Dockerfile is infrastructure as code: it defines immutable layers that docker build compiles into an image artifact. docker run instantiates that artifact as an isolated process. You cannot run a container from an image that does not yet exist.

System layers — each depends on the one before

Cloud VM → development tooling → build recipe → image artifact → running process → remote persistence. Every operation in this workflow promotes the system into the next layer. Skipping a layer breaks the chain.

Your goal

Sequence the operations that move through those layers: provision the cloud environment, install tooling, author the build recipe, compile the image, verify the artifact, instantiate a container, then replicate your work back to the remote origin.

💻 GitHub Codespaces system design — provisioned environment to running container
Panel A: a change moves through all system layers — cloud VM → Dockerfile (build recipe) → image (immutable artifact) → running container (isolated process). Panel B: running docker build without a Dockerfile in the build context fails immediately — the build layer has no recipe to compile.

The objective: Map the system design of a GitHub Codespaces workflow by sequencing the seven operations that move the system through its layers — from provisioning a cloud compute node to instantiating a running container and persisting work to the remote origin. Not every operation listed belongs in the correct sequence.

Think about: Each operation has a dependency on the layer established before it. You cannot install extensions without a running Codespace. You cannot build an image without a Dockerfile. You cannot run a container without an image artifact. You cannot push without local files to commit. What layer does each operation produce, and what does the next operation require?

▼
🌐Open GitHub Codespace
Step 1 — Provisions the cloud compute node tied to your GitHub repository. The Codespace is the execution environment; the working tree, terminal, and Docker daemon all live inside it.
📋 Layer: Cloud VM — nothing else in the system can run until this node is live.
🐍Python + Jupyter; Hello World notebook
Step 2 — Installs development tooling (Python and Jupyter extensions) into the provisioned environment, then validates the runtime by executing print("Hello World") in helloworld.ipynb.
📋 Layer: Development tooling — installed into the cloud VM; requires the Codespace to already exist.
📦Docker extension + Dockerfile
Step 3 — Adds the Docker extension and authors a Dockerfile — the build recipe that defines image layers as infrastructure as code. The file must exist on disk before the build step.
📋 Layer: Build recipe — the Dockerfile is the input artifact that the build system compiles.
🔧docker build -t lisp .
Step 4 — Compiles the Dockerfile into an immutable image artifact tagged lisp. Run from the terminal in the directory containing the Dockerfile; . sets the build context.
📋 Boundary: Build recipe → Image artifact — image does not exist until this succeeds.
📂docker image ls
Step 5 — Verifies the image artifact exists in the local registry and retrieves the image ID needed for instantiation. A system design checkpoint: confirm the artifact before creating a process from it.
📋 Layer: Image artifact verification — you cannot reference an image ID that does not exist.
🚀docker run -it [image id] /bin/bash
Step 6 — Instantiates the image as a running container process with an interactive shell. The container is isolated from the host, shares the kernel, and exists only while the process runs.
📋 Boundary: Image artifact → Running process — container cannot start without a valid image.
↑git push (submit to GitHub)
Step 7 — Replicates local commits (files, screenshots, Dockerfile) to the remote origin. The final boundary crossing — work exists on the cloud VM only until it is pushed to the repository.
📋 Boundary: Local history → Remote origin — run after the Docker exercises have produced local files to commit.
💻docker container ls
Lists running containers. Useful for observing the running process layer, but not one of the seven operations in the system design sequence for this workflow.
💻Install local Hyper-V / VMware first
A local hypervisor provisions VMs on physical hardware. GitHub Codespaces is a remote cloud VM — a different system architecture that requires no local hypervisor.
💻docker push lisp to Docker Hub
Replicates a local image to a public registry. This is a different boundary crossing from git push and is not part of this workflow's system design sequence.
💻pip install packages before opening repo
Dependency installs belong inside the provisioned Codespace environment, not before the compute node exists. Installing into an unrelated local context has no effect on the cloud VM.
