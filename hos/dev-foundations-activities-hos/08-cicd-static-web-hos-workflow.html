Azure Static Web Apps 
 
Azure Static Web Apps are tightly integrated with CI/CD workflows, making it easy to automate the build 
and deployment of static websites and serverless APIs. Here's how they relate to CI/CD: 
 
CI/CD Integration in Azure Static Web Apps 
1. GitHub Actions Integration 
When you create an Azure Static Web App and link it to a GitHub repository, Azure 
automatically sets up a GitHub Actions workflow. This workflow: 
• 
Triggers on events like push or pull_request to the main branch. 
• 
Build your front-end app and optional Azure Functions API. 
• 
Deploys the output to the Azure Static Web App environment. 
 
The workflow file is stored in .github/workflows/ and typically named like azure-static-web-
apps-<RANDOM>.yml [1]. 
 
2. Azure DevOps Pipelines Support 
Azure Static Web Apps also support Azure Pipelines: 
• 
You can manually configure a YAML pipeline to build and deploy your app. 
• 
Requires setting up a deployment token for authentication. 
• 
Offers flexibility for teams using Azure DevOps instead of GitHub [2]. 
 
CI/CD Workflow Components 
Whether using GitHub Actions or Azure Pipelines, your CI/CD setup typically includes: 
• 
Build step: Compiles your static site (e.g., using npm run build). 
• 
API build step (optional): Builds Azure Functions if included. 
• 
Deploy step: Pushes the built assets to Azure Static Web Apps.

Benefits of CI/CD with Azure Static Web Apps 
• 
Automation: No manual deployment needed—just push code. 
• 
Speed: Fast build and deploy cycles. 
•

• 
Security: Uses GitHub or Azure tokens for secure deployments.

GitHub Actions 
GitHub Actions is a powerful feature of GitHub that enables you to automate, customize, and execute 
your software development workflows directly in your GitHub repository. 
 
What GitHub Actions Does 
GitHub Actions allows you to: 
• 
Automate CI/CD pipelines (build, test, and deploy code). 
• 
Run workflows triggered by GitHub events (e.g., push, pull_request, issue). 
• 
Use or create reusable actions to simplify complex tasks. 
• 
Run jobs on different operating systems (Linux, Windows, macOS). 
 
Core Concepts 
Concept Description 
Workflow A YAML file that defines the automation process. Stored in .github/workflows/. 
Job 
A set of steps that run on the same runner. 
Step 
A single task (e.g., run a script, use an action). 
Action 
A reusable unit of code (e.g., setup Node.js, deploy to Azure). 
Runner 
A server that runs your workflow (GitHub-hosted or self-hosted). 
 
Example Workflow 
name: Node.js CI 
This workflow runs on every push, installs dependencies, and runs tests for a Node.js project. 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
Benefits 
• 
Integrated with GitHub: No need for external CI/CD tools. 
• 
Scalable: Supports parallel jobs and matrix builds. 
• 
Secure: Built-in secrets management. 
• 
Flexible: Works with any language or framework.

Section 2: Conducting CI/CD Pipeline Integration 
 
1. In your HOS08 GitHub Codespaces, open a new terminal, and type the following command. 
>>> git checkout -b development 
Creates a new branch called development from your current branch. Switches to that new branch so 
you can start working on it. 
 
git checkout -b development 
 
 
 
2. Modify the “index.html” file with the following code. 
 
<h1>Hello World!<h1> 
 
3. Commit the changed file to your GitHub repository. 
>>> git add --all 
Stages all changes (new, modified, and deleted files) in your working directory for the next commit. 
 
>>> git commit -m “development branch” 
Create a new commit with all staged changes and adds the message "development branch" to describe 
what was changed in this commit. 
 
>>> git push -f origin development 
Forcefully update the development branch on the remote repository (origin) with your 
local development branch.
