What Is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data flows for a system to satisfy specified requirements. It bridges the gap between requirements and implementation.

Key Principles

Every system design balances trade-offs across: scalability (handle growth), availability (stay online), consistency (correct data), latency (fast response), and cost (efficient resources).

# Back-of-the-envelope: Twitter-like service

# Users & activity
daily_active_users = 300_000_000     # 300M DAU

# Write throughput

# Read throughput
reads_per_sec = (daily_active_users * reads_per_user_day) / 86400
print(f"Read QPS: {reads_per_sec:,.0f}")   # ~347,222 QPS

# Storage per year (avg tweet ~300 bytes)
daily_tweets = daily_active_users * tweets_per_user_day
storage_per_day = daily_tweets * 300  # bytes
storage_per_year_tb = (storage_per_day * 365) / (1024**4)
print(f"Storage/year: {storage_per_year_tb:,.1f} TB")  # ~60 TB

# Read:Write ratio = 50:1 → read-heavy → caching critical!

Python — Flask
from flask import Flask, jsonify, request

app = Flask(__name__)
messages = []

# REST: Client polls for new messages
@app.route('/api/messages', methods=['GET'])
def get_messages():
    since = request.args.get('since', 0, type=int)
    new = [m for m in messages if m['id'] > since]
    return jsonify(new)

@app.route('/api/messages', methods=['POST'])
def post_message():
    data = request.json
    msg = {'id': len(messages)+1, 'text': data['text']}
    messages.append(msg)
    return jsonify(msg), 201

# Problem: clients must poll → wasted requests + latency
Python — WebSocket
import asyncio
import websockets

connected = set()

async def handler(websocket):
    connected.add(websocket)
    try:
        async for message in websocket:
            # Broadcast to all connected clients instantly
            await asyncio.gather(
                *[client.send(message)
                  for client in connected
                  if client != websocket]
            )
    finally:
        connected.discard(websocket)

# Advantage: real-time push, no polling overhead
asyncio.run(
    websockets.serve(handler, "localhost", 8765)
)

Implementing Cache-Aside with Redis

Python
import redis, json, hashlib

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def get_user_profile(user_id: str) -> dict:
    cache_key = f"user:{user_id}"

    # Step 1: Try cache first
    cached = r.get(cache_key)
    if cached:
        print("✓ Cache HIT")
        return json.loads(cached)

    # Step 2: Cache miss → query database
    print("✗ Cache MISS → querying DB")
    user = db.query("SELECT * FROM users WHERE id = %s", user_id)

    # Step 3: Populate cache with TTL
    r.setex(
        cache_key,
        3600,  # TTL: 1 hour
        json.dumps(user)
    )
    return user

def update_user_profile(user_id: str, data: dict):
    # Write-through: update DB, then invalidate cache
    db.execute("UPDATE users SET ... WHERE id = %s", user_id)
    r.delete(f"user:{user_id}")  # Invalidate!

Consistent Hashing Implementation

Python
import hashlib
from bisect import bisect_right

class ConsistentHash:
    def __init__(self, nodes=None, replicas=150):
        self.replicas = replicas  # Virtual nodes per server
        self.ring = {}
        self.sorted_keys = []
        for node in (nodes or []):
            self.add_node(node)

    def _hash(self, key: str) -> int:
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_node(self, node: str):
        """Add a server with virtual nodes spread across the ring."""
        for i in range(self.replicas):
            key = self._hash(f"{node}:{i}")
            self.ring[key] = node
            self.sorted_keys.append(key)
        self.sorted_keys.sort()

    def get_node(self, item: str) -> str:
        """Find which server handles this key."""
        h = self._hash(item)
        idx = bisect_right(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[idx]]

# Usage: adding/removing a server only remaps ~1/N keys!
ch = ConsistentHash(["server-A", "server-B", "server-C"])
print(ch.get_node("user:42"))   # → "server-B"
print(ch.get_node("user:99"))   # → "server-A"

Message Queues & Async Processing

Decouple services, handle traffic bursts, and build resilient event-driven architectures with Kafka, RabbitMQ, and SQS.

◆ Core Concepts

Why Asynchronous?

Synchronous processing creates tight coupling and cascading failures. Message queues act as buffers — producers push work, consumers process at their own pace. Benefits include: decoupled services, absorbing traffic spikes, retry semantics, and enabling event-driven architectures.

Key Trade-off

Async adds eventual consistency and operational complexity. Use it when the work can tolerate delay (email, analytics, image processing) — not when users need an instant response (payment confirmation).

Distributed Systems Fundamentals

CAP theorem, consensus protocols, distributed transactions, and handling failure in distributed systems.

◆ Core Concepts

The CAP Theorem

In a distributed system, when a network partition occurs, you must choose between Consistency (every read gets the most recent write) and Availability (every request gets a response). You cannot have both during a partition.

ChoiceSystem TypeExampleBehavior During Partition
CPConsistentZooKeeper, HBaseRejects requests until consistent
APAvailableCassandra, DynamoDBServes stale data, reconciles later
Beyond CAP

Modern systems often use PACELC: if Partition → choose A or C; Else (normal operation) → choose Latency or Consistency. DynamoDB is PA/EL, while ZooKeeper is PC/EC.

Implementing a Simple Raft-like Leader Election

Python — Conceptual
import random, time

class RaftNode:
    def __init__(self, node_id, peers):
        self.id = node_id
        self.peers = peers
        self.state = "follower"   # follower | candidate | leader
        self.current_term = 0
        self.voted_for = None
        self.votes_received = 0
        self.election_timeout = random.uniform(1.5, 3.0)  # seconds

    def start_election(self):
        """Transition to candidate, request votes from peers."""
        self.state = "candidate"
        self.current_term += 1
        self.voted_for = self.id
        self.votes_received = 1  # Vote for self
        print(f"Node {self.id}: starting election for term {self.current_term}")

        for peer in self.peers:
            vote = peer.request_vote(self.current_term, self.id)
            if vote:
                self.votes_received += 1

        # Majority = quorum
        if self.votes_received > (len(self.peers) + 1) / 2:
            self.state = "leader"
            print(f"✓ Node {self.id}: elected LEADER (term {self.current_term})")

    def request_vote(self, term, candidate_id) -> bool:
        """Grant vote if term is newer and haven't voted yet."""
        if term > self.current_term and self.voted_for is None:
            self.current_term = term
            self.voted_for = candidate_id
            return True
        return False

Monolith → Microservices Evolution

Microservices decompose a system into independent, deployable services that communicate over the network. Each service owns its data and can be scaled independently. But they introduce complexity: distributed transactions, network failures, and operational overhead.

The Golden Rule

Start with a monolith. Extract microservices only when you have a clear scaling bottleneck or organizational need (separate teams). Premature decomposition is the root of much suffering.

Circuit Breaker Pattern

Python
import time

class CircuitBreaker:
    """Prevents cascading failures across microservices."""

    def __init__(self, failure_threshold=5, recovery_timeout=30):
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.state = "CLOSED"      # CLOSED → OPEN → HALF_OPEN
        self.last_failure_time = None

    def call(self, func, *args):
        if self.state == "OPEN":
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "HALF_OPEN"  # Allow one test request
            else:
                raise Exception("Circuit OPEN — service unavailable")

        try:
            result = func(*args)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise e

    def _on_success(self):
        self.failure_count = 0
        self.state = "CLOSED"

    def _on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = "OPEN"
            print("⚠ Circuit breaker OPENED")

# Usage
cb = CircuitBreaker(failure_threshold=3)
try:
    result = cb.call(payment_service.charge, order)
except:
    # Fallback: queue for retry, return pending status
    queue.enqueue("retry_payment", order)

import hashlib, base64

class URLShortener:
    def __init__(self):
        self.counter = 0  # Auto-incrementing ID

    def encode(self, long_url: str) -> str:
        """Generate a unique short code.
        Strategy: base62 encode an auto-incrementing ID.
        7 chars in base62 → 62^7 = 3.5 trillion unique URLs."""
        self.counter += 1
        return self._to_base62(self.counter)

    def _to_base62(self, num: int) -> str:
        chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
        result = []
        while num > 0:
            result.append(chars[num % 62])
            num //= 62
        return "".join(reversed(result)).zfill(7)

📰 Design a News Feed (like Twitter/X)

The core trade-off: Fan-out on Write (pre-compute feeds at post time — fast reads, expensive for celebrities) vs Fan-out on Read (assemble feed at read time — slower reads, simpler writes). Most systems use a hybrid.

Python — Hybrid Feed
CELEBRITY_THRESHOLD = 100_000  # followers

def publish_post(user, post):
    db.save(post)

    if user.follower_count < CELEBRITY_THRESHOLD:
        # Fan-out on Write: push to all followers' feeds
        for follower_id in user.followers:
            redis.lpush(f"feed:{follower_id}", post.id)
            redis.ltrim(f"feed:{follower_id}", 0, 999)
    else:
        # Celebrity: skip fan-out, merge at read time
        pass

def get_feed(user_id, page=0):
    # Step 1: Get pre-computed feed from cache
    post_ids = redis.lrange(f"feed:{user_id}", page*20, (page+1)*20)

    # Step 2: Merge in celebrity posts (fan-out on read)
    celeb_posts = db.query("""
        SELECT * FROM posts
        WHERE user_id IN (followed celebrities)
        ORDER BY created_at DESC LIMIT 20
    """)

    # Step 3: Merge, rank, return
    return merge_and_rank(post_ids, celeb_posts)

🗺️ Design a Rate Limiter

Algorithms: Token bucket, sliding window log, sliding window counter, fixed window counter.

Python — Sliding Window
import time

class SlidingWindowRateLimiter:
    def __init__(self, redis_client, max_requests=100, window_sec=60):
        self.redis = redis_client
        self.max_requests = max_requests
        self.window = window_sec

    def allow_request(self, client_id: str) -> bool:
        key = f"ratelimit:{client_id}"
        now = time.time()
        pipe = self.redis.pipeline()

        # Remove entries outside the window
        pipe.zremrangebyscore(key, 0, now - self.window)
        # Count remaining entries
        pipe.zcard(key)
        # Add current request
        pipe.zadd(key, {str(now): now})
        # Set TTL for cleanup
        pipe.expire(key, self.window)

        _, count, _, _ = pipe.execute()
        return count < self.max_requests
