Deep Dive: Technology Stack

📨 Kafka — Event Streaming Backbone

Role: Central nervous system. Every click, impression, and conversion flows through Kafka topics in real-time.

Use Cases

  • Stream billions of click/impression events
  • Fan-out events to multiple consumers (Flink, Spark, Elasticsearch)
  • Guaranteed at-least-once delivery with rebalancing
  • Topic retention for replay/recovery

Topics & Partitioning

  • click-events — Partitioned by seller_id for parallel processing
  • impression-events — High throughput, partitioned by ad placement
  • conversion-events — Purchase confirmations, partitioned by order_id
  • Each partition replicated to minimize data loss

Partitioning Strategy

  • Key-based partitioning ensures related events land on same partition
  • Flink consumers track per-partition offsets for exactly-once semantics
  • Offset management via Flink state backend (RocksDB) or ZooKeeper

Operational Challenges

  • Consumer Lag — Monitor lag between latest offset and consumer offset
  • Broker Saturation — Network bandwidth can bottleneck during spikes
  • Rebalancing Storms — Mass consumer failure can cause rebalancing cascades
  • Topic Sprawl — Need governance to prevent topic saturation

⚡ Apache Flink — Real-Time Stream Processing

Role: Real-time computation engine. Consumes Kafka events, computes aggregations, detects anomalies, and materializes results to storage.

Job Examples

  • Click Aggregator — Tumbling windows (1-min) grouping clicks by ad placement
  • Impression Counter — Session windows detecting user impression patterns
  • Revenue Aggregator — Sliding windows computing rolling 5-min GMV
  • Anomaly Detector — Stateful operators comparing current rates to baseline

State Management

  • RocksDB Backend — Persists operator state to disk for fault tolerance
  • Savepoint — Explicit checkpoints for planned restarts or version upgrades
  • Checkpoint Alignment — Ensures exactly-once semantics across parallelism
  • TTL State Cleanup — Auto-cleanup of old state to prevent unbounded memory

Windowing Strategy

  • Tumbling (1-min) — Non-overlapping; good for counts and sums
  • Sliding (5-min, 1-min step) — Overlapping; for trending metrics
  • Session (30-sec gap) — Detects user activity bursts/droughts
  • Late event handling: drop, redirect to side output, or merge with next window

Operational Challenges

  • Backpressure — Downstream sinks (ClickHouse) can't keep up; buffers fill
  • Checkpoint Timeouts — Long-running operators can fail to checkpoint
  • Job Restart Latency — Restoring state from RocksDB takes time during recovery
  • Watermark Drift — Clock skew in event timestamps causes out-of-order processing

🔥 Apache Spark — Batch & Interactive Processing

Role: Batch processing for ETL, machine learning, and ad-hoc queries. Complements Flink for use cases needing distributed computing.

Supplement: Condensed notes from eBay’s public Spark write-ups (2014 adoption + 2021 SQL engine) — eBay & Apache Spark — digest for discussion.

Use Cases

  • Nightly ETL — Transform and deduplicate raw events from HDFS
  • Bid Recommendations — ML pipeline training models for keyword bids
  • Attribution Reconstruction — Historical click-to-conversion linking
  • Ad-hoc Analytics — Data scientists query for new insights

DAG & Execution

  • Transformations — map, filter, join, groupByKey, reduceByKey create DAG
  • Actions — collect, count, saveAsParquet trigger driver submission
  • Lazy Evaluation — Transformations don't execute until action is called
  • Catalyst Optimizer — Rewrites logical plan to efficient physical plan

Partitioning & Shuffling

  • Hash Partitioning — Default for joins and group-bys
  • Range Partitioning — Useful for time-series data (date ranges)
  • Custom Partitioner — Route records to executors manually
  • Shuffle Optimization — Sort-merge join vs. hash join trade-offs

ML Pipeline Integration

  • MLlib — Distributed algorithms (random forests, logistic regression)
  • Feature Engineering — NLP, one-hot encoding, scaling pipelines
  • Model Persistence — Save trained models to cloud storage for serving
  • Training Jobs — Run nightly for bid recommendations and ranking

🐘 Hadoop — Log Storage & Batch Archive

Role: Long-term data archival and heavy-duty batch processing. Stores petabytes of historical data (Apollo/Hermes).

Architecture

  • HDFS (Hadoop Distributed File System) — Data distributed across nodes with 3x replication
  • NameNode — Metadata server tracking file locations
  • DataNodes — Physical storage nodes holding blocks
  • MapReduce — Distributed batch computation (often replaced by Spark)

Data Organization

  • Daily Partitions — Data organized by date (e.g., /data/clicks/2025/04/07/)
  • Format — Parquet for structured data, Avro for schemas, ORC for analytics
  • Compression — Snappy or gzip to reduce storage footprint
  • Retention — 2-3 years of hot data, older data archived to glacier

Typical Workflow

  • Kafka Hadoop Connector ingests raw events to HDFS hourly
  • Nightly Spark job deduplicates and transforms raw events → Parquet
  • Data scientists query with Spark SQL or Hive meta store
  • Export subsets to ClickHouse for fast analytics

Operational Challenges

  • NameNode Bottleneck — Single point of metadata; HA requires Zookeeper
  • Small Files Problem — Thousands of small files per day consume metadata
  • Slow Queries — Full table scans on petabytes can take hours
  • Network Saturation — Data movement during rebalancing can choke bandwidth

🔍 Elasticsearch (Pronto Internal) — Logs & Metrics

Role: Real-time log aggregation, anomaly detection, and metadata storage. Powers alerting and debugging dashboards.

Use Cases

  • Log Ingestion — Structured logs from microservices with JSON format
  • Anomaly Detection — Elasticsearch ML detects unusual error patterns
  • Troubleshooting — Full-text search for debugging incidents
  • Metadata Storage — Config snapshots, experiment definitions, ad rules

Indexing & Sharding

  • Time-Based Indices — Daily indices (e.g., logs-2025.04.07) for retention
  • Sharding — Distributes huge indices across cluster nodes
  • Replicas — Each shard typically replicated 2x for availability
  • Index Lifecycle — Auto-archive or delete old indices via ILM policies

Query Patterns

  • Match Queries — Full-text search on error messages
  • Range Queries — @timestamp between two points in time
  • Aggregations — terms aggs counting errors by service
  • Painless Scripts — Custom scoring or filtering logic

Operational Challenges

  • Disk Pressure — Indices grow fast; need aggressive cleanup policies
  • GC Pauses — Java garbage collection can cause brief unresponsiveness
  • Shard Imbalance — Uneven data distribution across nodes
  • Query Timeout — Slow aggregations can timeout at query layer

⚙️ ClickHouse (NuColumnar) — Real-Time Analytics

Role: Ultra-fast columnar database for real-time metrics and reporting. Powers dashboards, alerts, and revenue tracking.

Columnar Architecture

  • Column Store — Data stored by column, not row (better compression)
  • Vectorized Execution — Process millions of rows per second
  • Data Skipping — Metadata (min/max per block) skips irrelevant data
  • LZ4/Zstd Compression — High compression ratios reduce disk I/O

Ingestion Pipeline

  • Flink Consumer — Kafka → aggregated data → ClickHouse HTTP API
  • Batch Inserts — Flink batches records (e.g., 1-min windows) for efficiency
  • ReplacingMergeTree — Handles late updates and corrections
  • Partitioning — By date for easy archival to cold storage

Query Patterns

  • GROUP BY Queries — Aggregate clicks/GMV by placement, seller, time
  • Range Scans — Time-range queries for recent metrics (last 24 hours)
  • JOIN Operations — Link placements to campaigns on lookup tables
  • SUM/COUNT/AVG — Revenue aggregations via simple SQL

Operational Challenges

  • Memory Pressure — Large aggregations must fit in RAM
  • Merges During Inserts — ReplacingMergeTree background merges can stall
  • Query Complexity — No JOIN optimization; complex queries slow down
  • Replica Lag — Replication lag can cause metric discrepancies

🔍 Prometheus & Grafana — Metrics & Dashboards

Role: Time-series metrics collection and visualization. Powers operational dashboards and PromQL-based alerting rules.

Prometheus Architecture

  • Pull Model — Prometheus scrapes /metrics endpoints from services
  • Scrape Config — Target discovery via Kubernetes, Consul, or static files
  • Remote Storage — Write metrics to remote TSDB for long-term storage
  • Retention — Default 15 days local; long-term via remote write

Metric Types

  • Gauge — Current value (e.g., CPU %, memory used)
  • Counter — Monotonically increasing (e.g., total requests)
  • Histogram — Latency distribution (buckets for p50, p99)
  • Summary — Quantile tracking (alternative to histogram)

PromQL Queries

  • Instant Vector — {job="ads-api"}[current value per series]
  • Range Vector — {job="ads-api"}[5m] [last 5 min of values per series]
  • rate() — Per-second increase; rate(requests[5m])
  • histogram_quantile() — Derive p99 latency from histogram buckets

Grafana Dashboards

  • Revenue Dashboard — GMV, clicks, impressions real-time graphs
  • Service Health — API latency, error rates, availability per service
  • Resource Usage — Pod CPU/memory, disk I/O, network bandwidth
  • Alert Status — Current firing alerts with severity levels

🔦 Sherlock.IO (Internal) — Anomaly Detection

Role: Real-time anomaly detection using statistical models. Identifies unusual patterns in logs, metrics, and events.

Detection Methods

  • Baseline Comparison — Compare current metrics to same time last week
  • ARIMA Models — Forecast expected value; flag if actual exceeds threshold
  • Clustering — Identify log patterns that are not in "normal" cluster
  • Rate of Change — Flag if metric changes > 20% in 5 minutes

Integration Points

  • Elasticsearch ML — Consumer lag anomaly detection on Kafka topics
  • Custom Detectors — Revenue drop, click drop, latency spike rules
  • Alert Firing — Anomaly triggers PagerDuty alert + Slack message
  • False Positive Tuning — Baseline adjustments to reduce noise

Common Signals

  • GMV drop > 15% vs. baseline
  • Click/impression drop > 20% vs. rolling average
  • API latency p99 > 500ms
  • Error rate > 1% on critical services

How anomaly detection is implemented

In practice, “anomaly detection” here is a pipeline, not a single model: raw telemetry becomes features (rates, ratios, lag, error shares), compared to baselines (rolling windows, same time last week, or forecasts), then scored and routed to alerting. Multiple implementations coexist — statistical rules, time-series models, and log/ML jobs — because ads systems need both fast path (minutes) and robust path (seasonality, marketing events).

Data path

  • Ingest — Prometheus scrapes; Kafka streams for event-derived KPIs; Elasticsearch for log-derived errors
  • Windows — Tumbling/sliding windows (Flink or PromQL rate() over ranges) to form comparable rates
  • Baseline store — Historical aggregates (same hour DOW, trailing median) or model output (ARIMA / ES ML expected value)
  • Score & decide — Deviation, z-score, or rule threshold → severity + deduplication key
  • Notify — PagerDuty / Slack; optional ticket; fingerprint to suppress repeats

Streaming vs batch roles

  • Flink / stateful path — Compare live aggregates to in-state baselines for click fraud spikes, attribution swings, consumer lag (minutes-level)
  • Scheduled jobs — Recompute slow-moving baselines, retrain seasonal components, backfill after outages
  • Elasticsearch ML — Unsupervised patterns on log volumes and Kafka lag time series
  • Static thresholds — Still used for hard SLOs (e.g. p99 cap) where models add noise

Requirements (detection layer)

  • Latency — Business KPI anomalies visible within SLA (often single-digit minutes for revenue)
  • Precision vs recall — Tune to avoid alert fatigue; document false-negative risk for money metrics
  • Explainability — Each alert should carry dimension hints (service, region, placement) for triage
  • Ownership — Clear line between platform-owned detectors and product-owned experiment guards

Ads-specific twists

  • Campaign & seasonality — Baselines must exclude known promos or use stratified series
  • Auction dynamics — Bid floor changes can look like anomalies unless experiments are tagged
  • Attribution delay — Conversion metrics lag clicks; detectors need lag-aware windows
  • Multi-tenant noise — One large seller or DSP can skew aggregates; use top-N contribution views

🎛️ Control Center (Shepherd) — Observability Hub

Role: Central dashboard correlating deployments, experiments, metrics, and alerts. Enables rapid incident RCA by timeline.

Features

  • Deployment Timeline — Code pushes logged with commit hash and version
  • Experiment Tracking — Experiment config, rampup percentage, impact metrics
  • Metric Dashboards — Pull from Prometheus; synced with deployment markers
  • Alert History — Time-correlated view of what fired when

Investigation Workflow

  • Alert fires on GMV drop at 14:32 UTC
  • Open Control Center timeline for past hour
  • See code rollout at 14:30 to API service
  • See experiment ramp at 14:15 on search ranking
  • Correlate with metric dips in graph overlay

Data Sources

  • ServiceNow — Code deployment records (codeChangeScrubber)
  • Kafka Metadata — Batch job start/end timestamps
  • Prometheus — Real-time metrics for trending
  • Elasticsearch — Error logs and event annotations

Requirements for an ads control center

A generic observability UI is not enough: monetization teams need a single narrative that ties what changed (code, config, experiment, data feed) to what broke (revenue, latency, quality) on a shared timeline. Below are requirements typical of a control center built for programmatic ads.

Product & UX

  • Unified timeline — Deployments, experiment ramps, config changes, and alerts on one axis (UTC)
  • Metric overlay — GMV, impressions, clicks, latency, error rate with zoom and comparison windows
  • RCA workspace — Attach incident ID, hypotheses, links to dashboards and queries
  • Role-aware views — SRE vs ads PM: same data, different default slices (service vs placement)

Technical & integration

  • Fresh markers — Deployment and experiment events within ~1 minute of ground truth
  • Queryable backends — Prometheus (or compatible TSDB), log index, change DB (ServiceNow / internal)
  • Audit trail — CAL-style log for who changed flags, budgets, or targeting (non-repudiation)
  • APIs — Machine-readable timeline for automation and postmortems

Reliability & safety

  • Availability — Control center itself must not be a SPOF during incidents; read-optimized
  • RBAC — Revenue-sensitive metrics and customer identifiers restricted
  • Correlation without false certainty — Show confidence; multiple overlapping changes are common

🧪 Touchstone — A/B Testing Framework

Role: Experimentation platform. Manages experiment configuration, bucketing, and real-time statistical analysis.

Core Components

  • Experiment Config — Treatment/control assignment, traffic split, ramp schedule
  • Bucketing Service — Deterministic assignment via user_id hash
  • Event Tagging — ET (placement) and XT (event) tags on impressions
  • Analysis Backend — Collects tagged events, runs t-tests, computes p-value

Experiment Lifecycle

  • Design — Define hypothesis, metric to track (GMV, clicks)
  • Ramp — Start at 1%; gradually increase to 100% if safe
  • Monitor — Real-time dashboards show impact vs. control
  • Decide — Statistical significance; rollout to 100% or cleanup

Statistical Framework

  • Delta Method — Estimate variance of treatment effect
  • Sequential Testing — Peek at results before full sample collected
  • p-value Threshold — Usually 0.05; p < 0.05 = statistically significant
  • Power Analysis — Pre-calculate sample size needed to detect effect

Operational Challenges

  • Multiple Comparisons — Running 100 experiments increases false positive rate
  • Network Effects — Treatment can affect control; coordination required
  • Seasonality Confounds — Weekend vs. weekday differences
  • Time-to-Significance — Large effects visible in hours; small effects need 2+ weeks

📋 ServiceNow — Change Management

Role: Change tracking system. codeChangeScrubber logs all code deployments for RCA correlation with metric anomalies.

Deployment Record Fields

  • Service Name — Which microservice was deployed
  • Version / Git Hash — Exact commit identifier
  • Timestamp — Deployment finish time (UTC)
  • Rollback Info — Previous version in case of quick rollback

Integration Points

  • codeChangeScrubber service reads Jenkins build logs
  • Writes record to ServiceNow upon successful deploy
  • Control Center queries ServiceNow for timeline view
  • Incident response uses deployment timeline for root cause

RCA Example

  • GMV drops 25% at 14:30 UTC
  • Check ServiceNow: API service deployed at 14:28
  • Query git for changes: buggy ranking algorithm
  • Rollback API to previous version; GMV recovers
