Monitoring Stack

Prometheus + Grafana

  • Revenue Dashboard — GMV, clicks, impressions, ROAS real-time
  • Service Health Dashboard — API latency (p50, p99), error rates, availability
  • Resource Dashboard — Pod CPU/Memory, disk I/O, network bandwidth
  • Database Health — ClickHouse query latency, Elasticsearch shard status, Kafka consumer lag
  • Custom Alerting — PromQL rules for revenue drops, latency spikes, error rate thresholds

Control Center (Shepherd)

  • Deployment Timeline — Visual markers for code pushes, services, versions
  • Experiment Ramps — Experiment config and traffic split over time
  • Metric Correlation — Overlay metrics on deployment/experiment timeline
  • Alert Timeline — When alerts fired, severity, resolution time
  • RCA Workbench — Link tickets, store findings, document remediation

Sherlock.IO

  • Anomaly Dashboard — Current alerts, historical patterns, baseline trends
  • Service Log Browser — Full-text search across Elasticsearch logs
  • Trending Errors — Error rates by service, error message clustering
  • Correlation Analysis — Which service fault correlates with revenue drop?
  • Predictive Alerts — Early warning if pattern looks like past incidents

Kubernetes Dashboard (Tess.io)

  • Pod Status — Running, pending, failed, restarting pods per service
  • Rolling Deployments — Progress of code rollout, ready replicas count
  • Node Status — CPU, memory, disk capacity per node
  • Crash Loop Detection — Alert if pod restarting frequently
  • Resource Quotas — Namespace limits; prevents one team starving others

🚨 Incident Response Playbook

SLA: L1 Infra and L2 Domain/QE must respond within 15 minutes of alert.

Phase 1: Alert & Triage (0-5 min)
• PagerDuty fires alert on threshold breach (GMV drop, click drop, latency spike)
• Slack notification with metric dashboard link and severity level
• On-call engineer acknowledges and begins investigation
• Open Control Center timeline for past hour to spot recent changes
Phase 2: Investigation (5-15 min)
• Check Sherlock for log anomalies and error patterns
• Review Control Center for recent deployments, experiments, or config changes
• Query Prometheus/Grafana for service-level metrics (latency, error rate, CPU)
• Check Kafka consumer lag; if high, possible data pipeline bottleneck
• Check Flink job status; if lagging or restarting, data delay likely
Phase 3: Diagnosis (15-30 min)
• Cross-check with multiple data sources (ClickHouse, Elasticsearch, Prometheus)
• Narrow to likely root cause: deployment, experiment, resource, or data
• Check CAL logs (Control Center Audit Log) for configuration changes
• Consult team chat/wiki for known issues or recent work on alert system
Phase 4: Remediation (30+ min)
• Rollback problematic code deployment
• Kill failed experiment; traffic ramps back to control
• Scale services up if resource-constrained
• Restart failed workers or batch jobs
• Monitor metrics to confirm recovery (usually 5-10 min lag before visible improvement)

📋 Post-Incident Review (RCA)

Documentation

  • Timeline — When alert fired, diagnosed, fixed, severity level
  • Root Cause — The specific code, config, or experiment change
  • Revenue Impact — Estimated lost GMV and ad impressions ($)
  • Duration — How long before full recovery

Analysis

  • Why Was It Missed? — Was there an alert? Did it fire?
  • Why Was Detection Slow? — Did MTTD (mean time to detect) meet SLA?
  • Why Was Resolution Slow? — Did MTTR (mean time to respond) meet SLA?
  • If Preventable? — What process/test/alert would have caught it?

Preventative Measures

  • New Alert Rule — Add threshold or pattern detector to catch similar issues
  • Test Addition — Unit test or integration test to prevent regression
  • Code Review Checklist — Require specific approval if code touches alert system
  • Monitoring Improvement — Add metric dashboards or log patterns

📊 Key Monitoring Metrics (SLA Targets)

Revenue Metrics

  • GMV — $ billed to sellers
  • Ad Revenue — $ collected from eBay
  • ROAS — GMV ÷ Revenue (monitors ad spend efficiency)
  • SLA Target: GMV variance < 5% per day

Engagement

  • Clicks — Direct ad interactions
  • Impressions — Ad views (tracked via JS pixel)
  • CTR — Click-Through Rate (Clicks ÷ Impressions)
  • SLA Target: CTR stable; alert if >30% swing

System Health

  • API Latency — p50, p99 response times
  • Error Rate — % requests failing
  • Service Availability — Uptime %
  • SLA Targets: p99 < 500ms, error < 1%, uptime 99.99%

Data Quality

  • Data Freshness — Lag between event generation and materialization
  • Reconciliation Gap — Discrepancy between sources
  • Schema Compliance — % events matching expected schema
  • SLA Targets: Lag < 5 min, gap < 2%, compliance > 99%
