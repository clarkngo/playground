eBay & Apache Spark — digest for discussion

Two public write-ups from eBay Innovation bracket almost a decade of Spark adoption: a 2014 introduction focused on why Spark and how jobs run on YARN, and a 2021 piece on a custom SQL-on-Hadoop engine built to replace a vendor analytics platform. Below: condensed facts, how the stories connect, and prompts for discussion.

Sources (primary):
  • Using Spark to Ignite Data Analytics — Scheibmeir, May 28, 2014
  • Explore eBay’s New Optimized Spark SQL Engine for Interactive Analysis — Ma, Li, Dhanpal, May 17, 2021

One arc, two eras

2014 — “Adopt & explain”

Spark as a parallel engine for large-scale analytics: RDDs keep iterative work in memory; at eBay, jobs commonly ran on Hadoop via YARN, reading and writing HDFS. Audience: engineers and analysts learning what Spark is for and how it sits next to Hive.

2021 — “Operate & optimize”

A production SQL service must match a legacy platform’s latency and scale after a 20+ PB migration. The post is about gateway architecture, governance, Delta-style mutability, and dozens of engine-level optimizations (caching, indexes, AQE, Parquet).

Article A — what to take away (2014)

  • Problem Spark solves: iterative analytics on huge datasets — keeping intermediate state in memory can be orders of magnitude faster than rereading from disk each iteration.
  • Deployment pattern: Spark on YARN: ApplicationMaster negotiates containers; executors run tasks against data in HDFS.
  • Scale snapshot (stated in 2014): clusters on the order of ~2k nodes, ~100 TB RAM, ~20k cores — useful as a historical sense of scale; today’s numbers will differ.
  • Language & libs: strong Scala usage; example of MLlib (e.g. K-means) over seller metrics in HDFS.
  • Hive vs faster SQL: Shark (Spark SQL predecessor era) reported roughly 5× faster than Hive for some workloads — illustrates the push toward interactive SQL on big data.

Article B — what to take away (2021)

  • Context: migration of >20 PB off a vendor platform onto in-house Hadoop; need for a SQL engine with speed, stability, and security comparable to the old tool.
  • Core stack: customized Spark SQL on Apache Spark 2.3.1; Spark Thrift Server on YARN; Hive metastore on a separate cluster; JDBC/ODBC gateway (Hive Thrift–compatible) for BI tools.
  • Governance: authentication (e.g. internal IdP + Kerberos), SQL GRANT/REVOKE, TLS, and no direct end-user HDFS access.
  • Product features: Delta Lake patterns for UPDATE/DELETE (including joins); bulk download API for very large result sets; volatile (session-scoped materialized) tables vs heavy temp views.
  • Performance themes: transparent SSD cache on a dedicated analytics cluster; Bloom-style indexes for Parquet; AQE backported and extended for skew; bucket alignment (merge / re-bucketing); Parquet read path optimizations; dynamic partition pruning coexisting with AQE; runtime filters.
  • Scale snapshot (stated in 2021): on the order of 1,200+ distinct users/day, 260k+ queries, 80% of queries under 27 seconds — a concrete SLA-oriented talking point.

How the two articles relate

Theme 2014 2021
Audience question What is Spark, and how do we run jobs? How do we run interactive SQL as a service at vendor-grade performance?
Execution model YARN + HDFS, batch/ML-oriented Long-lived Thrift server + pooled executors + shared metastore
SQL Hive comparison, Shark speedups Deep customization of Spark SQL + operational features (ACLs, exports, mutability)
Optimization focus In-memory RDDs, iterative algorithms Scan path, indexes, adaptive execution, caching, Parquet I/O

Discussion prompts

Use as openers or breakout questions. Cite which article supports each answer.

  1. Why would a company standardize on Spark on YARN + HDFS instead of only a warehouse SaaS product?
  2. The 2014 post emphasizes RDDs and memory. The 2021 post barely mentions RDDs. What shifted in how eBay used Spark?
  3. After migrating 20+ PB, why might “same SQL, new engine” still miss user expectations? What gaps did eBay need to close?
  4. Pick one optimization from 2021 (e.g. transparent cache, Bloom index, AQE + skew). What failure mode does it mitigate?
  5. Security vs usability: How do SQL GRANTs and “no raw HDFS” change the threat model compared to giving analysts cluster accounts?
  6. Volatile tables vs temp views: When does plan complexity matter more than storage cost?
  7. If you were introducing Spark 3/4 today, which 2021 workarounds (backporting AQE, DPP coexistence) are now “solved upstream”?
  8. How would you validate the 80% < 27s claim in your own org (measurement methodology, cohort bias)?
