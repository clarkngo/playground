Read Replica Sizing

📋 Scenario

An e-commerce platform generates 80,000 total RPS at peak with a 90% read / 10% write ratio. A single PostgreSQL instance handles 8,000 RPS at 70% CPU utilisation. Reads can be distributed across read replicas (which receive synchronous replication from one primary). Writes must all go to the primary. The team wants to know how many total database nodes are needed (primary + replicas), keeping each node below 70% utilisation.

📊 Given Values

Total Peak RPS
80,000
Read : Write Ratio
90 : 10
Node Max RPS
8,000
Max Utilisation
70%
Key Formulas: Read RPS = Total RPS × read% | Write RPS = Total RPS × write% | Replicas needed = ⌈Read RPS / (node capacity × util%)⌉ | Primary also handles all writes + some reads if under capacity | Total nodes = replicas + 1 primary

🧮 Step-by-Step Calculation

Step 1 — Total read RPS at peak
Formula: 80,000 RPS × 90%
RPS
Step 2 — Total write RPS at peak
Formula: 80,000 RPS × 10%
RPS
Step 3 — Effective RPS per node at 70% utilisation
Formula: 8,000 RPS × 0.70
RPS/node
Step 4 — Read replicas needed (round up)
Formula: ⌈Read RPS / effective RPS per node⌉
replicas
Step 5 — Write load on the primary as % of its capacity
Formula: (Write RPS / 8,000) × 100
%
Step 6 — Total database nodes (primary + replicas)
Formula: 1 primary + replicas from Step 4
total nodes
Step 7 — Spare read capacity across all replicas (RPS)
Formula: (replicas × effective RPS per node) − actual Read RPS
spare RPS

✅ Worked Solution

Read RPS = 80,000 × 0.90 = 72,000 RPS
Write RPS = 80,000 × 0.10 = 8,000 RPS
Effective/node= 8,000 × 0.70 = 5,600 RPS
Replicas = ⌈72,000 / 5,600⌉ = ⌈12.86⌉ = 13 replicas
Primary load = (8,000 / 8,000) × 100 = 100% → primary is fully loaded with writes
Total nodes = 1 + 13 = 14 nodes
Spare cap = (13 × 5,600) − 72,000 = 72,800 − 72,000 = 800 spare RPS
Engineer's Takeaway: Notice that the primary is at 100% write load — this signals the primary is a potential bottleneck. Real systems would combine a write-optimised primary with a message queue (async replication buffer) or switch to a write-scalable DB (Cassandra, DynamoDB) if writes continue to grow. The 13 replicas also leave only 800 spare RPS — minimal buffer for traffic spikes.
