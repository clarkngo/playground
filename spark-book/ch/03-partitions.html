Chapter 3 — Structured APIs

Partitions & Parallelism

A partition is the unit of parallelism in Spark. Too few and cores sit idle. Too many and scheduling overhead eats your gains. Drag the sliders below and watch the task distribution change in real time.

Key concepts
📁

Partition

A logical chunk of the dataset. Each partition becomes exactly one task per stage. Spark processes them in parallel, one per available core slot.

⚙

Task slots

Total slots = executors × cores per executor. If partitions > slots, tasks queue and run in waves. If partitions < slots, cores sit idle.

🌱

Skew

When one partition is 10× larger than others, one task runs long after the rest finish. The stage cannot complete until the last task does.

📊

Default: 200

spark.sql.shuffle.partitions defaults to 200. Often too many for small data (tiny files) and too few for very large shuffles.

Under- vs over-partitioned
Under-partitioned

1 partition, 16 cores

Only 1 task runs. 15 cores sit idle the entire time. The job takes the same time as a single-core run. Classic symptom: Spark UI shows 1 active task, stage never parallelizes.

Well-partitioned

2–4 × total cores

Tasks run in waves. Cores stay busy. Small tasks finish and pick up stragglers. Even if one partition is slightly large, others absorb the slack. Aim for 128–256 MB per partition as a starting point.

Over-partitioned

10,000 tiny partitions

Scheduler overhead dominates. Thousands of task metadata entries flood the Driver. Each tiny file read incurs HDFS/S3 latency. The job spends more time scheduling than computing.

After coalesce()

Merge before write

Writing 10,000 partitions creates 10,000 small output files. coalesce(N) reduces partition count without a full shuffle — use before write() to avoid the small-files problem.

Real-world use cases
Skew

Joining a skewed dataset

User IDs often follow a power-law distribution. A join on user_id sends 90% of records to one executor. Fix with salting: append a random suffix to the key, join, then aggregate.

Cloud

Right-sizing a Glue job

AWS Glue defaults to 200 shuffle partitions on a 10 DPU cluster (40 cores). For a 5 GB dataset that is 200 × 25 MB partitions — fine. For a 500 GB dataset, raise to 2000+.

Storage

S3 small-files problem

Writing 500 partitions to S3 Parquet means 500 files. Reading them back multiplies LIST and GET calls. Coalesce to ~128 MB target file size before writing to keep downstream reads fast.

Common pitfalls
⚠

repartition() vs coalesce()

repartition(N) does a full shuffle — use it to increase partitions or balance skew. coalesce(N) merges partitions without shuffle — use it only to decrease, typically before writing.

⚠

spark.sql.shuffle.partitions is global

The default 200 applies to every shuffle in the job. A job with a small first shuffle and a large second shuffle both get 200. Override per-DataFrame with df.repartition(N) instead.

⚠

Partition count does not equal parallelism

If you have 32 partitions but only 4 cores, tasks run in 8 sequential waves. True parallelism is min(partitions, totalCores). Adding more partitions past total cores only adds wave count.
