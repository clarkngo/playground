Chapter 2 — Spark Core Concepts

Lazy Evaluation & DAGs

Spark never runs a transformation immediately. It builds a Directed Acyclic Graph of work, then executes the whole plan at once when you call an action. Build the DAG below and watch what happens when you hit collect().

Key concepts
🕒

Lazy evaluation

Transformations like map() and filter() return a new RDD description — no computation happens yet.

📊

DAG

Spark records each transformation as a node in a graph. Edges show data dependencies. No cycles allowed.

⚡

Action triggers execution

collect(), count(), save() — calling any action kicks off the scheduler to execute the full DAG.

✂

Stage boundaries

Wide transformations (shuffle) split the DAG into stages. Each stage is fully pipelined; stages run sequentially.

Real-world use cases
Debug

Why nothing is running

New Spark users often build a long chain and wonder why it finished instantly. Lazy eval is why — you need count() or show() to trigger execution.

Optimize

Filter early, shuffle late

Because nothing runs until the action, Catalyst can reorder your transformations. Put filter() before groupByKey() and Spark may push it down even if you wrote it after.

Inspect

Read the DAG with explain()

Calling df.explain() prints the physical plan without executing it — lazy eval makes this possible. Use it to spot unexpected shuffles before the job runs.

Common pitfalls
⚠

groupByKey() vs reduceByKey()

Both are wide. But groupByKey() shuffles all values to the reducer, while reduceByKey() pre-aggregates on each partition first. On large data, groupByKey() can OOM executors.

⚠

Calling collect() on huge RDDs

collect() pulls everything to the Driver. Add it to your DAG here and watch the log. In production, prefer writing to storage over collecting.

⚠

Recomputation without caching

If you trigger two actions on the same RDD, Spark recomputes the full lineage both times. Call rdd.cache() or rdd.persist() before the first action to avoid this.
