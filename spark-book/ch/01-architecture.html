Chapter 1 — Apache Spark Fundamentals

Spark Architecture

A Spark job is a conversation between a Driver that plans, a Cluster Manager that allocates, and Executors that do the work. This animator lets you trace that conversation across three real-world scenarios.

Key components
🖥

Driver

Runs your main(). Holds the SparkContext, builds the logical plan, and coordinates all stages. One per application.

⚖️

Cluster Manager

YARN, Mesos, or Spark Standalone. Allocates containers/workers. The Driver negotiates with it for resources.

⚡

Executor

A JVM process on a worker node. Runs tasks in parallel, caches RDD partitions, and reports progress back to the Driver.

📦

Task

The smallest unit of work. One task per partition per stage. Executors run tasks concurrently up to their core count.

Real-world use cases
Batch

Ad-hoc analytics on HDFS

Data teams run SQL aggregations over terabytes of Parquet. Spark reads in parallel across partitions; Driver collects only the final result set.

Streaming

Kafka ingestion pipeline

Micro-batches of click events flow from Kafka into Delta Lake. Each batch is a mini Spark job — same Driver/Executor model, just triggered on an interval.

Cloud-native

Spark on Kubernetes

Kubernetes replaces YARN as the cluster manager. Executor pods spin up dynamically and are killed on job completion, enabling serverless-style billing.

Common pitfalls
⚠

Driver OOM on collect()

Calling collect() pulls all partitions to the Driver JVM. On large datasets this crashes the Driver. Prefer take(N) or write results to storage.

⚠

Executor memory vs. overhead

spark.executor.memory sets heap size, but the JVM also needs off-heap memory (spark.executor.memoryOverhead). Set total container = memory + overhead or YARN kills the container.

⚠

One executor per machine is not always optimal

Fat executors (all cores on one JVM) suffer from GC pauses. Lean executors (1 core each) waste HDFS caching. The sweet spot is 4–5 cores per executor with multiple executors per node.
