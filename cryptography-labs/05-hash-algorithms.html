Hash Algorithms & Password Security

SHA-256 avalanche effect, algorithm lifecycle, bcrypt vs raw hashing, and the birthday attack

Scenario: You're auditing a web application that stores user passwords as unsalted MD5 hashes. Your task is to understand why this is catastrophic, demonstrate the cryptographic properties that make good hash functions essential, and propose a secure alternative. Along the way you'll see how even a single bit change cascades through SHA-256.

📊 Demo 2 — Hash Algorithm Comparison

Click any algorithm row to see why it was deprecated or is recommended.

MD5
128-bit digest
Very Fast BROKEN ▼ details
Status: Broken — Do not use for any security purpose
First collision attack demonstrated 1996 (Dobbertin). Practical chosen-prefix collisions demonstrated 2004 (Wang et al). Used in the Flame malware (2012) to forge Windows Update signatures. A modern GPU can compute ~10 billion MD5 hashes/second. All stored MD5 password hashes are trivially crackable via rainbow tables or brute force.

Still used for: Non-security checksums (file integrity verification where collision resistance isn't needed), legacy systems that can't be updated.
SHA-1
160-bit digest
Fast DEPRECATED ▼ details
Status: Deprecated — Phase out immediately
Theoretical weaknesses known since 2005. The SHAttered attack (2017) by Google and CWI Amsterdam produced the first practical SHA-1 collision — two different PDF files with identical SHA-1 hashes. Cost was ~$100K in cloud compute. NIST deprecated SHA-1 for digital signatures in 2011; browsers dropped it for TLS certificates by 2017.

Migration path: SHA-1 → SHA-256 (drop-in for most uses), SHA-1 HMAC → HMAC-SHA-256.
SHA-256
256-bit digest
Moderate CURRENT ▼ details
Status: Current NIST standard — safe to use
Part of the SHA-2 family (FIPS 180-4). No known weaknesses. Collision resistance: 2128 operations. Used everywhere: TLS certificates, Bitcoin proof-of-work, code signing, HMAC-SHA-256, PBKDF2-SHA-256.

Quantum note: Grover's algorithm reduces effective security to 2128 — still infeasible. SHA-256 is considered quantum-safe for hash functions.
Use for: Digital signatures, MACs, key derivation (with PBKDF2/HKDF), integrity checks.
SHA-3 / Keccak
256-bit digest
Slower RECOMMENDED ▼ details
Status: Recommended — different design from SHA-2
Won NIST hash competition (2012). Based on the sponge construction (Keccak), fundamentally different from SHA-2's Merkle–Damgård construction. This diversity matters: if a weakness is found in SHA-2's design, SHA-3 provides a fallback.

Variants: SHA3-256 (drop-in for SHA-256), SHA3-512, SHAKE128/256 (variable-length XOF).
Best for: New protocol designs, post-quantum hybrid schemes, when algorithm diversity is required.

📐 How are these hash rates calculated?

MD5 rate — why so fast?

MD5 was designed in 1992 for speed. It runs entirely in integer arithmetic (32-bit rotates, XOR, additions) with no memory-hard operations. Modern GPUs execute thousands of threads in parallel, each computing a full MD5 hash independently. Benchmark tools like hashcat and John the Ripper measure real-world GPU throughput:

  • Laptop CPU (Core i7) — ~500 million MD5/sec: single-core throughput, no GPU parallelism
  • RTX 4090 — ~68 billion MD5/sec: 16,384 CUDA cores each hashing in parallel; measured via hashcat benchmark (-m 0)
  • 8× H100 cluster — ~800 billion MD5/sec: scales nearly linearly; H100 has ~67B per card × 8
  • Nation-State (1,000 GPUs) — ~100 trillion MD5/sec: 1,000 × RTX 4090-class cards running 24/7

bcrypt rate — why so slow?

bcrypt is intentionally slow. At cost factor 12, it runs 212 = 4,096 internal rounds of the Blowfish cipher. Each round expands a 4 KB P-array in memory, which:

  • Prevents GPU parallelism — GPU memory bandwidth becomes the bottleneck, not compute
  • Forces ~8 ms per hash on a laptop CPU and ~0.2 ms per hash on a GPU (still slow per thread)
  • Hashcat achieves only ~5,000 bcrypt/sec on an RTX 4090 — vs 68 billion MD5/sec: a 13,600,000× slowdown

The crack-time formula

keyspace = charset_size password_length
avg_crack_time = keyspace ÷ hash_rate ÷ 2
÷ 2 because on average you find the password halfway through the search space

Character set sizes used here: lowercase (26) · uppercase (+26) · digits (+10) · special chars (+32). A password using all four has a charset of 94 — so an 8-char mixed password has 948 ≈ 6 quadrillion combinations.

🎂 Demo 4 — Birthday Attack Simulator

We simulate a collision in a 16-bit hash space (65,536 possible values). The birthday paradox predicts a collision after ~√65536 = 256 attempts on average.

📐 Formula: For an n-bit hash, collision resistance = 2n/2 operations (not 2n). SHA-256 needs 2128 operations to find a collision — infeasible with classical computers.
Why this matters for SHA-256: With a 256-bit output, an attacker needs 2128 ≈ 3.4×1038 hash computations to find a collision. Even at 1018 hashes/second, that would take 1013 years — longer than the age of the universe.

Which hash property guarantees that given a hash output, you cannot efficiently find the original input?

📚 The Three Hash Security Properties
  • Preimage resistance (one-way): Given H(x), cannot find x. This is what protects passwords.
  • Second-preimage resistance: Given x, cannot find x′ ≠ x such that H(x) = H(x′).
  • Collision resistance: Cannot find any two inputs x ≠ x′ where H(x) = H(x′). Required for digital signatures — attacker can't substitute a different document with the same hash.
  • Avalanche effect: A property of the function design (small input change → ~50% bit flip), not a formal security property.
  • Key stretching (bcrypt, PBKDF2): a technique to make hash computation slow, not a hash property itself.
