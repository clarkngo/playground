💡 Why 3 tiers? Root CAs are kept offline (air-gapped) in HSMs for maximum security. Intermediate CAs do the day-to-day signing. If an intermediate is compromised, it's revoked — the root CA stays safe and issues a new intermediate.

🔍 Demo 3 — Certificate Revocation: OCSP vs CRL

🎯 Why This Matters — Revocation exists because private keys get stolen. The choice between OCSP (real-time, privacy risk) and CRL (cached, potentially stale) is a security vs performance trade-off you will encounter in every PKI deployment.

Check both methods to understand how certificate revocation works in the real world.

When a certificate is compromised, revoked, or expired, the browser cannot verify it simply by checking the embedded expiration date — the public key might be stolen, the CA might have issued it fraudulently, or the organization might no longer control the domain. Browsers need real-time revocation status. CRL and OCSP are the two mechanisms.
—
📋 CRL (Certificate Revocation List)

What it is: The CA publishes a signed list of revoked certificate serial numbers, updated periodically (typically every 7–30 days). Browsers download the entire list and check if your cert's serial is on it.

Pros: Simple, no server query needed, works offline
Cons: Large file (Google Chrome CT log CRL is >80 MB), browsers cache stale data up to 24h, wastes bandwidth for every browser
⚡ OCSP (Online Cert Status Protocol)

What it is: The browser sends a small query to the OCSP responder (operated by the CA) asking "is this cert revoked?" The responder replies immediately with the current status — no list download needed.

Pros: Real-time, minimal bandwidth, up-to-date revocation info
Cons: Privacy leak (CA knows which sites you visit), OCSP responder downtime = validation failure
OCSP Stapling: Server pre-fetches & caches OCSP response, sending it with the certificate — browser doesn't need to query, privacy is protected

⚠️ Certificate Attack Scenarios
Rogue CA Attack
Attacker compromises a CA and issues a fraudulent certificate for google.com. CT logs make this detectable — Google's Chrome enforcement of CT means uncertified certificates fail immediately. DigiCert/Symantec distrust (2017–2018) was discovered via CT.
MITM with Valid Cert
Attacker obtains a valid certificate (via social engineering the CA, or domain validation bypass). Defense: HPKP (deprecated), CAA DNS records restricting which CAs can issue for your domain, CT monitoring with immediate revocation.
Wildcard Cert Abuse
A *.example.com certificate covers ALL subdomains including internal ones (admin.example.com, vpn.example.com). If the wildcard cert private key is stolen, all subdomains are compromised. Mitigation: use individual SAN certs for sensitive subdomains, not wildcards.
Certificate Pinning Bypass
Mobile apps pin a specific certificate or public key. Attackers use tools like Frida or Objection to hook the TLS verification function at runtime and bypass pinning. Defense: multi-layered pinning, integrity attestation, jailbreak/root detection.

During TLS, a client receives a certificate for 'bank.com'. The intermediate CA was recently compromised. Which mechanism MOST effectively prevents trust in this certificate?

📚 Certificate Revocation & Trust
  • CT + Revocation (B): When a CA is compromised, all certificates it issued must be revoked. CT logs make the mis-issuance visible, and OCSP/CRL revocation removes trust. This is the correct defense-in-depth answer.
  • Pinning alone (A): Would not help — if the attacker has the compromised intermediate, they could issue a new certificate that satisfies the pin if it was pinned to the intermediate rather than a specific key.
  • Checking root (C): Incorrect — the root signature on the intermediate may still be valid. The intermediate itself is what's compromised.
  • Not Before date (D): Irrelevant to compromise — a cert issued before the compromise date appears fully valid.
