Secure Cryptographic Implementation

Timing attacks, key derivation functions, implementation mistakes gallery, and key lifecycle

Scenario: A code review reveals your application uses == to compare HMAC tokens, MD5 for password hashing, and a hardcoded encryption key in source code. This lab walks through each of these classes of implementation error — and the fixes — that separate "uses cryptography" from "uses cryptography securely."

⏱️ Demo 1 — Timing Side-Channel Attack

🎯 Why This Matters — Timing side-channels show how algorithms can leak information through execution time even when the algorithm itself is mathematically sound. This class of attack found real vulnerabilities in RSA, AES, and MAC verification in production systems.

An early-exit comparison leaks information about how many characters match. See the timing difference.

❌ VULNERABLE: Early-exit comparison
function insecureCompare(a, b) { if (a.length !== b.length) return false; for (let i = 0; i < a.length; i++) { // Returns IMMEDIATELY on first mismatch // → leaks how many chars match! if (a[i] !== b[i]) return false; } return true; }
✅ SECURE: Constant-time comparison
function secureCompare(a, b) { if (a.length !== b.length) return false; let diff = 0; for (let i = 0; i < a.length; i++) { // XOR accumulates — always runs all chars // → same time regardless of match position diff |= a.charCodeAt(i) ^ b.charCodeAt(i); } return diff === 0; }

⚠️ The insecure version takes measurably longer for guesses sharing more prefix characters with the secret. After thousands of requests, attackers can statistically recover the secret character by character. Real-world example: Lucky 13 (2013) — timing attack on TLS CBC padding oracle.

🔑 Demo 2 — Key Derivation Functions Comparison

🎯 Why This Matters — Password databases get stolen regularly. The difference between SHA-256 (cracks in seconds on a GPU) and Argon2id (takes years) is entirely the KDF. This demo shows exactly why algorithm choice determines whether a breach becomes catastrophic.
⚡ Attacker Hardware:
Laptop CPU (Intel i7) — Single-core, ~1,200 PBKDF2 attempts/sec
PBKDF2
bcrypt
Argon2id
HKDF

PBKDF2 applies a pseudorandom function (HMAC-SHA-256) repeatedly, making brute-force expensive. NIST SP 800-132 now recommends ≥600,000 iterations.

FIPS 140-3 Approved ✅ · Use PBKDF2-SHA-256 with ≥600,000 iterations and 16+ byte salt for federal systems.

bcrypt uses Blowfish cipher with a cost factor that doubles work per increment. Includes automatic salting. Widely used but NOT FIPS-approved.

NOT FIPS-approved ⚠️ · Blowfish is not a NIST-approved algorithm. Cannot be used in FIPS 140-3 validated modules. Use PBKDF2 or Argon2 for federal compliance.

Argon2id won the Password Hashing Competition (2015). Memory-hard design defeats GPU/ASIC attacks. Recommended for new applications.

Argon2id(password, salt, time=3, memory=64MB, parallel=4)
→ Memory required: 64 MB per hash attempt
→ GPU efficiency: severely reduced (can't parallelize memory)
→ ASIC resistance: high (memory bandwidth limited)
→ Attacker GPU speed: ~100–1,000 Argon2/sec (vs 10B MD5/sec)
→ FIPS status: not yet standardized (OWASP recommends it)
Argon2id is the OWASP #1 recommendation for password hashing. Combines Argon2i (side-channel resistant) and Argon2d (GPU resistant).

HKDF (HMAC-based Extract-and-Expand KDF) is for key material, NOT passwords. No work factor — fast by design. Used in TLS 1.3 key schedule.

Step 1 — Extract:
  PRK = HMAC-SHA256(salt, IKM)
  → PRK is a pseudorandom key of fixed length

Step 2 — Expand:
  OKM = T(1) ‖ T(2) ‖ … where T(i) = HMAC-SHA256(PRK, T(i-1) ‖ info ‖ i)
  → Derive multiple keys from one master secret

Use cases: TLS 1.3 session keys, signal protocol ratchet, ECDH → AES key
⚠️ Do NOT use HKDF for passwords — it's too fast, no work factor

A developer uses PBKDF2 with 1,000 iterations and SHA-1 to hash passwords for a federal system. What are the TWO main problems?

📚 PBKDF2 Requirements (NIST SP 800-132)
  • SHA-1 is deprecated: Not approved for new cryptographic uses under FIPS 140-3. SHA-256 or SHA-512 must be used for PBKDF2-HMAC in federal systems.
  • 1,000 iterations is far too low: NIST SP 800-132 (2023 update) now recommends ≥600,000 iterations for PBKDF2-SHA256. At 1,000, a modern GPU can test millions of password guesses per second.
  • PBKDF2 itself IS FIPS-approved when using SHA-2 — option B is wrong about PBKDF2 not being FIPS-approved.
  • PBKDF2 CAN use SHA-1 technically — the problem is that SHA-1 is deprecated, not that it's incompatible.
