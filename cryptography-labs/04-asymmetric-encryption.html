Asymmetric Encryption & Secure Protocols

Key exchange, RSA, digital signatures, hybrid encryption, and TLS — how the internet stays secure

Developed by Clark Ngo

Scenario: You're building a secure messaging platform. Your users need to communicate privately — but they've never met and can't share a secret key in advance. You need key exchange without a pre-shared secret, message encryption, tamper-proof signatures, and a secure transport channel. This lab walks through every piece of that puzzle.

🎨 Diffie-Hellman Key Exchange

🎯 Why This Matters — Diffie-Hellman solves the fundamental key distribution problem: how do two parties agree on a secret key over a public channel? This mathematical breakthrough (1976) enables all secure internet communication without requiring a pre-shared secret.

DH allows two parties to establish a shared secret over a public channel — without ever sending that secret. The classic analogy uses paint mixing: mixing colors is easy, but separating them is nearly impossible.

🔑 RSA Fundamentals

🎯 Why This Matters — RSA's trapdoor function — easy to compute, hard to invert without the private key — underpins most public-key infrastructure. Understanding the math shows why key size matters and what it actually means to break RSA computationally.

RSA relies on the difficulty of factoring large numbers. This demo uses small primes so you can follow the math — real RSA uses primes with 1024+ digits.

Key Generation (p=17, q=11):

n = p × q = 17 × 11 = 187 (public modulus)
φ(n) = (p-1)(q-1) = 16 × 10 = 160 (Euler's totient)
e = 7 (public exponent, gcd(7,160)=1)
d = 23 (private exponent, 7×23=161≡1 mod 160)
Public key: (e=7, n=187) · Private key: (d=23, n=187)

  3. Watch m = cd mod n — decrypting with the private exponent (d=23)

Why RSA works: Anyone with the public key (e, n) can encrypt. Only the holder of the private key (d, n) can decrypt — because computing d from (e, n) requires factoring n, which is computationally infeasible for large primes.
⚠️ RSA in practice: Never encrypt data directly with RSA. Use RSA to encrypt a random symmetric key (AES), then encrypt data with that AES key (hybrid encryption).

✍️ Digital Signatures

🎯 Why This Matters — Signatures prove both identity and integrity simultaneously — they cryptographically bind a message to the specific private key owner. Without signatures, anyone could impersonate a server, forge software updates, or tamper with financial documents.

A digital signature proves authenticity (who sent it) and integrity (it hasn't changed). Using the same RSA keys: Alice signs with her private key; anyone with her public key can verify.

🔀 Hybrid Encryption

🎯 Why This Matters — RSA cannot efficiently encrypt large data; symmetric ciphers cannot solve key distribution. Hybrid encryption (RSA wraps an AES key, AES encrypts data) combines the best of both. This is the actual architecture used by TLS, PGP, and SSH.

RSA is too slow to encrypt large data directly. Real systems use hybrid encryption: RSA to securely exchange a random AES session key, then AES to encrypt the actual data.

TLS uses this exact pattern: The TLS handshake uses RSA or ECDH to establish a shared session key, then all subsequent traffic is encrypted with AES-GCM using that session key. This gives you RSA's security properties at AES's speed.

🤝 TLS 1.3 Handshake

🎯 Why This Matters — TLS 1.3 is the synthesis of everything in this course: asymmetric crypto for authentication and key exchange, symmetric for bulk data, AEAD for authenticated encryption, and Diffie-Hellman for forward secrecy — all in under 1 round trip.

🎲 Randomness & Entropy

🎯 Why This Matters — Cryptography fails completely if random numbers are predictable. The Debian OpenSSL bug (2008) shows what happens when entropy fails — every key generated on affected systems was compromised. os.urandom() is not interchangeable with Math.random().

Every cryptographic operation depends on unpredictable randomness. Weak random number generation has broken real-world systems — including RSA key generation on embedded devices.

❌ Weak Entropy (PRNG)
Seeded from system time → predictable
DUAL_EC_DRBG (NSA backdoor, 2007)
Debian OpenSSL bug (2008) — only 32,767 possible keys generated
Android Bitcoin wallets (2013) — k reuse in ECDSA
✅ Strong Entropy (CSPRNG)
OS-level: /dev/urandom, CryptGenRandom
Hardware: Intel RDRAND, TPM chips
Python: secrets.token_bytes(32)
Never use Math.random() for crypto!

⚠️ Why Math.random() is unsafe for cryptography

  • It's a PRNG, not a CSPRNG — output is fully deterministic once the internal seed is known; there's no unpredictability guarantee
  • Predictable future outputs — observing a dozen values lets an attacker reverse-engineer the seed and predict every future "random" number
  • No hardware entropy — crypto.getRandomValues() harvests OS/hardware noise (CPU timing jitter, interrupt events, hardware RNG); Math.random() does not
  • Real-world failures:
    • Debian OpenSSL 2008 — a single-line patch accidentally reduced entropy to just the process ID, leaving at most 32,767 distinct RSA keys
    • Android Bitcoin wallets 2013 — weak PRNG reused the ECDSA nonce k, which directly exposes the private key via a simple equation
  • Safe alternatives: crypto.getRandomValues() (JS/browser) · secrets module (Python) · SecureRandom (Java) · /dev/urandom (Linux)

💡 Why it matters — asymmetric crypto in the wild
  • HTTPS everywhere — TLS uses ECDH key exchange + AES-GCM encryption + RSA/ECDSA certificates for every secure website.
  • Signal Protocol — Uses a "Double Ratchet" combining DH key exchange + AES + HMAC for forward secrecy in every message.
  • Code signing — Software updates are digitally signed; your OS verifies the signature before installing — preventing supply-chain attacks.
  • SSH — Uses RSA/ED25519 public key authentication; your private key never leaves your machine.
