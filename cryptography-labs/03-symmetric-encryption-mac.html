Symmetric Encryption & Message Authentication

AES cipher modes, HMAC authentication, and why authenticated encryption matters

Scenario: You're a security engineer at a fintech startup processing thousands of transactions per second. You need to choose the right AES mode for encrypting transaction data and ensure messages haven't been tampered with in transit. The wrong choice could expose customer data — or let an attacker silently modify transaction amounts.

🔏 HMAC Message Authentication

🎯 Why This Matters — Encryption alone does not prevent tampering. HMAC adds integrity — without it, attackers can flip bits in ciphertext and produce valid-looking but corrupted plaintext, as the Padding Oracle demo below demonstrates.

Encryption hides data — but it doesn't prove the data hasn't been altered. A Hash-based Message Authentication Code (HMAC) binds message + secret key into a tag. Any change to the message produces a completely different tag.

💡 Try changing the dollar amount (e.g. $500 → $200, $1000) and watch how the HMAC tag changes completely. Then run the Tamper Attack to see detection in action.

🛡️ AES-GCM: Authenticated Encryption

🎯 Why This Matters — GCM solves both problems at once: encryption and authentication in a single pass. This is why TLS 1.3 mandates only AEAD modes — it prevents an entire class of attacks by design, eliminating the need to separately manage a MAC.

GCM mode combines encryption + authentication into one pass, producing a ciphertext and a 128-bit authentication tag. Any modification to the ciphertext immediately invalidates the tag.

⚡ Bit-Flip Attack on GCM Ciphertext

An attacker flips a single bit in the ciphertext (byte index 3, mask 0xFF). Unlike CBC, GCM catches this immediately — decryption is rejected entirely.

💡 GCM vs CBC comparison

  • CBC alone — encrypts but doesn't authenticate. Bit flips corrupt plaintext silently.
  • CBC + HMAC — secure but requires two separate operations (encrypt-then-MAC order matters!).
  • AES-GCM — single-pass AEAD. Any modification invalidates the tag. Used in TLS 1.3, Signal, SSH.

⚠️ Padding Oracle Attacks on CBC

🎯 Why This Matters — The padding oracle attack shows how a seemingly harmless error message ("invalid padding") can leak the entire plaintext over repeated queries. This real-world attack (POODLE, Lucky 13) motivates why authenticated encryption is not optional.

When a server reveals whether CBC padding is valid separately from whether decryption succeeded, an attacker can decrypt any ciphertext — one byte at a time — without knowing the key.

By sending modified ciphertexts and observing "padding valid / invalid" responses, the attacker learns one plaintext byte per ~128 requests. For a 16-byte block, that's ~2048 requests — easily automated. Real attacks: POODLE (SSLv3), BEAST (TLS 1.0), Lucky13 (TLS CBC timing).

Defense: Use AES-GCM (no padding needed). If you must use CBC, apply encrypt-then-MAC and return identical errors for padding failures and MAC failures — never distinguish between them.

💡 Why it matters — real-world incidents
  • Adobe (2013) — Used AES-ECB for password storage. 153M encrypted passwords leaked; identical passwords were visible as identical ciphertexts.
  • POODLE (2014) — Forced SSLv3 downgrade exploited CBC padding oracle to decrypt HTTPS session cookies.
  • Lucky13 (2013) — Timing side-channel in TLS CBC padding check allowed plaintext recovery. Fixed by migrating to GCM.

Modern guidance: use AES-256-GCM for new systems. Always authenticate your ciphertext.
