IPsec, TLS 1.3 & Perfect Forward Secrecy

Tunnel vs Transport mode, IKEv2 key exchange, TLS 1.2 vs 1.3 differences, and VPN protocol comparison

Scenario: Your organization's VPN was found to be using TLS 1.2 with static RSA key exchange. An incident report suggests an adversary has been recording encrypted traffic for years. Now you need to understand what data is at risk (hint: Perfect Forward Secrecy), compare IPsec and TLS architectures, and recommend a modern protocol stack.

💡 ESP vs AH: ESP (Encapsulating Security Payload) provides encryption + optional authentication. AH (Authentication Header) provides authentication only — no encryption. In practice, ESP with authentication is almost always used. AH cannot traverse NAT (it authenticates the IP header, which NAT changes).

A company uses TLS 1.2 with RSA key exchange (no ECDHE). An attacker records encrypted traffic. Three years later the server's private key is compromised. What is the outcome?

📚 Why Static RSA Breaks Perfect Forward Secrecy
  • TLS 1.2 RSA key exchange: Client generates a pre-master secret, encrypts it with the server's RSA public key, sends it. The server decrypts with its private key. Session keys are derived from this pre-master secret.
  • The threat: An attacker recording this traffic has the RSA-encrypted pre-master secret. Once they steal the private key, they decrypt it → derive all session keys → decrypt all past traffic.
  • ECDHE (PFS): Each session generates a fresh ephemeral key pair. The private key is discarded after the session. Even with the server's long-term private key, the attacker cannot reconstruct the ephemeral session key.
  • TLS 1.3 mandates ECDHE for exactly this reason — PFS is not optional.
