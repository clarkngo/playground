Module 6 — Architecture

Layered Software Architecture

Why This Matters
The Problem

When business logic lives in the UI, or the UI talks directly to the database, the system becomes tightly coupled. Every change ripples everywhere, making testing and refactoring extremely costly.

The Solution

Layered (clean/hexagonal) architecture enforces that dependencies point inward. The UI depends on the application layer, which depends on domain interfaces, which are implemented by infrastructure. This makes each layer independently testable.

Real-World Use

Domain-Driven Design (DDD), Clean Architecture (Robert Martin), and Hexagonal Architecture all use this pattern. It is the foundation of most enterprise Java, .NET, and Python frameworks.

Your Goal

Understand why the direction of dependencies matters, and how inverting data access through interfaces allows you to swap databases or mock infrastructure without touching business logic.

The Objective: You are designing the layer structure of a production-grade software application. Sequence the layers from the outermost user-facing interface all the way to the database and external services at the infrastructure boundary.

Think about: Which layer talks to the user? Which layer is purely business logic with no infrastructure dependencies? What abstraction separates domain logic from database implementation? Watch out for anti-patterns disguised as layers.

€desktop;💻 Presentation Layer
User-facing layer (React, Angular, HTML forms). Receives input, displays output. Should contain NO business logic.
💡 This is always the outermost layer, closest to the user.
⚙Application Layer
Orchestrates use cases. Knows what needs to happen but not how. Calls domain objects and coordinates responses.
💡 Use cases live here, not in the UI.
🏛Domain Layer
Pure business logic. No imports from infrastructure layers. The most stable, innermost ring.
💡 Domain rules should be expressible without knowing whether you are using MySQL or MongoDB.
📄Repository Interface
An interface (or abstract class) defined in the domain layer that describes data operations in domain terms (findById, save).
💡 The interface belongs to the domain; the implementation belongs to infrastructure.
🗃Data Access Layer
Implements the Repository Interface using actual database technology (Hibernate, SQLAlchemy, Prisma). Only this layer knows about SQL or ORM specifics.
💡 Implementation details live here, separated from the contract.
🖥Database
The persistent store. Accessed only through the Data Access Layer. Never directly from domain or presentation code.
💡 The database is infrastructure -- keep it at the boundary.
🌐External Services
Third-party APIs, email services, payment processors. Called through adapters defined in the application layer.
💡 External services are also infrastructure, similar to the database.
