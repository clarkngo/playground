Module 9 — Microservices

Microservices System Design

Why This Matters
The Problem

A monolith that grows too large becomes impossible to deploy safely or scale independently. One team blocks another, and a single bug can take down the entire application.

The Solution

Microservices decompose the application into independently deployable services. An API Gateway routes requests, a Service Registry enables discovery, and a Message Broker decouples event-driven communication.

Real-World Use

Netflix, Uber, and Amazon all use microservice architectures. AWS App Mesh, Consul, and Kafka implement the service registry and message broker layers at cloud scale.

Your Goal

Understand the key infrastructure components that make microservices viable: gateway, discovery, async messaging, database isolation, caching, and observability.

The Objective: You are designing the core infrastructure for a microservices-based system. Sequence the components from the external entry point down through service discovery, individual services, async communication, data isolation, caching, and observability.

Think about: How does an external client know which service to call? How do services communicate asynchronously without tight coupling? Why does each service need its own database? Watch out for decoys that belong to monolithic architectures.

🔐API Gateway
The single entry point for all external traffic. Routes requests to the correct microservice, enforces auth, handles rate limiting, and abstracts the internal service topology from clients.
💡 External clients always talk to the gateway, never directly to individual services.
📌Service Registry
A directory where services register their network addresses and health status. The gateway and other services query the registry to discover where to send requests (e.g., Consul, Eureka).
💡 Services must be discoverable before they can be called.
⚙️Individual Microservices
Small, independently deployable services (Order Service, User Service, Payment Service). Each owns its domain logic and data. Deployed and scaled independently of other services.
💡 Services run after the gateway routes and the registry resolves the address.
🔌Message Broker
An async event bus (Kafka, RabbitMQ) that decouples services from each other. Services publish events; other services subscribe. No direct service-to-service calls for non-critical paths.
💡 The broker sits between services and their downstream consumers.
🗃Per-Service Database
Each microservice owns its own database schema or instance. No shared database between services. This enforces loose coupling and allows each service to choose its own storage technology.
💡 Database-per-service is a core microservices pattern that prevents tight coupling at the data layer.
⚡Distributed Cache
A shared in-memory cache (Redis, Memcached) that services read before hitting their databases. Reduces latency and database load for frequently accessed data.
💡 Caching sits between services and their databases to reduce redundant reads.
📊Observability Stack
Distributed tracing, centralized logging, and metrics dashboards (Jaeger, ELK, Prometheus/Grafana). Essential for debugging in a distributed system where a single request spans multiple services.
💡 Observability is the final layer that monitors everything running beneath it.
