Overview
Real-time systems guarantee that computations complete within defined time bounds — not just fast, but predictably fast. A missed deadline can mean a dropped call or a plane crash, depending on the application class.
🧠

RTOS Kernels

Specialized operating system kernels that schedule tasks with bounded, deterministic latency. Examples: FreeRTOS, VxWorks, QNX Neutrino, Zephyr. The kernel is the heart of any real-time system.

📐

Scheduling Algorithms

Mathematical frameworks for deciding which task runs when. Rate-Monotonic Scheduling (RMS) and Earliest Deadline First (EDF) are the two foundational approaches with proven schedulability bounds.

🔩

Embedded Hardware

Microcontrollers (MCUs) and microprocessors designed for real-time workloads. ARM Cortex-M (bare-metal/RTOS) and Cortex-R (hard real-time with ECC) are the dominant architectures.

🛡️

Safety Standards

Certification frameworks governing software in life-critical systems: IEC 61508 (functional safety), DO-178C (avionics), ISO 26262 (automotive), IEC 62443 (industrial). Compliance is mandatory, not optional.

🔌

Communication Buses

Deterministic fieldbus and network protocols: CAN (automotive), LIN (low-speed automotive), FlexRay (ADAS), ARINC 429/664 (avionics), EtherCAT and TSN (industrial Ethernet).

🛠️

Development Tools

Cross-compilers (GCC, LLVM, IAR, Green Hills MULTI), JTAG/SWD debuggers, logic analyzers, WCET analysis tools (AbsInt aiT), and hardware-in-the-loop (HIL) test rigs.

Key Terminology
Essential vocabulary for real-time systems engineering — from scheduling theory to hardware constraints.
Determinism Core Concept ▼
A system is deterministic when the same input always produces the same output within the same time bound, regardless of other system activity. This is the defining property of real-time systems — not just correctness, but temporal correctness. A non-deterministic system may occasionally miss deadlines, which is acceptable for soft RT but catastrophic for hard RT.
Hard Real-Time System Classification ▼
A system where missing any deadline is catastrophic — the failure has consequences more severe than not completing the task at all. Examples: airbag controllers, pacemakers, fly-by-wire flight control. The system must be proven to never miss a deadline under any load scenario, typically via schedulability analysis.
Soft Real-Time System Classification ▼
A system where missing a deadline degrades performance or quality but is not catastrophic. Examples: video streaming (a late frame causes a glitch), audio playback, user interfaces. The system optimizes for meeting deadlines but can tolerate occasional misses gracefully.
Firm Real-Time System Classification ▼
Between hard and soft. A missed deadline renders the result useless (it is discarded), but missing it is not actively harmful. Example: a financial trading system that must process a market tick within 50 ms — a late result is ignored, not acted upon incorrectly.
RTOS (Real-Time Operating System) Core Technology ▼
An operating system designed to service requests within guaranteed time bounds. Key differences from general-purpose OSes: fully preemptive kernel, bounded interrupt latency, priority-based scheduling with no unbounded priority inversions, and deterministic memory allocation. Examples: FreeRTOS, VxWorks, QNX Neutrino, Zephyr, RTEMS.
WCET (Worst-Case Execution Time) Timing Analysis ▼
The maximum time a task can take to execute under any input and hardware state. WCET analysis is the foundation of schedulability proofs — you cannot guarantee deadlines without knowing WCET. Measured via static analysis tools (AbsInt aiT, Bound-T) or safe over-approximation on hardware with predictable pipelines. Caches and branch predictors make WCET analysis extremely difficult on modern out-of-order CPUs.
Latency Timing ▼
The delay between an event occurring and the system responding to it. In real-time systems, interrupt latency (time from interrupt assert to first instruction of ISR) and scheduling latency (time from task becoming ready to task running) are the two critical latency figures. Both must be bounded and small.
Jitter Timing ▼
The variation in timing of a recurring event or task execution. A task that should run every 1 ms but sometimes runs at 0.95 ms and sometimes at 1.05 ms has 50 µs of jitter. Low jitter is critical in control systems (motor control, audio) and network time-sensitive applications. General-purpose OSes have high jitter due to non-deterministic scheduling.
Preemption Scheduling ▼
The ability of the scheduler to interrupt a running lower-priority task and immediately switch to a higher-priority task that has become ready. Full preemption is essential for meeting deadlines in hard real-time systems. Without it, a high-priority task must wait for the current task to voluntarily yield — an unbounded and unacceptable delay.
Context Switch Scheduling ▼
The process of saving the CPU state (registers, program counter, stack pointer) of the currently running task and restoring the state of the next task. Context switch time is a key RTOS benchmark — typical values range from a few hundred nanoseconds (bare-metal MCU) to a few microseconds (Linux). This time directly adds to scheduling latency.
ISR (Interrupt Service Routine) Hardware Interface ▼
A function that executes immediately when hardware signals an interrupt (e.g., timer tick, UART byte received, GPIO edge). ISRs must be as short as possible — they block all lower-priority interrupts. The best practice is to do minimal work in the ISR (read a register, set a flag, post a semaphore) and defer processing to a task.
Priority Inversion Hazard ▼
A scheduling anomaly where a high-priority task is effectively blocked by a lower-priority task holding a shared resource (mutex). A medium-priority task can preempt the low-priority task, causing the high-priority task to wait indefinitely. The Mars Pathfinder mission (1997) experienced this bug. Solutions: Priority Inheritance Protocol (PIP) or Priority Ceiling Protocol (PCP) — both implemented in POSIX mutexes and RTOS mutexes.
Mutex / Semaphore Synchronization ▼
Synchronization primitives for protecting shared resources. A mutex (mutual exclusion) is owned by one task at a time and supports priority inheritance. A semaphore is a signaling mechanism (counting or binary) used to coordinate producer-consumer relationships. In real-time systems, both must have bounded acquisition time to maintain determinism.
Watchdog Timer Safety Mechanism ▼
A hardware timer that resets the system if not periodically "kicked" (reset) by the software. If the application hangs, deadlocks, or enters an infinite loop, the watchdog fires and forces a safe restart. Both hardware watchdogs (MCU peripheral) and software watchdogs (RTOS task monitoring) are used in safety-critical systems.
Tick / System Clock Timing ▼
The periodic interrupt that drives the RTOS scheduler. Common tick rates: 1 kHz (1 ms per tick) for FreeRTOS defaults, 100–1000 Hz for Linux. Tasks with periods shorter than one tick require tickless modes or hardware timers. Tickless (dynamic tickless) kernels suppress idle ticks to reduce power on battery-constrained MCUs.
RMS (Rate-Monotonic Scheduling) Scheduling Theory ▼
A static-priority scheduling algorithm where higher-rate (shorter period) tasks get higher priority. Proven optimal among fixed-priority algorithms by Liu and Layland (1973). The schedulability bound: a set of n periodic tasks is schedulable if total CPU utilization U does not exceed n(2^(1/n) - 1), which approaches ~69.3% as n grows. Simple to implement, widely used in safety-certified systems.
EDF (Earliest Deadline First) Scheduling Theory ▼
A dynamic-priority scheduling algorithm where the task with the nearest absolute deadline runs next. EDF is optimal: it can schedule any task set that is theoretically schedulable (utilization up to 100%). The drawback is complexity in implementation and catastrophic behavior at overload — when overloaded, EDF misses deadlines unpredictably, whereas RMS degrades more gracefully. Less common in safety-critical systems due to certification complexity.
POSIX.1b Real-Time Extensions Standard ▼
IEEE standard (1993) extending POSIX for real-time applications. Adds: real-time signals, POSIX timers (timer_create), priority scheduling (SCHED_FIFO, SCHED_RR), semaphores (sem_open), shared memory, message queues, and memory locking (mlockall). QNX Neutrino is fully POSIX.1b compliant; Linux supports it via pthreads and the rt library.
Time-Triggered Architecture Design Pattern ▼
A design where all task activations are driven by a global clock, not by events. Tasks execute in predetermined time slots — no task can interfere with another. FlexRay and TT-Ethernet use this model. Extremely predictable and analyzable, but inflexible. Contrast with event-triggered systems, which respond to stimuli — more efficient but harder to analyze for WCET.
Hypervisor / Partitioning Architecture ▼
A software layer that runs multiple operating systems (partitions) on one processor with hardware isolation. In avionics, ARINC 653 defines space and time partitioning: each partition gets exactly its allocated CPU time and cannot access other partitions memory. Real-time hypervisors (Wind River Hypervisor, QNX Hypervisor, Xen with RT extensions) allow a certified RTOS to share a chip with an Linux infotainment stack — common in modern vehicles.

A separation kernel RTOS used in the most security-sensitive environments: NSA-evaluated, Common Criteria EAL6+ certified. Used in military avionics, secure communications, and nuclear plant controls where formal verification is required.

LynxOS / LynxSecure
POSIX-compliant RTOS and separation hypervisor by Lynx Software Technologies. Common in military avionics and space applications. LynxSecure provides hardware-enforced partitioning for mixed-criticality systems.

Open-Source RTOS
FreeRTOS (Amazon)
The most widely deployed RTOS on microcontrollers. MIT-licensed, extremely lightweight (kernel fits in ~6 KB Flash). Runs on 40+ MCU architectures. Amazon maintains it as FreeRTOS with AWS IoT integrations. Ideal for resource-constrained embedded systems where cost matters more than certification.
IoT / MCU
Zephyr RTOS (Linux Foundation)
A modern, modular RTOS backed by Intel, Nordic Semiconductor, NXP, and Google. Designed for connected IoT devices with a native Bluetooth and 802.15.4 stack. Growing safety certification story (IEC 61508 SIL 2). Increasingly used where FreeRTOS was previously default.

The PREEMPT_RT patch set (now partially mainlined) converts Linux into a soft/firm real-time OS by making most kernel code preemptible. Core Metrics
How real-time systems are measured, characterized, and proven correct. These metrics appear in datasheets, design reviews, and certification audits.
MetricDefinitionBenchmark / Notes
Interrupt Latency Time from hardware interrupt assertion to first instruction of the ISR executing. Bare-metal MCU: <1 µs. RTOS with critical section: 1–10 µs. Linux PREEMPT_RT: 50–200 µs. Hard RT systems target single-digit µs.
Context Switch Time Time to save current task state and restore next task state, measured from last instruction of outgoing task to first instruction of incoming task. FreeRTOS on Cortex-M4: ~1–3 µs. VxWorks: ~2–5 µs. Linux: ~5–20 µs with PREEMPT_RT.
WCET (Worst-Case Execution Time) Upper bound on how long a task can run, across all inputs and system states. Must be provably safe, not just measured. Measured via static analysis tools (AbsInt aiT) or safe measurement-based bounds. Must be less than task period minus blocking time for schedulability.
Jitter Variation in task start time or period from one instance to the next. A task scheduled every 1 ms that sometimes starts at 0.98 ms and sometimes at 1.03 ms has 50 µs of jitter. Industrial motor control: <10 µs jitter required. Audio systems: <1 µs (or sample-rate jitter causes audible artifacts). EtherCAT achieves <1 µs network jitter.
CPU Utilization Ceiling Maximum safe CPU utilization for a task set under RMS: n(2^(1/n) - 1). For large n this approaches ~69.3%. A task set using more than ~70% CPU under RMS is not guaranteed schedulable. EDF allows up to 100% but at overload risk. Safety margins typically target <60% utilization.
Deadline Miss Rate Fraction of task activations that fail to complete before their deadline. For hard RT this must be 0; for soft RT it is a design parameter. Hard RT: 0% — any miss is a failure. Soft RT: system designers define acceptable miss rates (e.g., <0.01% for video decode). Monitoring requires hardware performance counters or RTOS trace tools.
Stack Usage (HWM) Maximum stack depth reached by a task. Expressed as high-water mark (HWM). Stack overflow is undefined behavior on most MCUs and will corrupt adjacent memory silently. FreeRTOS: uxTaskGetStackHighWaterMark() returns remaining free words. Typical practice: allocate 2x measured HWM, verify in system test. Static stack analysis tools (PC-lint, StackAnalyzer) provide formal bounds.
Schedulability Whether a task set can be proven to always meet all deadlines given worst-case execution times and periods. A binary property: schedulable or not. Proven via utilization bound tests (RMS) or response-time analysis (RTA). RTA is more accurate but more complex. Safety-critical systems require a formal schedulability proof in the design documentation.

Common Workflows
Three foundational runtime patterns every real-time systems engineer must understand deeply.

Preemptive Task Scheduling Cycle

The core loop of a preemptive RTOS — how multiple tasks share one CPU without any task monopolizing it beyond its WCET.
1
Timer Tick Interrupt
The hardware timer fires at the system tick rate (e.g., 1 kHz). The RTOS ISR is invoked. Tick counter incremented; sleeping tasks whose delay has expired are moved from blocked to ready state.
2
Scheduler Runs
The RTOS scheduler inspects the ready queue and selects the highest-priority ready task. If it is different from the currently running task, a context switch is triggered.
3
Context Switch
CPU registers (including stack pointer and program counter) of the outgoing task are saved to its Task Control Block (TCB). The incoming task TCB registers are restored to the CPU. Execution resumes at exactly the point the incoming task was last preempted.
4
Task Executes Within WCET
The selected task runs. If a higher-priority task becomes ready mid-execution (e.g., due to an ISR posting a semaphore), the scheduler immediately preempts the current task and switches again.
5
Task Blocks or Completes
Task calls a blocking RTOS API (e.g., vTaskDelay, xSemaphoreTake) or completes its current activation. It returns to the blocked or ready queue. The scheduler selects the next highest-priority ready task and the cycle repeats.

ISR → Deferred Processing (Bottom-Half Pattern)

The canonical pattern for handling hardware interrupts in real-time systems without blocking the ISR for extended periods.
1
Hardware Event Fires
A sensor, timer, or peripheral asserts an interrupt line. The CPU finishes the current instruction, saves minimal state (PC, PSR on Cortex-M via hardware), and vectors to the ISR.
2
ISR — Minimal Work Only
The ISR reads the critical hardware register (e.g., received byte from UART FIFO), clears the interrupt flag, and immediately signals a waiting task via a semaphore or task notification. ISR returns in microseconds. No processing, no memory allocation, no blocking calls.
3
Deferred Handler Task Unblocks
The handler task, which was blocked waiting on the semaphore, becomes ready. If it has the highest priority among ready tasks, the RTOS immediately preempts the current task (yield from ISR) and runs the handler.
4
Process Data in Task Context
The handler task processes the data — parse a packet, run a PID control loop, write to a ring buffer. Running in task context means it can block, call OS services, and be preempted by even higher-priority tasks. The ISR is free to fire again.
5
Output or Forward
Processed result is written to an output queue, sent over a bus, or used to update actuator state. Task blocks again waiting for the next semaphore signal. Total response time (ISR to output) must be provably within the application deadline.

Safety-Critical Boot Sequence & Watchdog Validation

How a safety-critical embedded system transitions from power-on to normal operation with all integrity checks passed.
1
Power-On Reset & Boot ROM
Hardware reset de-asserts. Boot ROM (mask-programmed, immutable) runs. It verifies the bootloader signature using a hardware public key stored in OTP fuses. Failed verification halts boot — no way to proceed with untrusted code.
2
Bootloader — Self-Test & Init
Bootloader runs CPU built-in self-test (BIST), verifies RAM via march test patterns, validates application flash CRC/hash. Initializes clocks, watchdog timer (with short timeout), and minimum peripherals. Watchdog must be kicked quickly or it resets the system.
3
RTOS Initialization
Application image loaded. RTOS kernel initializes scheduler data structures, creates all tasks and queues. Tasks are not yet running. Watchdog period extended to application-level timeout.
4
Application Self-Test
Before entering normal operation, all critical subsystems run POST (power-on self-test): sensor calibration checks, actuator range tests, CRC verification of calibration data in NVM. Failed tests set a fault flag and enter a safe state (limp mode) rather than normal operation.
5
Normal Operation & Watchdog Supervision
RTOS scheduler starts. A dedicated watchdog task (highest-priority or separate MCU) periodically verifies all critical tasks are alive and executing within expected timing. Only when all tasks check in does it kick the hardware watchdog. Any hung task causes a supervised system reset to safe state.
Trends & Challenges
The forces reshaping real-time systems engineering in the 2020s — from new silicon architectures to the collision of AI and determinism.
🔓
RISC-V in Real-Time
The open RISC-V ISA is entering safety-critical domains. SiFive, Andes, and Bosch are developing RISC-V cores for automotive (Bosch AURIX successors) and space. FreeRTOS and Zephyr already support RISC-V. The challenge: no established safety-certified toolchains yet — compiler qualification for DO-178C/ISO 26262 is ongoing.
🔀
Mixed-Criticality Systems
Running safety-critical (ASIL D) and non-critical (QM) software on the same chip using hypervisors. Automotive next-gen zone controllers combine AUTOSAR Classic RT control with Linux ADAS stacks on one SoC (e.g., Qualcomm SA8xxx, Renesas R-Car). The engineering challenge: proving the ASIL D partition is unaffected by the Linux side.
🌐
TSN — Time-Sensitive Networking
IEEE 802.1 TSN brings deterministic timing to standard Ethernet, replacing proprietary fieldbuses like PROFIBUS and CANopen. TSN enables sub-1 ms latency with <1 µs jitter on standard Ethernet switches. Automotive Ethernet (100BASE-T1) + TSN is the backbone of next-gen vehicle networks. Industrial TSN is displacing EtherCAT in new designs.
🤖
AI Inference on the Edge
Running neural network inference in real-time embedded systems (object detection in ADAS, anomaly detection in industrial PLCs). The tension: neural nets are inherently non-deterministic in execution time due to data-dependent operations, making WCET analysis nearly impossible. Industry workaround: dedicated NPU hardware with bounded execution on fixed-topology networks.
🏛️
Certification Complexity & Cost
DO-178C DAL A certification for avionics software costs $1,000–$10,000 per line of code when including qualification of tools, development data, and test evidence. ISO 26262 ASIL D is similarly expensive. As systems grow in complexity (autonomous vehicles have 100M+ lines of code), the economics of full certification are forcing new approaches: model-based development, formal verification, and incremental certification.
☁️
Cloud-Connected Real-Time
Industrial IoT and connected vehicles require real-time embedded software to coexist with cloud connectivity. The architectural pattern: an RTOS core handles hard RT control; a Linux partition manages OTA updates, telemetry, and cloud APIs over TLS. The hard challenge is security — the cloud-connected partition must not compromise the certified RT partition.
Market Dynamics & Monetization
The economics of the real-time systems ecosystem — from RTOS licensing to safety certification as a revenue moat.
Pain Points
💸

Certification Cost

Safety certification dominates project budgets. DO-178C DAL A costs $1K–$10K per source line. ISO 26262 ASIL D adds months of documentation, testing, and third-party auditing. Small teams building safety-critical products often spend more on certification than on engineering.

🔒

Toolchain Lock-In

Switching RTOS vendors mid-project is nearly impossible. Certified toolchains (qualified compilers, RTOS safety manuals) are tightly coupled to specific versions. A project that certifies with IAR + VxWorks cannot switch to GCC + FreeRTOS without recertifying — a multi-year, multi-million-dollar effort.

📏

Memory & Resource Constraints

MCU-class systems still operate with 256 KB Flash and 64 KB RAM. Dynamic memory allocation is often forbidden in safety-critical code (MISRA C Rule 21.3). Engineers must statically size all buffers, task stacks, and queues at design time — an increasingly difficult constraint as system complexity grows.

🔄

Priority Inversion Bugs

Priority inversion is subtle, intermittent, and devastating. It only manifests under specific task scheduling scenarios that may not appear in testing but surface in production. The Mars Pathfinder experience (1997) is the canonical warning: the bug caused resets 18 minutes into the mission. Detection requires specialized RTOS trace tools.

🏚️

Legacy Porting

Aerospace and automotive systems have 20–40 year lifecycles. Software written for VxWorks 5.x in the 1990s must eventually move to modern hardware while maintaining certification equivalency. The porting cost, retesting burden, and re-certification effort are enormous — many programs choose to keep aging hardware flying rather than port.

Evolution & Foundations
From the first preemptive operating systems to modern safety-certified hypervisors — the 60-year arc of real-time systems.
Historical Timeline
1961

First Preemptive OS — CTSS

MIT Computation Center Timesharing System introduces preemptive scheduling, allowing the computer to interrupt running programs. This foundational concept — that the OS controls task scheduling rather than the task controlling the OS — underlies every RTOS designed since.

1973

Liu & Layland — RMS Paper

C. L. Liu and James W. Layland publish "Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment" in the Journal of the ACM. This paper establishes Rate-Monotonic Scheduling and provides the first rigorous mathematical foundation for real-time schedulability analysis. Still directly cited in avionics certification documents today.

1988

VxWorks 1.0 — Wind River

Wind River Systems releases VxWorks, the first commercial RTOS to gain widespread industry adoption. Its deterministic preemptive kernel, POSIX compatibility, and networking stack make it the standard for aerospace and defense embedded software throughout the 1990s and 2000s. It remains in active use in new programs today.

1993

POSIX.1b Real-Time Standard

IEEE ratifies POSIX.1b (formerly POSIX.4), standardizing real-time extensions: priority scheduling (SCHED_FIFO), real-time signals, timers, semaphores, and shared memory. This allows real-time applications to be written portably across RTOS platforms that claim POSIX compliance — a critical step toward software reuse in certified systems.

1995

QNX Neutrino — Microkernel RTOS

QNX Software Systems (later acquired by Blackberry) releases Neutrino, a microkernel RTOS where even device drivers run as user-space processes. A crash in a driver cannot corrupt the kernel. This architectural approach becomes the dominant model for automotive-grade RTOS, and QNX grows to run in 195M+ vehicles by 2024.

2003

FreeRTOS Goes Open Source

Richard Barry releases FreeRTOS under a modified GPL license (later MIT). Its tiny footprint (~6 KB), zero licensing cost, and ARM Cortex-M support drive massive adoption on microcontrollers. Amazon acquires FreeRTOS in 2017 and adds AWS IoT integration, making it the most widely deployed RTOS in the world by unit volume.

2012

PREEMPT_RT Matures — Linux Gets Real

The PREEMPT_RT patch set, developed by Thomas Gleixner and Ingo Molnar over a decade, reaches production maturity. Linux with PREEMPT_RT achieves sub-200 µs worst-case latency on x86, making it viable for soft/firm real-time in industrial and telecom applications. In 2021, core PREEMPT_RT changes are merged into Linux mainline.

2017

Zephyr RTOS — Linux Foundation

The Linux Foundation launches Zephyr as an open-source, Apache 2.0-licensed RTOS for connected IoT and embedded systems. Backed by Intel, Nordic Semiconductor, NXP, and Google, Zephyr integrates native Bluetooth, Wi-Fi, and 802.15.4 stacks with a modular architecture. It is now the primary open-source challenger to FreeRTOS in the IoT and wireless sensor space.

Foundational Works
WorkAuthor / YearWhy It Matters
Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment Liu & Layland / 1973 Establishes Rate-Monotonic Scheduling (RMS) and provides the utilization bound. The mathematical foundation of real-time scheduling theory. Every real-time systems engineer must understand this paper.
Hard Real-Time Computing Systems (Buttazzo) Giorgio Buttazzo / 1997 (3rd ed. 2011) The definitive textbook covering task models, scheduling algorithms (RMS, EDF, DMS), resource sharing protocols (PCP, PIP), aperiodic servers, and multiprocessor scheduling. The graduate-level reference for real-time systems courses worldwide.
POSIX.1b-1993 (IEEE Std 1003.1b) IEEE / 1993 Standardizes real-time OS interfaces (scheduling policies, timers, semaphores, signals). Enables portable real-time application code across compliant RTOS platforms. The lingua franca of commercial RTOS APIs.
IEC 61508 — Functional Safety of E/E/PE Systems IEC / 1998 (Ed. 2: 2010) The parent safety standard for electrical, electronic, and programmable electronic safety systems. Defines Safety Integrity Levels (SIL 1–4) and the V-model development lifecycle. IS0 26262 (automotive) and IEC 62304 (medical) are derivative standards. Compliance is mandatory in most industrial and safety-critical domains.
DO-178C — Software Considerations in Airborne Systems RTCA / 2011 The governing standard for avionics software certification. Defines Development Assurance Levels (DAL A–E), required software lifecycle data, and verification objectives. DAL A software requires 100% decision coverage and has no known safety defects. Compliance is required by the FAA and EASA for any software controlling flight-critical functions.
AUTOSAR Classic & Adaptive Specification AUTOSAR Consortium / 2003–present Defines the standard software architecture for automotive ECUs. AUTOSAR Classic standardizes the RTOS (OSEK/VDX-based), communication stacks (COM, PDU Router), and hardware abstraction for body control and powertrain ECUs. AUTOSAR Adaptive (POSIX-based, C++14) targets ADAS and connected vehicle high-compute platforms. Nearly every automotive ECU shipped today uses some layer of AUTOSAR.
