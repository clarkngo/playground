Database Sharding

When a single database can't hold all your data, you shard — split the dataset horizontally across multiple databases, each responsible for a partition of the keyspace. Drag the Year slider to watch your data grow and see new shards get added automatically. Sharding is painful to do later — get the plan right upfront.

🔑 Hash Sharding

Apply a hash function to the shard key (e.g., user_id % N). Distributes data evenly but makes range queries across shards impossible. Best for random access by ID.

shard = hash(user_id) % num_shards
📏 Range Sharding

Split by key ranges (A–M on shard 1, N–Z on shard 2). Enables efficient range queries but risks hot spots — all users whose names start with 'A' hitting one shard.

if user_id < 1B → shard_1 else → shard_2
🗺️ Directory Sharding

A lookup table maps each key to a specific shard. Most flexible — you can move data freely. But the directory itself becomes a bottleneck and single point of failure.

shard = lookup_table[user_id]
