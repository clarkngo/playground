Rate Limiting Algorithms

Rate limiting protects your API from abuse and prevents cascading failures — but the algorithm you choose determines how your system behaves under bursts. A token bucket absorbs spikes gracefully. A fixed window has a critical boundary exploit. A leaky bucket smooths all traffic to a constant rate. Configure the traffic pattern and watch each algorithm respond differently.

📐 Algorithm Comparison Guide

Algorithm Burst Handling Memory Boundary Issue Best For
Token Bucket ✅ Allows controlled bursts O(1) None APIs, most common use cases. Used by AWS, Stripe.
Fixed Window ⚠️ 2× burst at boundaries O(1) Yes — boundary spike Simple counters where exact accuracy isn't critical.
Leaky Bucket 🔵 Smooths all to constant rate O(1) None Protecting downstream services from any spike.
Sliding Window Counter ✅ Smooth, approximated O(1) None Production APIs. Used by GitHub, Cloudflare.
Sliding Window Log ✅ Perfectly accurate O(requests) None Low-volume APIs requiring exact enforcement.
Implementation note: In distributed systems (multiple API servers), all algorithms require a shared store like Redis for coordination. Redis supports INCR + EXPIRE for fixed windows, and sorted sets (ZRANGEBYSCORE) for sliding window logs. Token bucket state (current tokens) can be stored as a Redis float with a timestamp.
