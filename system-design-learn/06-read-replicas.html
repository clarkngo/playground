Read Replicas & Database Scaling

Most applications read far more than they write. Reads can be served by any up-to-date copy of the data. Read replicas are database copies that follow the primary and serve only reads — letting you multiply read capacity horizontally while writes still go to one place. ⚠️ Replication Lag

Replicas are not perfectly in sync with the primary. Asynchronous replication means there's a lag (typically 10–200 ms). If a user writes data and immediately reads it, they might hit a replica that hasn't received the write yet — this is called read-your-own-writes inconsistency. Solutions: sticky sessions, routing reads to primary for 500ms after a write, or synchronous replication (expensive).

📈 When Replicas Stop Working

Read replicas scale reads but NOT writes. If your write rate grows (more users posting, higher write percentage), the primary becomes the bottleneck. At that point, you need sharding — splitting the dataset horizontally across multiple primary nodes. Each shard handles a subset of keys/users and has its own replica set.
