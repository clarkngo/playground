📖 Concept Overview

Evals (evaluations) are the discipline of systematically measuring agent quality. Unlike traditional software where correctness is binary (tests pass or fail), agent outputs are often probabilistic, context-dependent, and partially correct. Evals provide structured frameworks for measuring quality across multiple dimensions: does the agent accomplish the task? Is its reasoning sound? Does it stay within budget? Does it behave safely?

Tracing is the observability layer — recording exactly what the agent did, when, at what cost, and with what outcome. A trace is like a flight data recorder for your agent: if something goes wrong, you can replay the exact sequence of LLM calls, tool invocations, token counts, and latency measurements. Without tracing, debugging production agent failures is essentially impossible — you're trying to understand a complex dynamic system with no data.

Together, evals and tracing enable the agent development flywheel: define success criteria (evals), run agents against a test suite, trace the failures, identify patterns, improve the agent (better prompts, better tools, better logic), and run evals again. This systematic improvement cycle is what separates production-quality agents from demos that work once.

📊 Eval Methodologies
✅ Deterministic assertions

Exact checks: "Did the agent create a file called output.json?", "Does the response contain the word 'error'?", "Did the agent call fewer than 5 tools?". Fast, cheap, reliable. Best for: structural requirements, format validation, safety checks that must never fail.

🤖 LLM-as-judge

A separate (often stronger) LLM scores the agent's output on a rubric: correctness, completeness, helpfulness (1–5). Flexible, can handle open-ended tasks, but adds latency and cost. Best for: subjective quality dimensions that can't be expressed as exact checks.

👤 Human evaluation

Human raters score agent outputs on quality dimensions. Gold standard for final quality assessment. Expensive and slow. Best for: establishing ground truth baselines, validating LLM-judge accuracy, high-stakes domains (medical, legal).

📈 Trajectory evaluation

Evaluate the agent's process, not just its final output. Did it take the most efficient path? Did it avoid unnecessary tool calls? Did it correctly identify and recover from errors? Process quality often predicts future generalization better than final-answer quality.

🔍 Reading a Waterfall Trace
  1. Identify the span types
    Each horizontal bar is a "span" — a unit of work with a start time and duration. LLM calls (purple) show where the model was thinking. Tool calls (blue) show external actions. Errors (red) show failures. The trace timeline reads left-to-right chronologically.
  2. Find the critical path
    The span that ends latest determines the total latency. If two spans overlap on the timeline, they ran in parallel. The sequential chain from start to the rightmost point is the critical path — the sequence you must optimize to reduce overall latency.
  3. Look for retries and errors
    Retry spans appear as repeated blocks for the same operation. A cluster of retries followed by a success means a transient failure was handled. A cluster ending in a terminal error is a bug. The observation before a retry (what the agent saw) often reveals the root cause.
  4. Calculate per-component costs
    Each LLM span has a token count. Sum input tokens × price/M + output tokens × price/M for each span. Tool calls have their own costs (API fees, compute time). The cost breakdown by component reveals where budget optimizations have the most impact.
  5. Correlate trace patterns with eval scores
    The most powerful insight comes from comparing traces of high-scoring vs. low-scoring runs. Do failing runs have more retries? Longer LLM spans (more tokens, slower reasoning)? Different tool call sequences? Pattern-matching across many traces reveals systematic agent weaknesses.
💡
The eval test suite: treat agents like software

The best agent teams maintain a regression test suite — a set of representative tasks with ground-truth expected outputs. Every agent change (new prompt, new tool, new model version) is run against the full suite before deployment. This catches regressions that human intuition misses: a prompt change that improves task A may silently break task B.

✅
Start with failure analysis, not success optimization

When building evals, first classify your failure modes: what does the agent get wrong? How often? Under what conditions? This is more actionable than measuring average success rate. A 90% success rate with 10% catastrophic failures is much worse than 80% success with all failures being minor.

📐 Designing a Scoring Rubric
✔️ Correctness (0–100)

Did the agent accomplish the primary objective? For code tasks: do the tests pass? For research tasks: are the facts accurate? Correctness is usually the highest-weight criterion — an incorrect answer that's efficient and safe is still wrong.

📋 Completeness (0–100)

Did the agent address all parts of the task? A response that correctly answers one sub-question but ignores two others scores poorly on completeness. Use a checklist of required outputs and score one point per item delivered.

⚡ Efficiency (0–100)

Did the agent accomplish the task with minimal wasted steps? Penalize unnecessary tool calls, excessive retries, and bloated responses. Efficiency matters for cost and latency at scale. A correct answer using 10× more tokens than necessary is a problem.

🛡️ Safety (0–100)

Did the agent stay within appropriate boundaries? Did it avoid leaking sensitive data, executing dangerous commands, or taking irreversible actions without confirmation? Safety is often a binary gate — a 0 here should disqualify the run regardless of other scores.

🪤 Common Pitfalls
Optimizing the eval, not the agent

If you tune the agent heavily against a small fixed eval set, it will score well on that set but fail in production. Fix: Maintain a held-out test set never used during development. Continuously add new eval cases from production failures.

P50 hiding P95/P99 failures

Average success rate looks great, but 5% of runs are catastrophic. Users remember their worst experience. Fix: Always report P95 and P99 metrics alongside P50. Treat tail failures with the same urgency as average performance issues.

Tracing without sampling strategy

Tracing every LLM call in production generates enormous amounts of data and cost. Fix: Sample traces (100% for errors, 10% for slow runs, 1% for normal runs). Use structured logging with consistent correlation IDs to enable cross-request debugging.

✅ Key Takeaways
→
You can't improve what you don't measure. Evals are not optional for production agents — they're the feedback signal that drives every improvement. Define success criteria before writing a single line of agent code.
→
Traces are your debugging superpower. When an agent fails in production, a complete trace gives you the exact sequence of calls, inputs, and outputs to understand why. Without it, you're guessing.
→
Safety is a gate, not a criterion. An agent that passes safety checks 99% of the time has a 1% chance of serious harm. Safety failures should immediately fail the run, regardless of correctness or efficiency scores.
→
The eval flywheel is the competitive moat. Teams that systematically run evals, trace failures, and improve based on data outpace teams that rely on intuition. Invest in eval infrastructure early — it compounds over time.
