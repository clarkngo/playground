📖 Concept Overview

  
The context window is an LLM's working memory — everything the model can "see" at once. It includes the system prompt, the full conversation history, tool definitions, tool results, and any documents that have been loaded. Modern models range from 8K tokens (≈6,000 words) to 1M+ tokens (≈750,000 words), but cost and latency scale with window size.

  
For short tasks, the context window is sufficient — the whole conversation fits comfortably. For long-running agents (debugging a large codebase, processing a legal document, running a multi-day research project), the window fills up. When the limit is hit, something must be dropped. The truncation strategy determines what gets kept and what gets lost — and a poor strategy can cause the agent to "forget" critical earlier context.

  
Memory is the broader system beyond the immediate context window. It includes: in-context memory (what's in the window right now), external memory (a vector database or file system the agent can query), episodic memory (summaries of past sessions), and semantic memory (facts extracted from prior interactions). Real production agents layer multiple memory systems to achieve reliable long-horizon behavior.






  
⚙️ Truncation Strategies Explained

  

    

      
🪟 Sliding Window

      
Keep the most recent N tokens. Drop the oldest messages when the window fills. Simple and predictable, but the agent loses all memory of early context — which may include the original task description or critical decisions. Best for: short, stateless tasks where recent context is all that matters.

    

    

      
📝 Summarization

      
When the window fills, call the LLM again to summarize the oldest portion of the conversation. The summary replaces the original text. Slower (requires an extra LLM call) but preserves semantic content much better than truncation. Best for: long conversations where the gist of early context matters.

    

    

      
🔍 RAG (Retrieval-Augmented Generation)

      
Store all past interactions in a vector database. Before each LLM call, retrieve the top-K most semantically relevant chunks and inject them into the context. The context stays small; memory is effectively unlimited. Best for: knowledge-heavy agents that need to recall specific facts from a large history.

    

    

      
🗜️ Selective Retention

      
Classify each message by importance (system prompt = keep always; user goals = keep; intermediate tool results = compress; raw file contents = drop after processing). Priority-based retention keeps the highest-value content. Best for: complex agents with heterogeneous context types.

    

  






  

    
💡

    

      
Token counting: what actually uses space?

      
In a typical agent conversation, the token breakdown is approximately: System prompt (5–15%), Tool definitions (10–20%), Conversation history (20–40%), Tool results / file contents (30–60%). Tool results — especially raw file reads or search results — are the biggest context consumers. Compressing them (extracting only the relevant parts) is usually the highest-leverage optimization.

    

  

  

    
⚠️

    

      
"Lost in the middle" problem

      
Research shows LLMs perform worst at recalling information placed in the middle of a long context — they reliably remember the beginning and end but lose track of content in between. This is critical for agent design: put the most important instructions at the start and end of the context, not buried in the middle.

    

  






  
🏗️ Building a Memory Architecture

  
    
    
  1. 
      
    
        
    In-context (working memory)
    
        
    The active context window. Everything currently available to the LLM. Fast (no retrieval needed) but finite. Manage carefully: compress tool results, drop completed sub-task history, keep the goal and constraints always visible.
    
      
    
    
    2. 
    
  2. 
      
    
        
    External memory (vector store / file system)
    
        
    Documents, code files, past conversation summaries stored outside the model. Retrieved on demand via embedding similarity search. The agent queries: "Find past conversations about X" and gets relevant chunks injected into context. Enables unlimited long-term memory.
    
      
    
    
    3. 
    
  3. 
      
    
        
    Episodic memory (session summaries)
    
        
    At the end of each session, generate a structured summary: what the user asked for, what was accomplished, what's still pending, what was learned. Store these summaries and inject them at the start of future sessions. The agent "remembers" past work without replaying full transcripts.
    
      
    
    
    4. 
    
  4. 
      
    
        
    Semantic memory (fact extraction)
    
        
    Extract stable facts from interactions — user preferences, project constraints, domain-specific terminology — and store them in a structured knowledge base. Unlike episodic memory (what happened), semantic memory stores what is true. Inject the most relevant facts into every session's system prompt.

🌍 Real-World Context Management

  

    
🤖 Claude Code — compact command summarizes context; /clear resets; CLAUDE.md persists project memory

    
🧠 MemGPT — explicit paging: "main context" + "archival memory" with explicit load/save

    
🔍 Cursor AI — codebase indexing + RAG to retrieve relevant code snippets per query

    
📚 NotebookLM — sources stored externally; retrieved per question with citations

  






  
✅ Key Takeaways

  

    

      
→

      
The context window is finite and precious. Every token you put in the context is a token of attention the model spends. Waste less on raw data; spend more on reasoning and goals.

    

    

      
→

      
No single strategy fits all tasks. Short tasks → sliding window. Long conversations → summarization. Knowledge-intensive agents → RAG. Most production agents combine all three.

    

    

      
→

      
The "lost in the middle" problem is real. Put your most critical instructions at the start (system prompt) and repeat them at the end if they're essential. Don't bury key constraints in the middle of a long history.

    

    

      
→

      
Memory is a system, not a feature. Long-horizon agents need layered memory: in-context for immediate work, external stores for past knowledge, episodic for session continuity, semantic for stable facts.
