Code execution is a superpower for agents — it grounds them in reality. Each iteration the agent sees real stdout/stderr and can self-correct, something pure language models cannot do.
📖 Concept Overview

Code execution is one of the most powerful capabilities an agent can have. Instead of reasoning about what code would produce, the agent can actually run code and observe the real output. This closes a critical loop: hypotheses about code behavior can be verified empirically rather than inferred. The result is an agent that can debug, analyze data, generate visualizations, run tests, and build software with real feedback at each step.

Code execution requires a sandbox — an isolated environment where code runs safely, without access to the host system's sensitive files, network services, or credentials. The sandbox enforces resource limits (CPU time, memory, network access) and captures stdout, stderr, and exit codes. This output is then injected back into the agent's context as the "observation" that drives the next reasoning step.

The power of code execution emerges through iteration. The agent writes code, runs it, sees an error, reads the error, writes a fix, runs again. This loop can repeat dozens of times autonomously. Crucially, errors become information rather than failures — they tell the agent exactly what went wrong and where. An agent with code execution converges to correct solutions through empirical feedback in a way that no amount of static reasoning can match.

🔒 Sandboxing Architecture
🐳 Container isolation (Docker)

Each execution spawns a fresh container. Strong isolation, reproducible environment, no state leakage between runs. Overhead: ~500ms startup. Used by: Devin, E2B, most production code execution APIs. Ideal for untrusted or user-submitted code.

⚡ In-process sandbox (Pyodide/Deno)

Python or JS runs inside the agent process using WebAssembly or V8 isolates. Near-zero startup time. Limited syscall access provides some isolation. Used by: ChatGPT Code Interpreter (Pyodide variant), browser-based agents. Fast but weaker isolation.

🖥️ VM snapshot

Execution restores to a known-good VM snapshot, runs code, captures output, reverts. Very strong isolation and reproducibility. High overhead (seconds per execution). Used by: research systems where determinism is critical.

🔐 Host process (trusted agent)

Code runs directly in the host process with no sandbox. Maximum capability, zero overhead — but requires a fully trusted agent. Used by: Claude Code, GitHub Copilot on developer machines. Acceptable when the user controls and has consented to the environment.

⚙️ The Code-Execute-Observe Loop
  1. Agent writes code
    Based on the task and any prior observations, the agent generates code. Good agents write small, testable chunks rather than large monoliths — this makes errors easier to isolate and fix. The code is passed to the sandbox via a run_code or bash tool call.
  2. Sandbox executes
    The sandbox runs the code with time and memory limits. It captures stdout, stderr, return value, and any generated files. If the code times out or hits a memory limit, the sandbox returns a timeout error rather than hanging indefinitely.
  3. Output injected as observation
    The sandbox output (stdout + stderr + exit code) is formatted and injected into the agent's context as a tool result. The agent now "sees" exactly what the code produced — including any error tracebacks, which are rich debugging signals.
  4. Agent reads output and reasons
    The agent reads the output. If it's correct, it moves on. If there's an error, it reads the traceback, identifies the cause, and writes a fix in the next iteration. This self-correction loop is what makes code-execution agents so capable at debugging.
  5. Iterate until done
    The loop continues until the output matches expectations, tests pass, or a maximum iteration count is reached. Good agents track their iteration count and use it to diagnose stuck states: "I've tried 5 different approaches for this error — I should try a completely different strategy or ask for help."
💡
Why errors are features, not bugs

A Python traceback contains the exact file, line number, and error type that caused the failure. For an LLM, this is far more useful than asking it to predict behavior. Studies show that agents with code execution converge to correct solutions 2–5× faster than agents that reason about code without running it. The error message is the highest-signal feedback available.

⚠️
Context bloat from long outputs

If the sandbox produces thousands of lines of output (a large dataframe, verbose logs, test suite output), injecting all of it into context is wasteful. Always truncate or summarize long outputs — keep the first and last N lines, or extract just the error message from a verbose traceback. The agent rarely needs the full output to reason correctly.

🌍 Code Execution in Real Systems
🤖 Claude Code — Bash tool runs commands on developer's machine; full host access
💬 ChatGPT Code Interpreter — Python sandbox via Pyodide; supports file I/O and charts
🔬 Devin — full dev environment: terminal, browser, editor; Docker-based isolation
⚡ E2B — cloud sandbox API; 50ms cold start; supports Python, JS, shell
🏗️ GitHub Copilot Workspace — runs tests in CI after agent-generated changes
🪤 Common Pitfalls
Infinite retry loops on systematic errors

The agent keeps trying the same approach because it doesn't recognize that the error is fundamental (wrong library version, wrong API, misunderstood requirement). Fix: After N failed attempts, explicitly prompt the agent to try a completely different approach or escalate to the user.

Stateful sandbox confusion

If the sandbox is stateful (variables persist between executions), the agent may be confused by leftover state from previous iterations. Fix: Either use fresh sandboxes for each major step, or explicitly track and display the current sandbox state in the agent's context.

Dangerous code execution without review

An agent that can run arbitrary bash has the power to delete files, exfiltrate data, or make API calls with real consequences. Fix: Show the user what code will be run before execution for high-risk operations. Implement allowlists for shell commands in sensitive environments.

✅ Key Takeaways
→
Running code beats reasoning about code. Empirical feedback from execution is more reliable than static analysis. Agents with code execution tools consistently outperform those without on software tasks.
→
Error messages are high-signal observations. A traceback tells the agent exactly what went wrong. Design agents to read and reason about errors carefully rather than dismissing them or blindly retrying.
→
Sandbox choice reflects the trust model. Full host access (Claude Code) maximizes capability for trusted users. Container sandboxes protect the host for untrusted agents. Match sandbox isolation to the risk level of the use case.
→
Truncate long outputs aggressively. A full dataframe printout or verbose test log rarely adds useful information. Keep outputs concise to conserve context tokens for reasoning rather than raw data.
