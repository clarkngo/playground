1 Requirements

Functional Requirements

Key Non-Functional Requirement

Core functional: Post creation, feed generation, and feed ranking are the three essential features. Real-time updates and media support are important secondary features. Likes/comments and search are good to mention but not the focus.

Non-functional: Low latency and high availability are both critical. Users expect their feed to load near-instantly. Strong consistency is NOT required for a news feed — eventual consistency is acceptable (a post appearing a few seconds late in a friend`s feed is fine).

Key details:

  • GET /feed uses cursor-based pagination (page_token) instead of offset — more efficient for feeds that change frequently
  • GET /feed/refresh is a lightweight check for new content without fetching the full feed (powers the "5 new posts" banner)
  • POST /posts is asynchronous — returns immediately, fan-out happens in the background
  • Visibility field controls who sees the post (public, friends, private)
  • Consider long-polling or WebSockets for real-time feed updates

Redis sorted sets are ideal for feed caches: O(log N) inserts, O(log N + M) range queries. Each user gets a sorted set of post IDs ranked by score.

The feed_cache table is the heart of the system. It pre-computes each user`s feed so reads are fast. Posts table stores the actual content. Friendships table drives fan-out decisions. The is_celebrity flag on users determines whether to use fan-out-on-write (normal users) or fan-out-on-read (celebrities with millions of followers).

Read Path

Write path: User creates post → Post Service writes to Posts DB → Fan-out Service reads friend list → For each friend, push post_id into their feed cache (Redis sorted set). For celebrities (10K+ followers), skip fan-out — their posts are merged at read time.

Read path: User requests feed → Feed Service reads from feed cache (Redis) → Merge celebrity posts on-the-fly → Feed Ranker scores and orders posts → Hydrate post details from Posts DB/cache → Return ranked feed.

6 Deep Dives

Click each topic to explore implementation details.

Fan-out on Write vs Fan-out on Read ▼

Fan-out on Write (Push model): When a user publishes a post, immediately push the post_id into every follower`s feed cache. Pros: feed reads are extremely fast (pre-computed). Cons: write amplification is massive — a user with 1,000 friends causes 1,000 writes. For celebrities with millions of followers, this is prohibitively expensive.

Fan-out on Read (Pull model): When a user reads their feed, fetch the latest posts from all friends at read time. Pros: no write amplification. Cons: feed reads are slow — must query N friend timelines and merge/rank them.

Hybrid approach (recommended): Use fan-out on write for normal users (fast reads). For celebrities (>10K followers), skip fan-out. At read time, merge the pre-computed feed with fresh celebrity posts. This limits write amplification while keeping reads fast.

The Celebrity Problem ▼

The problem: A celebrity with 10M followers publishes a post. Fan-out on write means 10M cache writes instantly. This creates a latency spike and can overwhelm the fan-out workers.

Solution: Flag users as celebrities when follower_count exceeds a threshold (e.g., 10K). Celebrity posts are NOT fanned out. Instead, at read time, the feed service fetches celebrity posts separately and merges them with the pre-computed feed cache. This adds slight read latency but prevents catastrophic write storms.

Implementation: Maintain a per-user list of followed celebrities. At feed read time, query each celebrity`s recent posts (from a per-celebrity sorted set in Redis) and merge with the user`s feed cache using a k-way merge.

Feed Ranking with ML ▼

Ranking signals: Recency (when was it posted), affinity (how often you interact with the author), engagement (likes/comments ratio), content type (photos typically get higher engagement), post quality score.

Simple scoring formula: score = recency_weight * time_decay + affinity_weight * interaction_score + engagement_weight * engagement_rate

ML pipeline: Train a model on click-through rate and engagement signals. Features include user-author interaction history, post content embeddings, time of day, and device type. Serve predictions via a lightweight model (logistic regression or small neural net) that can score 50 posts in <10ms.

Two-stage ranking: First, retrieve top 500 candidate posts from cache. Second, run the ML ranker to score and select the top 50. This keeps latency low while allowing sophisticated ranking.

Cache Invalidation Strategy ▼

Post deletion: When a user deletes a post, fan-out a delete event to remove the post_id from all followers` feed caches. Use the same fan-out infrastructure as post creation.

Feed cache TTL: Set Redis sorted sets to expire after 7 days of inactivity. Active users get fresh feeds; inactive users` caches are rebuilt on next login. This saves memory for dormant accounts.

Consistency tradeoff: Accept eventual consistency. If a deleted post appears in someone`s feed for a few seconds before cache invalidation propagates, that is acceptable. The alternative (strong consistency) requires distributed transactions and kills performance.

7 Trade-offs

Every design decision involves trade-offs. Compare the key choices.

Push vs Pull Model

Push (Fan-out on Write)

+ Feed reads are O(1) from pre-computed cache
+ Low read latency, great user experience
- Massive write amplification for popular users
- Wasted work for inactive users who never read

Pull (Fan-out on Read)

+ No write amplification at all
+ Always returns freshest data
- Slow feed reads (must query N timelines)
- High read latency, especially with many friends

Consistency vs Availability of Feed

Strong Consistency

+ Post appears in all feeds instantly
+ Deletes reflected immediately everywhere
- Requires distributed transactions
- Much higher latency, lower throughput

Eventual Consistency

+ High throughput, low latency
+ Simpler architecture, easier to scale
- Posts may appear with slight delay
- Deleted posts may briefly remain visible

Ranking: Freshness vs Relevance

Chronological (Freshness)

+ Simple to implement
+ Users see all posts, nothing hidden
- Low-quality content surfaces equally
- Users miss important posts if feed is busy

ML-Ranked (Relevance)

+ Higher engagement, surfaces best content
+ Personalized per user
- Opaque algorithm, user distrust
- Filter bubble effect, less diversity

8 Interview Tips

Advice for presenting this design in an actual interview.

Start with fan-out on write. It is the simpler model and handles the common case well. Then proactively mention the celebrity problem and propose the hybrid approach. This shows you understand real-world scale challenges.
Quantify the fan-out problem. Saying "a user with 300 friends causes 300 fan-out writes, and at 4,600 posts/sec that is 1.4M fan-out writes/sec" makes the problem concrete and justifies your hybrid design.
Mention the hybrid approach for celebrities. This is the key insight interviewers look for. Normal users use push, celebrities use pull, merged at read time. Facebook and Twitter both use variations of this approach.
Discuss feed ranking as a separate layer. Feed generation (what posts to include) and feed ranking (what order to show them) are separate concerns. Mention that ranking can start simple (chronological) and evolve to ML-based. This shows iterative thinking.
