1 Requirements

Identify core functional and non-functional requirements for a real-time chat system.

Functional Requirements

Most Critical Non-Functional

Core: 1:1 messaging, group chats, presence, message history, and push notifications are essential. Read receipts and media are important but secondary.

Non-functional: Real-time delivery (<200ms) and message ordering are both critical. Eventual consistency is acceptable for presence (a few seconds delay is fine). Zero message loss is important but at-least-once delivery with dedup is the practical approach.

3 API Design

Chat uses both WebSocket (real-time) and REST (history, setup) APIs.

WebSocket ws://chat.example.com/ws
  → send_message    { chat_id, content, type }
  ← receive_message { msg_id, chat_id, sender_id, content, timestamp }
  → typing          { chat_id, is_typing }
  → presence        { status: "online"|"away"|"offline" }
  ← ack             { msg_id, status: "sent"|"delivered"|"read" }

GET /chats/{chatId}/messages?before=timestamp&limit=50
  → Paginated message history (cursor-based)

POST /chats
  Body: { type: "group", name: "Team Chat", member_ids: [...] }

GET /chats
  → List of user conversations with last message preview

Key design decisions:

  • WebSocket for real-time send/receive; REST for history and chat management
  • Cursor-based pagination (timestamp) is better than offset for chat history
  • Message acknowledgment (sent → delivered → read) flows back over WS
  • Typing indicators are ephemeral — no persistence needed
  • Presence updates via heartbeat, not per-message

Cassandra excels here: partition by chat_id, cluster by timestamp for efficient range queries. Write-optimized LSM tree handles high message throughput.

Cassandra is the standard choice for message storage at scale. Partition by chat_id + cluster by created_at gives O(1) partition lookup and efficient time-range scans. For smaller scale, PostgreSQL with partitioning works fine. Keep user/chat metadata in PostgreSQL or MySQL — it has relational queries and low volume.

5 Architecture

Animated message flow from sender to recipient through the system.

Flow: Sender connects via WebSocket to a WS Gateway (Go/Rust for performance). Gateway forwards to Message Service, which writes to Cassandra and publishes to Kafka. Delivery Service consumes from Kafka, looks up which WS Gateway the recipient is on, and pushes the message. If recipient is offline, push via APNs/FCM.

Presence: Clients send heartbeats every 5s. WS Gateway updates Redis. If no heartbeat for 30s, mark offline. Presence is separate from messaging — use a dedicated presence service.

6 Deep Dives

Explore the trickiest implementation details of a chat system.

WebSocket Management & Reconnection ▼

Connection management: Each WS Gateway server holds ~50K persistent connections. Use a connection registry (Redis hash) mapping user_id → gateway_server_id so the delivery service knows where to route.

Reconnection: Clients reconnect with the last received message timestamp. The server replays any missed messages from Cassandra. Exponential backoff prevents thundering herd on server restart.

Health checks: Server sends ping frames every 30s. If no pong within 10s, close the connection and clean up the registry entry. Client-side: reconnect on network change events.

Message Ordering Guarantees ▼

Per-chat sequence IDs: Each chat maintains a monotonically increasing sequence counter. Messages within a chat are ordered by this sequence. Use Redis INCR for atomic sequence generation.

Snowflake IDs: Alternative approach — 64-bit IDs encoding timestamp + machine ID + sequence. Globally sortable by time, no central counter needed. Used by Discord and Twitter.

Trade-off: Per-chat sequences give strict ordering within a conversation but require a central counter per chat. Snowflake IDs are approximately ordered (millisecond precision) and fully distributed.

Group Message Fanout ▼

Small groups (<100 members): Inline fanout — the message service directly pushes to each member. Fast, simple, acceptable overhead.

Large groups (100-500 members): Queued fanout — write the message once, enqueue a fanout job. Workers fetch the member list and deliver in batches. Prevents a single large group from blocking other messages.

Optimization: Store one copy of the message. Each recipient gets a pointer (chat_id + msg_id) in their inbox. This saves storage vs duplicating the message per recipient.

7 Trade-offs

Compare the key architectural decisions for a chat system.

WebSocket vs Long Polling vs SSE

WebSocket

+ Full duplex, lowest latency
+ Efficient for high-frequency messages
- Stateful connections, harder to load balance
- Requires connection management infrastructure

Long Polling / SSE

+ Simpler infrastructure, stateless
+ Works through all proxies/firewalls
- Higher latency (long poll: half-duplex)
- SSE is server→client only

Cassandra vs PostgreSQL for Messages

Cassandra

+ Linear write scalability
+ Built for time-series data patterns
- No transactions across partitions
- Limited query flexibility

PostgreSQL

+ ACID, flexible queries, joins
+ Easier to operate at moderate scale
- Write throughput ceiling
- Sharding is complex

8 Interview Tips

How to present a chat system design effectively in an interview.

Mention connection management first. The interviewer wants to know you understand that 10M persistent WebSocket connections is the core infrastructure challenge — not the messaging logic itself.
Discuss 1:1 vs group separately. They have different fanout patterns, different ordering concerns, and different scale characteristics. Treating them as distinct subsystems shows architectural maturity.
Presence is its own subsystem. Many candidates bolt presence onto messaging. In practice, presence (heartbeats, status propagation) should be a separate service with its own data store (Redis) and its own scalability concerns.
Mention end-to-end encryption. Even if you do not design it fully, acknowledging that E2E encryption means the server cannot read message content (only route it) shows security awareness and differentiates you from other candidates.
