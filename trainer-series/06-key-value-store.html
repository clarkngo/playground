Design a Key-Value Store

DynamoDB / Cassandra / Redis — distributed storage at scale
Consistent Hashing · Replication · Conflict Resolution · Gossip Protocol

Step 1 Requirements

Select the functional requirements you think are essential:

Select the most important non-functional requirement:

Functional: put/get/delete operations, distributed across nodes, replication for fault tolerance, tunable consistency. SQL and ML are not core to a key-value store.

Non-functional: <10ms P99 for reads, high availability (prefer AP in CAP), horizontal scaling. The store should prioritize low latency and availability over complex query capabilities.

Reference numbers:

100K reads/sec, 10K writes/sec
Read bandwidth: 100K × 1KB = ~100 MB/s
Write bandwidth: 10K × 1KB = ~10 MB/s

LSM-Tree is preferred for write-heavy key-value stores (like Cassandra, RocksDB). Writes go to MemTable + WAL (fast sequential I/O), then flush to immutable SSTables. Reads check MemTable → Bloom filters → SSTables. B-Trees are better for read-heavy workloads but have write amplification from in-place updates.

Partitioning: Consistent hashing ring maps each key to a primary node. The next N-1 nodes on the ring hold replicas. Virtual nodes (vnodes) ensure even distribution.

Step 5 Architecture

Write path: Client → any Coordinator Node → consistent hash finds responsible nodes → write to primary + W-1 replicas (quorum W=2 of N=3) → ACK to client.

Read path: Client → Coordinator → read from R=2 replicas → return latest version (by vector clock or timestamp) → read repair if divergent.

Quorum math: R + W > N ensures strong consistency. R=2, W=2, N=3 means reads and writes overlap on at least one node.

Membership: Gossip protocol propagates cluster state. Merkle trees detect and repair inconsistencies between replicas.

Step 6 Deep Dives

Consistent Hashing with Virtual Nodes ▶

A basic hash ring maps each node to one position. Problem: when a node joins or leaves, only its neighbors are affected, but load can be highly uneven.

Virtual nodes (vnodes): Each physical node gets 100-200 positions on the ring. Benefits:

  • Even load distribution across heterogeneous hardware
  • When a node fails, its load spreads across many nodes (not just one neighbor)
  • Faster rebalancing when adding/removing nodes

Hash function: typically MD5 or murmur3 of the key, mapped to a 2^128 or 2^64 ring space.

Conflict Resolution: Vector Clocks vs LWW ▶

Vector Clocks: Each node maintains a vector of logical clocks [N1:3, N2:5, N3:1]. Can detect concurrent writes (neither dominates). Downside: vectors grow with number of nodes, requires client-side resolution for true conflicts.

Last-Write-Wins (LWW): Each write has a timestamp. Latest timestamp wins. Simple but can lose data — two concurrent writes, one is silently dropped. Requires synchronized clocks (NTP).

In practice: DynamoDB uses vector clocks and returns conflicting versions to the client. Cassandra uses LWW for simplicity. The choice depends on whether data loss is acceptable.

Failure Detection: Gossip + Phi Accrual ▶

Gossip protocol: Every second, each node picks a random peer and exchanges membership state. Information spreads exponentially — reaches all N nodes in O(log N) rounds.

Phi Accrual Failure Detector: Instead of a binary alive/dead threshold, phi accrual outputs a suspicion level (phi value). Higher phi = more likely dead. Adapts to network conditions — a node with variable latency gets a higher threshold before being marked down.

When a node is detected as down:

  • Hinted handoff: writes intended for the down node are stored temporarily on another node
  • When the node recovers, hints are replayed to bring it up to date
  • Anti-entropy with Merkle trees runs periodically to fix any remaining inconsistencies

Step 7 Trade-offs

Strong Consistency

R + W > N guarantees overlap. Higher latency (wait for quorum), lower availability during partitions. Use when correctness matters (financial data).

Eventual Consistency

R=1, W=1 for max speed. Risk stale reads. Background anti-entropy repairs. Use when availability matters more (social media likes).

In-Memory Storage

Sub-millisecond reads. Limited by RAM cost. Data loss risk on crash (mitigate with snapshots + WAL). Great for cache use cases.

Disk-Based (LSM-Tree)

Much larger capacity per dollar. Single-digit millisecond reads. Write-optimized with sequential I/O. Standard for persistent KV stores.

Vector Clocks

Detects true conflicts. Preserves all concurrent writes. Client must resolve conflicts. Vector size grows with cluster. More correct.

Last-Write-Wins

Simple timestamp comparison. No client-side resolution needed. Silently drops concurrent writes. Requires clock synchronization. Simpler to operate.

Step 8 Interview Tips

Draw the hash ring immediately. Consistent hashing is THE core concept. Draw a circle, place nodes, show how keys map to nodes and how virtual nodes improve balance.
Explain R/W/N quorum math. Show that R+W>N gives strong consistency. Give concrete examples: N=3, W=2, R=2 means every read sees at least one up-to-date replica.
Mention the gossip protocol. Decentralized membership management is what makes the system truly distributed. No single point of failure for cluster coordination.
Discuss node failure handling. Cover hinted handoff for temporary failures, Merkle trees for anti-entropy repair, and how the system rebalances when nodes permanently leave.
