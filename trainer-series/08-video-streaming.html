Design a Video Streaming Platform

YouTube / Netflix — upload, transcode, and stream at global scale
Transcoding Pipeline · Adaptive Bitrate · CDN Distribution · View Counting

Step 1 Requirements

Select the functional requirements you think are essential:

Select the most important non-functional requirement:

Functional: Upload, transcode, adaptive bitrate streaming, CDN delivery, view counting, and basic recommendations. Live editing and real-time collab are out of scope.

Non-functional: Fast start time and smooth playback are the top priorities. Always streaming 4K wastes bandwidth on mobile. Exact real-time view counts are unnecessarily expensive — approximate counts are sufficient.

Step 2 Capacity Estimation

Reference numbers:
100M DAU x 5 videos = 500M views/day ≈ 5,800 views/sec
500K uploads x 200MB raw = 100TB/day raw upload
500K x 5 versions x 100MB = 250TB/day transcoded
CDN bandwidth for streaming: assuming 5 min avg video at 2Mbps = ~75MB per view
500M views x 75MB = ~37PB/day CDN egress (massive!)

Step 3 API Design

// Upload flow (two-step)
POST /api/videos/upload
     Body: { "title": "...", "description": "..." }
     → 200 { "videoId": "v123", "uploadUrl": "https://s3.../presigned" }

// Streaming
GET  /api/videos/{id}/manifest.m3u8
     → HLS manifest with multiple quality levels

// Feed
GET  /api/feed?userId=X&page=1
     → 200 { "videos": [...] }

// View tracking
POST /api/videos/{id}/view
     Body: { "watchTimeSec": 120, "quality": "720p" }
Key design decisions:

Pre-signed URL upload: Client uploads directly to S3 via pre-signed URL, bypassing your servers. This avoids bottlenecking your upload service with huge video files.

HLS manifest: The .m3u8 manifest lists available quality levels (240p, 480p, 720p, 1080p, 4K) and segment URLs. The client player picks the appropriate quality based on bandwidth.

View tracking: Fire-and-forget POST. The view service writes to Kafka, not directly to the database. Counts are aggregated asynchronously.

Hybrid approach: SQL for structured metadata (videos, users, subscriptions) where you need ACID transactions. NoSQL / object storage for video segments (immutable, append-only). Kafka + batch aggregation for view counts.

Video segments are stored in object storage (S3) and served via CDN. The database only stores the CDN URL reference, not the actual video data.

Step 5 Architecture

Upload path: Client → pre-signed URL → S3 → S3 event triggers transcoding queue → Transcoding Workers (FFmpeg, parallel jobs per resolution) → transcoded segments to S3 → CDN origin pull.

Streaming path: Client requests manifest → CDN edge serves manifest + segments. Adaptive bitrate: client monitors bandwidth, switches quality levels mid-stream by requesting different segment URLs.

View counting: Client → View Service → Kafka → Count Aggregator (batch, every few seconds) → DB update. Approximate counting is fine — nobody notices if the count is off by a few hundred.

Step 6 Deep Dives

Transcoding Pipeline: DAG of FFmpeg Jobs ▶

When a video is uploaded, a DAG (directed acyclic graph) of transcoding jobs is created:

  • Split raw video into segments (e.g., 4-second chunks)
  • For each segment, transcode to 5 resolutions in parallel: 240p, 480p, 720p, 1080p, 4K
  • Generate thumbnails at key frames
  • Create HLS manifest linking all segments and resolutions

FFmpeg workers run on GPU instances for hardware-accelerated encoding. Each worker pulls jobs from an SQS/Kafka queue. A single video may spawn 50+ parallel jobs.

Fault tolerance: If a worker dies mid-transcode, the segment job returns to the queue and is picked up by another worker. The DAG orchestrator tracks completion of all segments before marking the video as "ready".

Adaptive Bitrate Streaming (HLS/DASH) ▶

HLS (HTTP Live Streaming): The manifest (.m3u8) lists available quality levels:

#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p/stream.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2400000,RESOLUTION=1280x720
720p/stream.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p/stream.m3u8

The client player (e.g., hls.js) monitors download speed of each segment. If bandwidth drops, it switches to a lower quality for the next segment. If bandwidth improves, it upgrades. This happens seamlessly mid-playback.

Segment size matters: 2-4 second segments balance quality adaptation speed (shorter = faster switching) with encoding efficiency (longer = better compression).

View Counting at Scale ▶

The problem: 500M views/day. Direct DB writes = 5,800 writes/sec to a single row. Hot key problem.

Solution: Kafka buffering + batch aggregation

  • View events → Kafka topic (partitioned by video_id)
  • Aggregation consumer: batch count events every 5-10 seconds
  • Single DB UPDATE per video per batch: SET count = count + 47
  • For viral videos: further shard the counter across multiple rows, sum on read

Deduplication: Use a bloom filter or Redis set with TTL to deduplicate views from the same user within a time window. Approximate dedup is acceptable.

Step 7 Trade-offs

Pre-Transcode All Resolutions

Higher upfront cost and storage. Instant playback at any quality. Standard approach for popular platforms. 5x storage per video.

On-Demand Transcoding

Transcode only when requested. Saves storage for rarely-watched videos. First viewer experiences delay. Good for long-tail content.

HLS (Apple)

Industry standard. Broad device support. Uses .m3u8 manifests and .ts segments. Supported natively on iOS/Safari. Slightly higher latency.

DASH (Open Standard)

ISO standard, royalty-free. Uses .mpd manifests and .mp4 segments. Better DRM support. Not supported natively on Apple devices without MSE.

Exact View Counts

Requires distributed transactions or strong consistency. Much higher cost. Necessary for monetization-critical counting (ad views). Slower.

Approximate View Counts

Kafka buffering + batch aggregation. Counts may lag by seconds. Perfectly fine for display purposes. Handles viral videos gracefully.

Step 8 Interview Tips

Separate upload and streaming paths clearly. These have completely different characteristics: upload is write-heavy and asynchronous, streaming is read-heavy and latency-sensitive. Draw them as distinct flows.
Mention the transcoding pipeline early. Transcoding is the unique complexity of video systems. Explain the DAG of FFmpeg jobs, parallel processing, and how you handle failures.
CDN is crucial — discuss PoP strategy. Video streaming without CDN is a non-starter. Mention Points of Presence, cache hit ratios, origin pull vs push, and how popular videos get cached at edge.
View counting is a classic follow-up. Interviewers love asking how you count views at scale. Have the Kafka → batch aggregation → DB pattern ready. Mention deduplication and approximate counting.
