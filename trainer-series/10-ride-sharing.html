10M rides/day / 86400 ≈ 115 ride requests/sec
Each location update: ~1KB (driver_id, lat, lng, timestamp, status)
Location bandwidth: 500K x 1KB = ~500 MB/s ingest

     Body: { "pickupLat": 37.77, "pickupLng": -122.42,
             "destLat": 37.78, "destLng": -122.41 }
     → 200 { "rideId": "r123", "status": "REQUESTED", "estimatedFare": 12.50 }

// Driver accepts ride
POST /api/rides/{id}/accept
     → 200 { "rideId": "r123", "status": "MATCHED", "eta": 180 }

// Driver updates location (high frequency)
PUT  /api/drivers/location
     Body: { "lat": 37.775, "lng": -122.418 }
     → 200 { "ack": true }

// Get ride status and ETA
GET  /api/rides/{id}/status
     → 200 { "status": "DRIVER_EN_ROUTE", "driverLat": 37.775,
             "driverLng": -122.418, "eta": 120 }
Key design decisions:

Location updates: Use WebSocket or UDP for high-frequency updates (every 3-5s). HTTP would create too much overhead. The PUT endpoint shown above is simplified — in practice, this goes over a persistent connection.

Ride status: Riders poll this endpoint (or receive WebSocket push) to track driver location and trip state changes.

Surge pricing: GET /api/pricing/surge?lat=X&lng=Y returns the current surge multiplier for a zone. Computed from supply/demand ratio in each geospatial cell.

The geospatial index stores only available drivers. When a driver starts a trip, they are removed from the index. When they complete a trip, they are re-added.

Geohash in Redis is the simplest approach and handles most interview scenarios. GEOADD to insert, GEOSEARCH to find nearby drivers within a radius. O(log N) per operation.

QuadTree is preferred for production systems with uneven density (downtown NYC vs rural Montana). Dense areas are subdivided into smaller cells for finer-grained search.

Key insight: The geospatial index must be updated 500K times/sec (every driver location update). This is why in-memory solutions (Redis or custom QuadTree) are necessary — disk-based indexes are too slow.

Step 5 Architecture

Location flow: Driver app → Location Service (WebSocket) → updates geospatial index (Redis GEOADD) every 3-5 seconds.

Matching flow: Rider requests ride → Ride Service → Matching Service queries geospatial index for K nearest available drivers → sends ride offer to closest driver → if driver declines or times out (10s), try next driver → when accepted, create trip record.

Trip tracking: Both rider and driver apps receive real-time updates via WebSocket. Driver location streams to rider through the Location Service. Trip state transitions are published via event bus.

Step 6 Deep Dives

Geospatial Indexing: Geohash vs QuadTree ▶

Geohash: Encodes latitude/longitude into a string (e.g., "9q8yyk"). Strings with shared prefixes are geographically close. Redis uses geohash internally for GEOADD/GEOSEARCH.

Pros: Simple, Redis handles it natively. Cons: Fixed precision levels, edge-case issues at geohash boundaries (two nearby points can have different prefixes).

QuadTree: Recursively divides 2D space into 4 quadrants. Dense areas (cities) are subdivided further. Sparse areas (rural) stay as large cells.

Pros: Adapts to density, no boundary issues. Cons: Must be built custom, harder to distribute across servers.

For interviews: Start with Geohash + Redis. Mention QuadTree as an optimization if the interviewer asks about uneven density.

Matching Algorithm: Find and Dispatch ▶

Step 1: Query geospatial index: GEOSEARCH within 5km radius, return K nearest available drivers (K=5-10).

Step 2: Rank candidates by distance, rating, acceptance rate, and ETA (considering road network, not just straight-line distance).

Step 3: Send ride offer to top candidate. Driver has 10-15 seconds to accept.

Step 4: If declined or timed out, send to next candidate. After all K candidates exhausted, expand radius and retry.

Optimization — broadcast model: Instead of sequential offers, send to top 3 simultaneously. First to accept wins. Faster matching but some drivers see offers disappear.

Edge cases: No drivers found → notify rider, retry with expanding radius, suggest rider move to busier area. Driver cancels after match → re-enter matching with priority.

Trip State Machine: States and Transitions ▶

Every ride follows a strict state machine. Transitions are validated server-side to prevent invalid states.

Step 7 Trade-offs

Geohash (Redis)

Simple, battle-tested, Redis-native. Fixed precision levels. Boundary edge cases. Great for most use cases. Easy to shard by geohash prefix.

QuadTree (Custom)

Adapts to density. No boundary issues. Must build custom. Harder to distribute. Better for uneven geography. Used by Uber internally.

Dispatch to Nearest

Sequential offer to closest driver. Fair to drivers. Slower matching (10s timeout per attempt). Predictable experience.

Broadcast to K Drivers

Send to top K simultaneously. Fastest matching. First-accept wins. Some drivers see vanishing offers. Better for rider experience.

Pre-Computed ETA

Cache ETA for common routes. Fast lookup. Stale during traffic changes. Good for initial estimates. Update periodically in background.

Real-Time ETA

Calculate using live traffic data. Accurate but slower. Requires integration with maps API. Essential during active trips. More expensive.

Step 8 Interview Tips

Draw the matching flow first. Rider request → Matching Service → geospatial query → driver notification → accept/decline. This is the core of the system and should be your first diagram.
Geospatial indexing is THE key topic. Know Geohash and QuadTree well. Be ready to explain how you find nearby drivers efficiently. Draw the geohash grid or quadtree subdivision.
Mention the trip state machine explicitly. REQUESTED → MATCHED → EN_ROUTE → ARRIVED → IN_PROGRESS → COMPLETED. Show you think about edge cases: cancellations, timeouts, no drivers found.
Discuss surge pricing at a high level. Supply/demand ratio per geographic zone. When demand exceeds supply, multiply fare by surge factor. Mention that it incentivizes more drivers to come online.
