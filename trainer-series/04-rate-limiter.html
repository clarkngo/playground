3 API Design

The rate limiter acts as middleware, not a standalone API. Here is how it integrates.

// Rate limiter is middleware — intercepts every request
// If allowed:
HTTP/1.1 200 OK
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 87
X-RateLimit-Reset: 1679500060

// If rate limited:
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1679500060
Retry-After: 30
Body: { "error": "Rate limit exceeded. Try again in 30 seconds." }

// Admin API for configuring rules:
POST /api/rate-limits/rules
  Body: {
    "endpoint": "/api/posts",
    "limit": 100,
    "window_seconds": 3600,
    "key_type": "user_id"
  }

GET /api/rate-limits/rules
DELETE /api/rate-limits/rules/{ruleId}

Key details:

  • The rate limiter is middleware, not a separate service endpoint — it intercepts requests before they reach the application
  • X-RateLimit headers are essential for client-side backoff: Limit (max requests), Remaining (left in window), Reset (when counter resets)
  • 429 status code is the standard HTTP response for rate limiting
  • Retry-After header tells clients exactly when to try again
  • Admin API allows dynamic rule configuration without redeployment
  • key_type determines what to rate limit by: user_id, IP, API key, or endpoint

// Key: rl:{rule_id}:{user_id}
// Hash fields:
//   tokens  — current available tokens (float)
//   last_refill — timestamp of last refill

HSET rl:rule_1:user_123 tokens 87 last_refill 1679500000

// Fixed Window Counter
// Key: rl:{rule_id}:{user_id}:{window_start}
// Value: request count
SET rl:rule_1:user_123:1679500000 13
EXPIRE rl:rule_1:user_123:1679500000 3600

// Sliding Window Log
// Key: rl:{rule_id}:{user_id}
// Sorted set, score = timestamp, value = request_id
ZADD rl:rule_1:user_123 1679500042 req_abc
ZREMRANGEBYSCORE rl:rule_1:user_123 0 1679496442
ZCARD rl:rule_1:user_123

Redis provides sub-millisecond operations. INCR + EXPIRE is atomic with Lua scripts. Sorted sets enable precise sliding window tracking.

Two-tier storage: Rules live in a SQL database (PostgreSQL) for persistence and are cached in memory on each API server at startup. Counters live in Redis for sub-millisecond reads and writes. The token bucket approach stores just 2 fields per user-rule pair, making it extremely memory-efficient. Sliding window log is more accurate but uses more memory (stores every request timestamp).

5 Architecture

Allowed Request
Denied Request (429)

Request flow: Client → Load Balancer → Rate Limiter Middleware → Redis (check + increment counter) → If allowed: forward to API Server → Response with X-RateLimit headers. If denied: return 429 immediately (never reaches API server).

Key insight: The rate limiter must be in the hot path BEFORE the API server. Redis INCR + EXPIRE in a Lua script ensures atomic check-and-increment. Rules are cached in-memory on each server and refreshed periodically from the database.

Token Bucket Algorithm (Animated) ▼

How it works: Each user has a bucket that holds tokens. The bucket starts full (e.g., 10 tokens). Each request consumes 1 token. Tokens are refilled at a steady rate (e.g., 1 token/second). If the bucket is empty, the request is rejected.

Tokens: 10 / 10

Pros: Simple, memory-efficient (2 values per user), allows bursts up to bucket size. Cons: Choosing the right refill rate requires tuning.

// Token Bucket — Redis Lua Script
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local data = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(data[1]) or capacity
local last = tonumber(data[2]) or now

-- Refill tokens based on elapsed time
local elapsed = now - last
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= 1 then
  tokens = tokens - 1
  redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
  redis.call('EXPIRE', key, 3600)
  return 1  -- allowed
else
  redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
  return 0  -- denied
end
Sliding Window Log ▼

How it works: Store the timestamp of every request in a sorted set. To check the limit, remove all entries older than the window, then count remaining entries. If count < limit, allow the request and add its timestamp.

Pros: Most accurate algorithm — no boundary issues. Cons: High memory usage (stores every request timestamp). For a user making 1000 requests/hour, that is 1000 entries in the sorted set.

Best for: Systems that need precise rate limiting and can afford the memory cost. API billing, fraud detection.

Sliding Window Counter ▼

How it works: A hybrid approach. Maintain counters for the current and previous fixed windows. Estimate the count in the sliding window as: count = prev_window_count * overlap_pct + curr_window_count

Example: Window = 1 hour. Current time is 15 minutes into the hour. Previous hour had 80 requests, current hour has 20. Estimated count = 80 * 0.75 + 20 = 80. This approximates the true sliding window without storing individual timestamps.

Pros: Memory-efficient (just 2 counters), smooth rate limiting without boundary spikes. Cons: Approximation can allow slight over-limit in edge cases.

Fixed Window Counter ▼

How it works: Divide time into fixed windows (e.g., 1-minute intervals). Each window has a counter. Increment on each request; reject when counter hits the limit. Counter resets at window boundary.

Pros: Simplest algorithm, minimal memory (one counter per window). Cons: Burst at window boundaries — a user can make 2x the limit across two adjacent windows (100 at end of window 1, 100 at start of window 2 = 200 in 1 second).

Implementation: INCR rl:{user}:{window_start} with TTL set to window duration. The window_start is the current timestamp truncated to the window size.

Leaky Bucket Algorithm ▼

How it works: Requests enter a FIFO queue (the bucket). The queue is processed at a fixed rate (the leak rate). If the queue is full, new requests are rejected. This ensures a perfectly smooth output rate regardless of input burstiness.

Pros: Perfectly smooth output rate, great for APIs that need consistent throughput. Cons: Bursts are queued, not served immediately. Old requests may wait in the queue while new requests are rejected. Tuning queue size is tricky.

Difference from token bucket: Token bucket allows bursts (spend saved tokens), leaky bucket enforces a constant rate. Token bucket controls the rate of requests allowed, leaky bucket controls the rate of requests processed.

7 Trade-offs

Every design decision involves trade-offs. Compare the key choices.

Memory vs Accuracy

Fixed Window Counter

+ Minimal memory (1 counter per window)
+ O(1) check and increment
- Boundary burst problem (2x spike)
- Inaccurate at window edges

Sliding Window Log

+ Perfect accuracy, no boundary issues
+ Exact count at any point in time
- Stores every timestamp (high memory)
- O(N) cleanup of old entries

Local vs Distributed Rate Limiting

Local (Per-Server)

+ Zero network overhead
+ Works even if Redis is down
- Inconsistent across servers
- Total rate = limit * num_servers

Distributed (Redis)

+ Accurate global rate limiting
+ Consistent view across all servers
- Network latency per request (~0.5ms)
- Redis is a single point of failure

Hard vs Soft Rate Limits

Hard Limit

+ Strict protection against abuse
+ Predictable server load
- Frustrating for legitimate users at boundary
- Binary allow/deny, no flexibility

Soft Limit

+ Allows brief bursts above limit
+ Better user experience at boundary
- Can allow temporary overload
- Harder to reason about capacity

8 Interview Tips

Advice for presenting this design in an actual interview.

Start with the token bucket algorithm. It is the most commonly used in practice (used by Stripe, AWS, and most API gateways). It balances simplicity, memory efficiency, and burst handling. Then mention alternatives to show breadth.
Mention Redis INCR + EXPIRE atomicity. A common pitfall is the race condition between checking the counter and incrementing it. Using a Lua script in Redis makes the operation atomic. This shows you understand distributed systems edge cases.
Discuss what happens when the rate limiter fails. Should you fail-open (allow all requests) or fail-closed (block all)? For most systems, fail-open is safer — it is better to briefly allow excess traffic than to block all users. This is a great talking point.
Bring up the multi-tier approach. Local rate limiting (per server, in-memory) for the first line of defense, plus distributed rate limiting (Redis) for accurate global limits. Local catches the obvious abuse with zero latency; Redis handles the precise counting.
