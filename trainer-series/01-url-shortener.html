Design a URL Shortener

bit.ly from scratch
Classic Interview Problem • Read-Heavy System

Step 1 Requirements Gathering

Identify the functional and non-functional requirements for the URL shortener.

Functional Requirements (check all that apply):
What is the expected read:write ratio?
Target redirect latency?
Core Functional: Shorten URLs, redirect to original, custom aliases (optional), analytics (optional), expiration (optional). Auth and file uploads are out of scope.

Non-Functional: 100:1 read:write ratio (URLs are created once, read many times). Target <50ms redirect latency. High availability is critical — downtime means broken links across the internet.

Step 3 API Design

Define the REST API endpoints.

POST /api/shorten
Body: { "long_url": "https://example.com/very/long/path",
        "custom_alias": "my-link",   // optional
        "expires_at": "2026-12-31"  // optional
      }
Response: { "short_url": "https://sho.rt/abc123" }
GET /{shortCode}
Response: 301 Redirect → Location: https://example.com/very/long/path
GET /api/stats/{shortCode}
Response: { "total_clicks": 15420, "created_at": "...", "top_countries": [...] }
DELETE /api/{shortCode}
Response: 204 No Content
Key decisions:
• POST for creation (not idempotent — generates unique code each time).
• 301 (permanent redirect) for better SEO but makes analytics harder (browser caches redirect). Consider 302 (temporary) if analytics are important.
• Stats endpoint is separate — never block the fast redirect path.
• Rate limit the POST endpoint to prevent abuse.

NoSQL works well here: simple key-value lookup by short_code. DynamoDB TTL handles expiration natively.

SQL pros: ACID guarantees, UNIQUE constraint on short_code prevents collisions natively, joins for analytics.
NoSQL pros: Horizontal scaling, simple key-value access pattern fits perfectly, built-in TTL for expiration.
Both work. For a URL shortener, the access pattern is simple enough that NoSQL scales more naturally, but SQL is fine up to billions of records with proper indexing.

Step 5 High-Level Architecture

Animated request flow through the system.

Write path: Client → Load Balancer → App Server → generate base62 code → store in DB → populate cache → return short URL.

Read path (redirect): Client → LB → App Server → check Redis cache (99% hit rate) → if miss, query DB → 301 redirect. Cache-aside pattern.

Key insight: The Redis cache is the star of this system. With a 100:1 read:write ratio and most URLs accessed repeatedly, a well-tuned cache handles 99%+ of reads without touching the database.

Step 6 Deep Dives

Explore critical design decisions in detail.

Short Code Generation Strategies ▼
Option A: Base62 Counter
Use an auto-incrementing counter, encode to base62 (a-z, A-Z, 0-9). A 7-char code gives 62^7 = 3.5 trillion unique URLs. Simple, no collisions. But: predictable (sequential), needs distributed counter coordination.

Option B: MD5 Hash (first 7 chars)
Hash the long URL with MD5, take first 7 characters. Deterministic — same URL always gets same code. But: collision probability increases with scale. Need collision resolution (append counter).

Option C: Pre-generated Key Ranges
A Key Generation Service (KGS) pre-generates random keys and stores them in a DB. App servers fetch a batch. No collisions, no coordination at write time. Slight overhead for the KGS, but best for distributed systems.

Recommendation: KGS for production. Base62 counter for simpler deployments.
Cache Strategy ▼
Cache-aside pattern: On read, check Redis first. Cache miss → query DB → populate cache → return. On write, write to DB then cache.

Why not write-through? Most URLs are created and never accessed again. Cache-aside only caches URLs that are actually requested, saving memory.

TTL strategy: Set cache TTL to match URL expiration if set. For non-expiring URLs, use LRU eviction. Hot URLs stay cached naturally.

Cache sizing: If 20% of URLs get 80% of traffic (Pareto), caching ~20% of total URLs handles most reads. For 5 billion URLs at 500 bytes, 20% = ~500GB in Redis — achievable with a Redis cluster.
Analytics Pipeline ▼
Critical rule: Never block the redirect to record analytics. The redirect must be fast (<50ms).

Async pipeline: On each redirect, push a click event to Kafka (fire and forget). A consumer reads from Kafka, enriches with geo data (IP → country), and writes to an analytics store (ClickHouse or time-series DB).

Real-time vs batch: Kafka consumers can aggregate in micro-batches (every 5 seconds) for efficiency. Real-time dashboard reads from a pre-aggregated materialized view.

Step 7 Trade-offs

Compare key architectural decisions.

SQL vs NoSQL

SQL (PostgreSQL)

  • UNIQUE constraint prevents collisions
  • ACID transactions
  • Rich analytics queries with JOINs
  • Mature tooling and backup

NoSQL (DynamoDB)

  • Horizontal scaling out of the box
  • Simple key-value access pattern fits perfectly
  • Built-in TTL for expiration
  • Lower latency at extreme scale

Base62 Counter vs Hash

Base62 Counter

  • Zero collision probability
  • Short, sequential codes
  • Simple implementation
  • Needs distributed coordination

MD5 Hash (truncated)

  • Stateless — no counter needed
  • Same URL always gets same code
  • Collision resolution adds complexity
  • Slightly longer codes

301 vs 302 Redirect

301 (Permanent)

  • Browser caches — faster subsequent visits
  • Better for SEO link juice
  • Reduces load on our servers
  • Loses analytics (browser skips us)

302 (Temporary)

  • Every click hits our server
  • Accurate analytics tracking
  • Can change destination later
  • Slightly higher latency for users

Step 8 Interview Tips

Key points to mention in your interview.

Start with requirements clarification. Ask about scale (how many URLs per day?), read:write ratio, custom aliases, and whether analytics are needed. This shows structured thinking.
Do capacity math early. Calculating QPS, storage, and bandwidth up front frames the entire design. It tells you whether you need caching, sharding, or can get away with a single server.
Mention the cache hit ratio. A URL shortener with 99% cache hit rate means the DB only handles 1% of reads. This is the single most impactful optimization — make sure the interviewer knows you thought about it.
Discuss 301 vs 302 implications. This is a subtle but important trade-off. 301 is better for users (faster) but worse for analytics (browser caches the redirect). 302 gives you full visibility. Mentioning this shows depth.
