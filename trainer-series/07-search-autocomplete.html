Design Search Autocomplete

Google Suggestions — instant prefix matching at scale
Trie Data Structure · Frequency Ranking · Distributed Sharding · Query Filtering

Step 1 Requirements

Select the most important non-functional requirement:

Functional: Top-5 suggestions, frequency ranking, periodic ranking updates, content filtering, fast response. Full search results and image previews are separate systems.

Non-functional: Low latency is critical — users expect instant feedback. Prefix matching is the core operation. Typo tolerance is a nice-to-have. Rankings can be updated in batches (not real-time).

Step 2 Capacity Estimation

Reference numbers:
10M DAU x 10 searches/day = 100M searches/day
4 chars typed per search = 400M autocomplete queries/day
400M / 86400 ≈ 4,600 QPS
1M unique terms, avg 15 chars + metadata = ~500MB trie storage
Trie fits entirely in memory on each serving node.

Key design choice: The autocomplete API is read-only and extremely latency-sensitive. Search logging is fire-and-forget (async). Trie rebuilds happen offline.

Logs are written to Kafka, aggregated weekly via MapReduce to compute term frequencies.

The trie with cached top-K per node is the key insight. Without caching, you would need to traverse the entire subtree for every prefix to find the most popular completions — far too slow for real-time use.

Offline pipeline: Search logs → Kafka → MapReduce aggregation (weekly) → build new trie with updated frequencies → deploy atomically to all serving nodes. This separation of online serving from offline ranking is critical.

Step 5 Architecture

Online path (serving): User types → API Gateway → Autocomplete Service (in-memory trie) → return cached top-K for the prefix. Each keystroke triggers a new request. Debounce on client (50-100ms).

Offline path (ranking): Search logs → Kafka → Aggregation Service (MapReduce weekly) → Trie Builder → deploy new trie to serving nodes via blue/green swap.

Sharding: Shard trie by first 2 characters across nodes. "aa"-"az" on shard 0, "ba"-"bz" on shard 1, etc. Uneven distribution handled by splitting hot shards.

Step 6 Deep Dives

Trie Data Structure: Prefix Tree with Top-K ▶

A trie (prefix tree) stores strings character by character. Each path from root to a node represents a prefix.

Top-K caching: At each node, store the K most popular completions reachable from that node. When a user types "hel", we traverse to the "h"→"e"→"l" node and immediately return its cached top-5. No subtree traversal needed.

Space optimization: Compress paths with single children (patricia trie). "h-e-l-l-o" becomes a single "hello" edge. Reduces memory by ~50%.

Ranking Pipeline: Logs → Aggregate → Rebuild ▶

Collection: Every completed search is logged to Kafka (fire-and-forget). ~100M events/day.

Aggregation: Weekly MapReduce job reads all logs. Map: emit (term, 1). Reduce: sum counts. Apply time decay — recent searches weighted higher. Filter inappropriate terms against a blocklist.

Trie Build: Sort terms by frequency. Build trie, computing top-K at each node bottom-up. Serialize to a compact binary format. Upload to S3.

Deployment: Blue/green deployment. New trie loaded into memory on standby nodes. Traffic switched atomically. Old version kept for instant rollback.

Distributed Trie: Sharding by Prefix ▶

Sharding strategy: Partition by first 2 characters of the prefix. 26×26 = 676 possible shards. Each shard holds a subtrie for its prefix range.

Hot shard handling: Some prefixes are much more popular ("th", "wh", "ho"). Split hot shards further by 3rd character. Use a routing table that maps prefix ranges to shard IDs.

Replication: Each shard replicated to 2-3 nodes. Reads can go to any replica. Since tries are read-only (rebuilt offline), there are no consistency issues between replicas.

Scaling: Each node holds ~500MB / 26 shards ≈ 20MB per shard. Even modest servers can hold many shards. Scale by adding nodes and redistributing shards.

Step 7 Trade-offs

Trie (Custom)

Purpose-built for prefix matching. O(prefix_len) lookup. Top-K cached per node. Memory-efficient with compression. Requires custom build pipeline.

ElasticSearch Prefix

Off-the-shelf solution. Supports fuzzy matching, typo correction. Higher latency (~10-50ms vs ~1ms). Easier to operate but less optimized for this exact use case.

Real-Time Ranking

Rankings reflect searches from minutes ago. Complex: stream processing, incremental trie updates. Risk of gaming/spam affecting suggestions instantly.

Batch Ranking

Weekly rebuild. Simple, predictable, debuggable. Rankings lag by up to a week. Easier to filter inappropriate content before deployment. Industry standard approach.

In-Memory Trie

Sub-millisecond lookups. Limited by RAM. Must fit entire trie in memory. Perfect for autocomplete where dataset is bounded (~500MB).

Redis-Backed

Larger capacity via Redis Cluster. Adds network hop (~1-2ms). Sorted sets with ZRANGEBYLEX for prefix matching. Simpler deployment, slightly higher latency.

Step 8 Interview Tips

Draw the trie structure. Visually show how "hello", "help", and "helmet" share the "hel" prefix. Label a node with its cached top-K list. This immediately demonstrates you understand the core data structure.
Explain top-K caching per node. This is the key optimization. Without it, every query requires traversing the entire subtree — too slow. With it, lookups are O(prefix length).
Separate online serving from offline ranking. The serving path is read-only and must be fast. The ranking pipeline is write-heavy and can be batch. These have fundamentally different requirements.
Mention content filtering. Autocomplete suggestions are visible to everyone. You must filter inappropriate, offensive, or dangerous content. This is a filtering step in the offline trie build pipeline.
