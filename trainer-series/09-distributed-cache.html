Design a Distributed Cache

Memcached / Redis Cluster — sub-millisecond reads at scale
LRU/LFU Eviction · Cache-Aside · Hot Key Mitigation · Thundering Herd

Step 1 Requirements

Select the functional requirements you think are essential:

Select the most important non-functional requirement:

Functional: CRUD with TTL, distributed across nodes, eviction policies, replication, hot key handling, and thundering herd prevention. SQL queries and data pipelines belong to other systems.

Non-functional: Sub-millisecond reads are the primary reason a cache exists. Horizontal scaling lets you add nodes as traffic grows. Graceful degradation means the system still works (slower) when cache nodes go down.

Step 2 Capacity Estimation

Reference numbers:
10M keys x 10KB = 100GB total cache
3 nodes minimum → ~33GB per node (fits in memory on modern servers)
500K reads/sec, 50K writes/sec
Read bandwidth: 500K x 10KB = ~5 GB/s (spread across nodes)
A single Redis node handles ~100K ops/sec → need ~5 nodes for reads alone

In practice, caches use a client library, not HTTP APIs. The client library handles: 
// Client library (pseudocode)
class CacheClient {
  constructor(nodeList) {
    this.ring = new ConsistentHashRing(nodeList);
  }
  get(key) {
    const node = this.ring.getNode(key);
    return node.sendCommand('GET', key);
  }
  set(key, value, ttl) {
    const node = this.ring.getNode(key);
    return node.sendCommand('SET', key, value, ttl);
  }
}
The client library computes the consistent hash locally, connecting directly to the correct cache node. No proxy needed — this eliminates an extra network hop.

LRU is the default choice for most caching scenarios. Simple, effective, and handles most access patterns well. LFU is better when access frequency varies widely (e.g., some keys are accessed 1000x more than others and should never be evicted).

Key distribution: Consistent hashing ring maps keys to cache nodes. Each node independently manages its own eviction. No coordination needed between nodes for eviction decisions.

Step 5 Architecture

Cache-Aside (Lazy Loading): App checks cache → miss → query DB → populate cache → return. Most common pattern. Cache only stores data that has been requested.

Write-Through: App writes to DB → immediately update cache. Ensures cache is always consistent. Higher write latency but eliminates stale reads.

Write-Behind (Write-Back): App writes to cache → async flush to DB in batches. Fastest writes, but risk data loss if cache node crashes before flush.

The cache-aside pattern is the safest starting point for most interviews. Mention write-through as an improvement if the interviewer asks about consistency.

Step 6 Deep Dives

LRU vs LFU Eviction: Both O(1) ▶

LRU (Least Recently Used): Favors recency. A key accessed once very recently beats a key accessed 1000 times yesterday. Works well for temporal access patterns (news, feeds, sessions).

LFU (Least Frequently Used): Favors frequency. A popular key stays cached even if not accessed in the last few minutes. Works well for skewed distributions (product catalog where 1% of products get 80% of traffic).

Hybrid approaches:

  • Window-TinyLFU (used by Caffeine): admission filter + LRU window + SLRU main
  • Redis uses approximated LRU (samples 5 random keys, evicts least recent among them) for efficiency
  • Some systems use TTL-based eviction alongside LRU/LFU as a safety net
Hot Key Mitigation: The #1 Follow-Up Question ▶

Problem: A viral post or flash sale causes millions of requests to hit the same cache key on the same node. That single node becomes a bottleneck.

Solutions:

  • Local cache in app servers: Each app server caches hot keys in-process (with short TTL ~1-5s). Eliminates network hop entirely. Most effective solution.
  • Random suffix sharding: Store key under "product:123:shard0" through "product:123:shard9". Client randomly picks a shard. Spreads load across 10 nodes.
  • Read replicas: Replicate hot keys to multiple cache nodes. Client library routes reads to a random replica.

Detection: Monitor request counts per key. Auto-detect hot keys when rate exceeds a threshold. Promote to local cache automatically.

Thundering Herd Prevention ▶

Problem: A popular cache key expires. 10,000 concurrent requests all see a cache miss simultaneously. All 10,000 hit the database at once. Database crashes.

Solutions:

  • Request coalescing (singleflight): Only the first request fetches from DB. All other concurrent requests wait for the first result and share it. Implemented with mutexes/locks per key.
  • Staggered TTLs: Add random jitter to TTL (e.g., TTL = 3600 + random(0, 300)). Prevents mass simultaneous expiration.
  • Cache warming: Proactively refresh keys before they expire. A background job refreshes keys with TTL < 10% remaining.
  • Never-expire + async refresh: Serve stale data while refreshing in the background. Trade freshness for availability.

Step 7 Trade-offs

Cache-Aside

App manages cache explicitly. Cache only stores requested data. Risk of stale reads after DB update. Most common and simplest pattern.

Write-Through

Cache always consistent with DB. Higher write latency (write both). No stale reads. Caches data that may never be read.

LRU Eviction

Favors recency. Simple implementation. Works for most access patterns. Can evict frequently-used keys after a brief idle period.

LFU Eviction

Favors frequency. Better for skewed distributions. More complex bookkeeping. New keys struggle to build frequency and may be evicted prematurely.

Replication

Multiple copies of each key. Survives node failures. Higher memory cost. Read scalability. Must handle cache invalidation across replicas.

Sharding Only

Each key on exactly one node. Maximum memory efficiency. Single point of failure per key. Simpler consistency. Cold start on node replacement.

Step 8 Interview Tips

Draw cache-aside pattern first. App → check cache → miss → query DB → populate cache → return. This is the bread-and-butter pattern. Get it on the whiteboard early to anchor the discussion.
Explain consistent hashing for node selection. Show how the client library maps keys to nodes. Mention virtual nodes for even distribution. This shows you understand the distributed aspect.
Hot key problem is THE follow-up question. Interviewers will ask what happens when one key gets 100x more traffic. Have local caching, random sharding, and read replicas ready as answers.
Mention thundering herd prevention. This shows depth beyond basic caching. Request coalescing (singleflight) and staggered TTLs are the key techniques. Most candidates miss this.
