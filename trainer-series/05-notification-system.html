Step 2 Capacity Estimation

Estimate the notification volume across all channels.

At 1B notifications/day: ~11,500 notifications/sec average, ~50K/sec peak. Push dominates volume (600M/day), email is second (250M/day). Storage for in-app notifications: ~100M * 10 * 0.1 * 500 bytes = ~50GB/day. The system is write-heavy with high fan-out. Message queues must handle sustained throughput of 50K+ messages/sec.

Design decisions: (1) 202 Accepted — notification sending is async; the API queues the request and returns immediately. (2) Idempotency key prevents duplicate notifications from retry storms. (3) Channel preference filtering happens server-side, not client-side. (4) Priority field drives queue ordering. (5) Template system keeps notification content separate from delivery logic — this allows A/B testing, localization, and content changes without code deploys.

Step 5 High-Level Architecture

Design the notification pipeline from event source to delivery.

Flow: (1) Event sources (services, cron jobs, user actions) send notification requests to the Notification Service via API. (2) The service validates, deduplicates (idempotency key), checks user preferences, renders templates, and enqueues messages into priority queues (one per channel). (3) Channel-specific workers consume from queues: Push Worker calls APNs/FCM, Email Worker calls SendGrid/SES, SMS Worker calls Twilio. (4) Workers write delivery status to the Delivery Log. (5) Failed deliveries are retried with exponential backoff via a retry queue. (6) In-app notifications are written directly to the database and served via the inbox API.

Step 6 Deep Dives

Explore the critical components in detail.

Priority Queue Design ▼

Use separate queues for each priority level (high, medium, low) rather than a single queue with priority sorting. High-priority workers always process first. This prevents head-of-line blocking where a flood of low-priority marketing emails delays a critical password reset.

Implementation: Kafka topics per priority (notif-high, notif-medium, notif-low) with dedicated consumer groups. High-priority consumers are over-provisioned to ensure near-zero queue depth. Low-priority consumers are scaled based on budget constraints.

Why not a single priority queue? Most message brokers (Kafka, SQS) process messages in order within a partition. A single queue means low-priority messages ahead of high-priority messages block them. Separate queues with independent consumers solve this cleanly.

Retry with Exponential Backoff ▼

When a delivery attempt fails (APNs timeout, SendGrid rate limit, Twilio error), the message is placed in a retry queue with an increasing delay: 1s, 5s, 30s, 2min, 10min, 1hr. After 5-6 attempts, the notification is marked as permanently failed and logged.

Jitter: Add random jitter (0-50% of the delay) to prevent thundering herd. If 10,000 notifications fail simultaneously and all retry at the same time, the retry storm can be worse than the original failure.

Dead letter queue: After max retries, messages go to a DLQ for manual investigation. This prevents infinite retry loops and provides visibility into systemic failures.

Rate Limiting Per Channel ▼

Each delivery channel has different rate limits. APNs allows bursts but throttles sustained high volume. SendGrid has per-second and daily limits. Twilio charges per SMS and has regulatory rate limits per country.

User-level rate limiting: Prevent notification fatigue by capping per user: max 5 push/hour, 3 email/day, 1 SMS/day. These limits are configurable per notification category (transactional notifications like password resets bypass limits).

Provider-level rate limiting: Use a token bucket per provider to stay within their API limits. If the bucket is empty, messages queue until tokens refill. This prevents 429 errors and temporary bans from providers.

Deduplication Strategy ▼

Duplicate notifications are one of the most common complaints from users. They happen because of retry logic, event replay, or multiple services triggering the same notification.

Idempotency key: Every notification request includes a unique idempotency key (e.g., "order-456-shipped"). The notification service checks this key against a Redis set (with TTL) before processing. If the key exists, the request is silently dropped.

Sliding window dedup: For notifications without explicit idempotency keys, hash the (recipient_id + template_type + data) tuple and check against recent notifications. If an identical notification was sent within the last 5 minutes, suppress it.

User Preference Filtering ▼

Before enqueuing a notification, the service checks user preferences: (1) Is this channel enabled globally? (2) Is this notification category enabled for this channel? (3) Is the user in quiet hours? (4) Has the user hit their rate limit for this channel?

Quiet hours: If a high-priority notification arrives during quiet hours, it can either be delivered immediately (password reset) or queued until quiet hours end (marketing). The priority level determines the behavior.

Caching: User preferences are cached in Redis with a 5-minute TTL. A preference change triggers a cache invalidation. This keeps the hot path fast — preference lookups are sub-millisecond from cache.

Step 7 Trade-offs

Discuss the key architectural trade-offs.

At-Least-Once Delivery

  • Simpler implementation — retry on failure
  • No notifications are silently lost
  • Requires dedup logic on the receiving end
  • Good default for most notifications

Exactly-Once Delivery

  • No duplicate notifications ever
  • Much harder to implement (2PC or idempotency)
  • Higher latency due to coordination overhead
  • Overkill for most notification use cases

Push Model (Server Pushes)

  • Low latency — notifications arrive instantly
  • No wasted bandwidth from polling
  • Requires persistent connections (WebSocket)
  • Best for real-time in-app notifications

Pull Model (Client Polls)

  • Simpler infrastructure — no connection management
  • Works with stateless HTTP
  • Higher latency (depends on poll interval)
  • Wastes bandwidth with empty polls

Batching Notifications

  • Reduces notification fatigue
  • Lower cost (fewer API calls to providers)
  • Digest emails are less annoying
  • Higher latency for individual notifications

Real-Time Delivery

  • Instant notification for every event
  • Critical for transactional notifications
  • Can overwhelm users with volume
  • Higher infrastructure cost
Recommended approach: Use at-least-once delivery with idempotency-based dedup — simpler and works for 99% of cases. Use push for in-app and pull as fallback. Batch low-priority notifications (marketing digests) but deliver transactional notifications in real-time. The key insight: different notification categories deserve different delivery strategies. A password reset is not the same as a weekly marketing digest.

Step 8 Interview Tips

What interviewers are looking for and common mistakes.

Start with the event-driven architecture. The notification system is a classic event-driven system. Show that you understand the producer-consumer pattern with message queues between them. This immediately signals senior-level thinking.
Mention idempotency early. Duplicate notifications are the #1 user complaint. Bringing up idempotency keys and deduplication proactively shows you understand real-world production concerns, not just theoretical design.
Separate concerns by channel. Push, email, SMS, and in-app have completely different delivery characteristics, rate limits, and failure modes. Design them as separate workers consuming from shared queues, not as a monolithic sender.
Discuss user preferences as a first-class concern. Many candidates forget that users can opt out of notifications. Preference checking must happen early in the pipeline (before queuing) to avoid wasting resources on notifications that will be filtered.
Common mistake: ignoring quiet hours and timezones. A notification system that wakes users at 3 AM is a broken notification system. Mention quiet hours, timezone-aware scheduling, and priority-based override (password resets ignore quiet hours).
Common mistake: single queue for all priorities. If you put marketing blasts and password resets in the same queue, a marketing campaign can delay critical transactional notifications. Always use separate priority queues.
