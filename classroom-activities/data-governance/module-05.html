Data Ingestion & Medallion Architecture

🤖 Case Study: “SmartFactory — The IoT Data Chaos”

SmartFactory, a manufacturing company using IoT sensors to monitor temperature, pressure, and machine status, stores data in inconsistent formats with no ingestion pipeline and no separation between raw and processed data. Students act as Data Engineers to build a multi-source ingestion pipeline: extract data from APIs and CSV files, organize it into Bronze (raw) and Silver (processed) layers using Medallion Architecture, compare Data Lakes and Warehouses, and design a scalable IoT ingestion system.

Part 1 API Data Ingestion — Python Steps 1–2 · D1 +
✓ Complete Answer — Steps 1–2

Step 1 extracts weather data from the OpenWeather API or a simulated response. Step 2 saves the raw JSON before any transformation — this is the Bronze ingestion step performed in Python before data enters Databricks.

Step 1 — Option A: Real OpenWeather API Call
import requests import json API_KEY = "your_openweather_api_key" CITY = "New York" url = "http://api.openweathermap.org/data/2.5/weather?q=" + CITY + "&appid=" + API_KEY + "&units=metric" response = requests.get(url) weather_data = response.json() print(weather_data)
Step 1 — Option B: Simulated Response (no API key required)
import json # Simulated OpenWeather API response weather_data = { "city" : "New York", "temperature" : 22.5, "humidity" : 65, "weather_condition": "Clear", "timestamp" : "2026-04-29T10:00:00Z" } print(weather_data)
Step 2 — Save Raw JSON (Bronze — no transformation applied)
with open("/tmp/weather_raw.json", "w") as f: json.dump(weather_data, f, indent=2) print("Raw JSON saved: /tmp/weather_raw.json")
💡 Why This Answer? ▶

Why save the raw JSON before any transformation?

The Bronze layer rule is: never modify data at ingestion time. Saving the raw API response as-is means you always have the original source record to reprocess if your transformation logic changes. If you only save the transformed version and later realize you needed a field you dropped, you must call the API again — which may return different data. Raw storage is the insurance policy for your pipeline.

Why provide a simulated option?

API rate limits, authentication requirements, and network restrictions make live API calls unreliable for classroom labs. The simulated response produces the same JSON structure the real API returns for the fields this lab uses, allowing students to complete the full pipeline without an API key. In production, the real API would be used with proper secrets management (Databricks Secrets, not hardcoded keys).

Why use the requests library for API ingestion?

requests is the standard Python HTTP client for REST API calls. For production pipelines, add: error handling (response.raise_for_status()), retry logic for transient failures, and authentication headers. For streaming APIs that push data continuously, replace requests.get() with a WebSocket listener or a Kafka consumer.

💡 Why This Answer? ▶

Why use Databricks Volumes instead of FileStore?

Databricks Volumes (Unity Catalog) are the modern replacement for /FileStore/. Volumes support fine-grained access control, audit logging, and Delta Sharing integration. /FileStore/ is a legacy path without row-level or column-level governance. For new projects, always upload to a Volume: /Volumes/catalog/schema/volume_name/.

Why verify file existence before running the pipeline?

A pipeline that fails silently on a missing file is harder to debug than one that fails explicitly at the start. The verification cell acts as a pre-flight check — if either file is missing, you know immediately before running cells of transformation code. In production, this is extended with schema validation: confirming not just that the file exists but that it contains the expected columns and data types.

Part 3 Bronze Layer — Raw Data Ingestion Steps 5–6 · D1 +
✓ Complete Answer — Steps 5–6
Bronze Layer Rule: Load data exactly as received from the source. No column renaming, no type casting, no filtering, no transformation. The Bronze table is the immutable source of truth — every Silver table must be derivable from it.
Step 5 — Load JSON into Spark (Raw Layer)
# Load raw JSON exactly as received from API weather_raw = spark.read.json( "/Volumes/workspace/default/Volume/weather_raw.json" ) display(weather_raw) print(f"Schema: {weather_raw.dtypes}") print(f"Row count: {weather_raw.count()}")
Step 6 — Save Bronze Table
# Persist raw data as-is: no transformation before this point weather_raw.write.mode("overwrite").saveAsTable("weather_bronze") print("Bronze table created: weather_bronze")
Expected Schema — weather_bronze
ColumnInferred TypeNotes

weather_conditionstringKept as-is
timestampstringKept as-is — will be dropped in Silver
💡 Why This Answer? ▶

Why does Bronze store everything, including the timestamp that gets dropped later?

The Bronze table is a replayable source. If your Silver transformation logic changes — maybe the timestamp is needed for time-series analysis — you can re-run Silver from Bronze without going back to the API. If you dropped the timestamp at ingestion time, that information is gone. Bronze is not about what you need today; it is about preserving optionality for tomorrow.

Why use spark.read.json() instead of Python json.load()?

Spark distributes the read across the cluster, handles schema inference automatically, and returns a DataFrame that integrates directly with saveAsTable(). Reading with Python json.load() gives a Python dict that must be manually converted to a DataFrame. For a single-record JSON this difference is trivial; for files with millions of records, the distributed read is essential.

Why is Bronze the foundation of Medallion Architecture?

Medallion Architecture builds each layer from the previous: Silver is derived from Bronze; Gold is derived from Silver. If Silver is corrupted or transformation logic is wrong, you truncate Silver and re-derive it from Bronze. Without Bronze, corruption in Silver means your data is irreversibly lost. The Bronze layer costs very little storage but provides very high recovery value.

Part 4 Silver Layer — Processed & Query-Ready Data Steps 7–8 · D1 +
✓ Complete Answer — Steps 7–8
Step 7 — Extract Required Fields from Bronze
from pyspark.sql.functions import col # Read from Bronze, select only analysis-ready fields weather_silver = weather_raw.select( col("city"), col("temperature"), col("humidity"), col("weather_condition") # timestamp deliberately excluded: not needed for current analytics ) display(weather_silver)
Step 8 — Save Silver Table
weather_silver.write.mode("overwrite").saveAsTable("weather_silver") print("Silver table created: weather_silver") print("Columns: city, temperature, humidity, weather_condition")

💡 Why This Answer? ▶

Why is Silver "analysis-ready" rather than just "clean"?

Cleanliness is context-dependent. A Silver table for the dashboard team drops the raw timestamp. A Silver table for the data science team might keep it for feature engineering. Analysis-ready means the data is structured, validated, and free of obvious errors for a specific consumer group. A single Bronze table can feed multiple Silver tables, each optimized for a different downstream use case.

What transformations belong in Silver vs Gold?

  • Silver: drop unnecessary columns, cast types, rename columns, deduplication (dropDuplicates()), null handling (dropna(), fillna())
  • Gold: aggregations, joins, business logic, KPI calculations — never in Silver

Why use col() instead of string column names?

Using col("name") allows chaining transformations: col("temperature").cast("double").alias("temp_c"). It also makes column references explicit when joining tables with overlapping names. While weather_raw.select("city", "temperature") works here, col() builds the habit of explicit, chainable references that scale to complex multi-table pipelines.

💡 Why This Answer? ▶

Why use dropna() instead of fillna() for faulty sensor readings?

Sensor null = sensor failure, not missing data. If a temperature sensor returns null, the sensor itself malfunctioned — there is no meaningful value to impute. Filling null readings with a mean would corrupt the data: a failed sensor has no temperature to report, and imputing one could falsely indicate a normal machine state when it is in a Fault condition. fillna() is appropriate when null means "not collected" (an optional survey field) — not when it means hardware failure.

Why keep null rows in Bronze if they will be dropped in Silver?

The Bronze sensor table including fault rows has governance value: it records that sensor S005 reported a Fault at 08:00:15. Even though temperature and pressure were null, the machine_status was "Fault" — that event happened and must be preserved for maintenance logs. A future pipeline might create a separate Silver table specifically for fault events, reading from the same Bronze source. Never drop data at the Bronze stage because you cannot anticipate every future use case.

Why do both weather and sensor data follow the same Bronze/Silver pattern?

Medallion Architecture is source-agnostic. Whether data comes from a REST API, CSV, database, or stream, the same principle applies: ingest raw into Bronze, derive clean into Silver. This consistency means any data consumer immediately knows: tables ending in _bronze are raw and may have quality issues; tables ending in _silver are cleaned and query-safe. The naming convention is part of the governance contract.

💡 Why This Answer? ▶

Why does a Data Lake use schema-on-read while a Data Warehouse uses schema-on-write?

Schema-on-write requires you to define the table structure before data enters it — the database enforces that every row matches. This produces clean, fast-to-query data but requires knowing the schema upfront. Schema-on-read stores raw data without enforcement; the schema is applied at query time. Data Lakes use schema-on-read because IoT systems and APIs produce heterogeneous data that evolves over time — a rigid ingestion schema would cause pipeline failures every time the API adds a new field.

Why is there a Gold layer if Silver is already clean?

Silver tables are cleaned source data — they still look like original records, just without quality issues. Gold tables are business-ready aggregates: average machine temperature per zone, fault rate per shift, daily uptime percentages. A dashboard querying raw Silver rows to compute these metrics on every page load would be slow and resource-intensive. Gold pre-computes aggregations so dashboards render in milliseconds — the same principle behind materialized views, applied at lakehouse scale.

Why does SmartFactory need OpenMetadata if the tables are already in Databricks?

Databricks knows where tables are and what columns they contain. OpenMetadata adds the layer the business cares about: what the data means. A new analyst seeing sensor_bronze in Databricks has no way to know it contains null fault readings from malfunctioning sensors. The Bronze tag combined with a description and lineage showing derivation from sensor_data.csv communicates immediately: this is raw data, check Silver for clean records. Governance metadata makes the catalog self-documenting.

Reflection
Why is separating raw data (Bronze) from processed data (Silver) a governance requirement and not just a software engineering best practice?

Software engineering best practices are recommendations that teams can choose based on their circumstances. Governance requirements are obligations that protect the organization from data loss, audit failure, and regulatory exposure. The Bronze layer is not just a clean architecture pattern — it is the immutable record of what the system received. When an IoT sensor reports a fault and that reading is cleaned away in the transformation step, the Silver table provides no evidence the fault event occurred. If a machine fails and the maintenance team needs to know when the first anomalous reading appeared, only the Bronze layer can answer that question.

From a compliance perspective, organizations under data retention regulations cannot afford to lose source records. A pipeline that ingests API data directly into Silver with field selection applied at ingestion time has no Bronze — the original API response is gone the moment the pipeline runs. If the API later changes its field names or transformation logic is found to be incorrect, there is no source to replay from. Bronze solves this: it is the single point of truth that all derived tables trace back to, and its existence is what makes a data platform auditable and reproducible.

The deeper principle is that Bronze and Silver are not just technical layers — they represent a chain of custody for data. Just as forensic evidence requires every handoff to be documented, a governed data pipeline requires every transformation to be traceable to an unmodified source. When SmartFactory can show an auditor the Bronze sensor reading, the Silver transformation that cleaned it, and the Gold aggregate that informed the maintenance decision, they have a complete and defensible data lineage. Without Bronze, the chain breaks at the first step.
