Data Lake vs Data Warehouse Comparison
3 conceptual comparisons with real-world analogies + wildcard mental model
✓ Complete — 3 dimensions
1 — Data Type: The “Sensor” vs. The “Ledger”
What kind of data does each system accept at the door?
■ Data Lake — Raw
Imagine capturing every single frame from a camera feed or a continuous stream of telemetry from a robotics system. You don’t filter it yet because you might need the “noise” later to train a computer vision model. This is the Raw state — unfiltered and high-volume.
This lab: weather_raw.json stored to Volume with the full nested API response — coord, sys, wind structs all retained.
■ Data Warehouse — Structured
Think of an inventory management system or a financial ledger. The data is already “rectified” — every entry for a transaction or an ingredient count must fit into a specific column (Date, Item, Quantity). Optimized for accuracy and quick retrieval.
This lab: weather_silver with exactly 4 clean columns — city, temperature, humidity, weather_condition. No structs, no nested arrays.
2 — Schema: “Explore First” vs. “Plan First”
When does the structure of the data get enforced?
■ Data Lake — Schema-on-Read
Ideal for real-time game analytics or champion network graphs. You ingest the JSON data from an API immediately. You only decide how to “shape” that data — extracting metrics like win rates or item builds — at the moment you run your analysis script.
This lab: spark.read.json() reads weather_raw.json with no schema declared — Spark infers types at query time.
■ Data Warehouse — Schema-on-Write
Requires an upfront “blueprint.” Before data enters the warehouse, you must define the relationships (e.g., how a Student ID links to a Course ID). Perfect for institutional reporting where structure doesn’t change often and consistency is mandatory.
This lab: silver_df uses an explicit .select() with .alias() — the output schema is defined before the write, not discovered after.
3 — Use Case: “Discovery” vs. “Optimization”
What problem is each architecture designed to solve?
■ Data Lake — Data Science / ML
The playground for distributed computing and AI research. If you are building a recommendation engine or a predictive model, you need the massive, messy datasets found in a lake to find hidden patterns that structured tables might have discarded.
This lab: sensor_bronze keeps the null fault row — an ML model detecting anomalies needs to see those readings, not a cleaned version.
■ Data Warehouse — BI Reporting
The “Vibe Check” on business health — tracking token usage, project budgets, or monthly sales. Provides the Single Source of Truth a manager or Dean needs to make quick, data-backed decisions without writing complex transformation code.
This lab: sensor_silver is what a dashboard queries — clean rows, no nulls, ready for COUNT/AVG without pre-processing.
⚡ Wildcard Analogy — The Scrapbook vs. The Spreadsheet
■ Data Lake — The Scrapbook
You throw in photos, ticket stubs, and handwritten notes. It’s a mess, but it preserves the feeling and the full context of the memory — including the details you didn’t know you’d need later.
■ Data Warehouse — The Spreadsheet
You record the date, the cost of the ticket, and the location. It’s easy to calculate your total spending and sort by category, but you lose the “soul” — the unstructured details and context of the event.

Layer Technology What Enters Governance Role
Sensors / API IoT hardware (temperature, fault sensors), OpenWeather REST API Raw readings: temperature, humidity, fault codes, wind speed, AQI Data origin — no governance enforcement here; records what the physical world produced
Ingestion Databricks notebooks (PySpark), Volumes for CSV; simulated API calls for weather JSON API response, CSV sensor files uploaded to /Volumes/workspace/default/Volume/ Entry point into the governed pipeline; source metadata captured (file name, timestamp, row count)
Bronze Layer Databricks Delta table (weather_bronze, sensor_bronze) All original fields including nulls, timestamps, and raw sensor faults (S005 retained) Immutable source of truth. Never transformed. Enables replay if Silver logic changes. OpenMetadata Bronze tag confirms raw provenance.
Silver Layer Databricks Delta table (weather_silver, sensor_silver) Cleaned records: timestamp dropped from weather; null fault rows removed from sensors via dropna() Quality gate. Downstream analytics only query Silver+. OpenMetadata Silver tag signals data is safe to use for reporting.
Gold Layer Databricks Delta table (not built in this lab — future module) Pre-aggregated business metrics: average temperature per zone, daily fault rate, uptime % Business-ready aggregates. Feeds dashboards without per-query computation. OpenMetadata Gold tag confirms production-ready status.
Catalog OpenMetadata (connected to Databricks via connector) All table schemas, row counts, column lineage, Medallion tags Governance layer. Makes the pipeline self-documenting: every table has a tag explaining what it contains and which layer it belongs to. Enables audit trail.
Dashboard Databricks SQL, Power BI, or Tableau (future integration) Gold aggregates queried via SQL Consumption layer — reads only from Gold; never touches Bronze or Silver directly

Process Notes

①
Live OpenWeather API Call (Seattle)
Used the real OpenWeather API with a personal API key to pull live weather data for Seattle. The raw JSON response was saved to /Volumes/workspace/default/Volume/weather_raw.json before loading into Spark, preserving the full nested structure as the Bronze record.
②
Bronze Intentionally Stores Nulls
Sensor S005 has a null fault_code. This row is kept in sensor_bronze because Bronze is the evidence layer — removing it would destroy the audit trail for the malfunctioning sensor event.
③
No .format() on saveAsTable()
Used plain .write.mode("overwrite").saveAsTable() for all 4 tables — no .format("parquet") or .format("delta"). Databricks defaults to Delta, so specifying a format is either wrong (parquet breaks DML) or redundant (delta is already the default).
④
OpenMetadata Tagging Requires Saved Tables
Each table must exist in the Databricks catalog before OpenMetadata can discover and tag it. DataFrames in memory are invisible to the catalog — saveAsTable() is the required step before any D2 screenshot can be taken.
