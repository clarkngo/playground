Part 1 Enterprise Data Architecture Overview Architecture Diagram · D1 +
✓ Architecture Layers & Diagram

A well-designed enterprise data platform separates concerns across five distinct layers. Each layer has a single responsibility — mixing concerns (for example, running analytics directly on source data) creates the fragmentation this lab exists to solve.

💡 Why This Answer? ▶

Why separate data into layers instead of one flat store?

Layer separation enforces the single-responsibility principle for data. When reporting runs on Gold, it never touches Bronze — protecting the raw source from corruption. When a Gold aggregation is wrong, you rebuild it from Silver without touching Bronze. Each layer has a predictable contract: Bronze is immutable, Silver is query-safe, Gold is business-ready. This predictability is what makes large-scale analytics maintainable.

Why does the Governance Layer span the entire stack?

Governance is not a layer you reach at the end — it applies at every stage. Bronze tables need ownership and sensitivity tags. Silver tables need lineage back to Bronze. Gold tables need business definitions. OpenMetadata sits alongside the entire pipeline, cataloging metadata at each stage so auditors and data stewards have visibility from raw ingestion to reporting output.

Part 3 Create Raw Read-Only Data Stores Steps 3–4 · D1 +
✓ Complete Answer — Steps 3–4
Read-Only Data Store: A Bronze table is written once at ingestion time and never modified. Analysts query it but cannot alter it. This preserves original data for governance, auditing, and pipeline replay — if Silver transformations are later found to be incorrect, you re-derive Silver from an unchanged Bronze.
Step 3 — Load Transactions Dataset
# Load raw CSV exactly as uploaded — no transformation transactions_df = spark.read.csv( "/FileStore/tables/Transactions_500.csv", header=True, inferSchema=True ) display(transactions_df) print(f"Row count: {transactions_df.count()}") print(f"Schema: {transactions_df.dtypes}")
Expected Schema — transactions_df
ColumnInferred TypeNotes
transaction_idstringUnique identifier per transaction
customer_idstringLinks to customer dimension
countrystringCustomer country
amountdoubleTransaction value in USD
transaction_datestring / dateDate of transaction
statusstringCompleted, Pending, Failed
Step 4 — Save Bronze Table (Read-Only Store)
# Persist raw data as-is: Bronze is the immutable source of truth transactions_df.write.mode("overwrite").saveAsTable( "transactions_bronze" ) print("Bronze table created: transactions_bronze")
💡 Why This Answer? ▶

Why use inferSchema=True for Bronze?

At the Bronze layer, Spark reads the file and infers column types automatically. This is intentional — Bronze stores data as-close-to-source as possible. If you hardcode types and the source changes (e.g., an amount field that was integer becomes decimal), the pipeline breaks. Bronze is resilient because it accepts what the source sends. Type enforcement happens in Silver.

Why does "read-only" matter if we use .write.mode("overwrite")?

The Bronze table is written exactly once per pipeline run (full overwrite). After the write, the table is read-only from the perspective of analysts and downstream processes — they can SELECT from it but have no path to UPDATE or DELETE rows. In production, this is enforced by granting only SELECT privileges on the Bronze catalog. The pipeline itself uses a service account with write access, but no human analyst can modify Bronze.

Part 4 Data Modeling — Dimensional Architecture Steps 5–6 · D1 +
✓ Complete Answer — Steps 5–6

Dimensional modeling splits data into Fact tables (measurable events — transactions, sales) and Dimension tables (descriptive attributes — customers, products, locations). Facts are joined to dimensions at query time for flexible analytics.

Dimensional Model — Transactions
TableTypeColumnsPurpose
customer_dimDimensioncustomer_id, countryUnique customer attributes — descriptive
fact_transactionsFacttransaction_id, customer_id, amount, transaction_date, statusMeasurable events with foreign key to dimension
Step 5 — Create Customer Dimension Table
# Dimension: unique customer attributes — deduplicated customer_dim = transactions_df.select( "customer_id", "country" ).dropDuplicates() display(customer_dim) print(f"Unique customers: {customer_dim.count()}")
Step 6 — Create Transaction Fact Table
# Fact: measurable events with foreign key to customer_dim fact_transactions = transactions_df.select( "transaction_id", "customer_id", "amount", "transaction_date", "status" ) display(fact_transactions) print(f"Total transactions: {fact_transactions.count()}")
💡 Why This Answer? ▶

Why use dropDuplicates() on the dimension?

A dimension table must have one row per unique entity. If a customer appears in 50 transactions, the dimension should still have one row for that customer. dropDuplicates() on customer_id ensures the dimension contains each customer exactly once. Without this, joins to the dimension produce duplicate rows in the fact table, inflating metrics like total sales.

Why does the fact table NOT include country?

Country is a customer attribute, not a transaction attribute — it belongs in the dimension. This is the normalization principle of dimensional modeling: store descriptive attributes in dimensions, store measurable values in facts. When an analyst needs country-level sales, they JOIN fact_transactions to customer_dim on customer_id. This means country information is defined in one place; if a country code changes, you update the dimension, not every fact row.

What is the relationship between fact and dimension tables?

The fact table holds a foreign key (customer_id) that links to the primary key of the dimension table. This is called a star schema when one fact is surrounded by multiple dimensions. The query pattern is: SELECT SUM(amount) FROM fact_transactions JOIN customer_dim ON customer_id WHERE country = "USA". The fact table provides the numbers; dimensions provide the filters and labels.

Part 5 Sensor Architecture Modeling Steps 7–9 · D1 +
✓ Complete Answer — Steps 7–9

The sensor dataset follows the same dimensional pattern: a dimension for device identity attributes and a fact table for measurable sensor readings over time.

Step 7 — Load Sensor Dataset
# Load IoT sensor CSV — raw, no transformation sensor_df = spark.read.csv( "/FileStore/tables/sensor_data_500.csv", header=True, inferSchema=True ) display(sensor_df) print(f"Row count: {sensor_df.count()}")
Expected Schema — sensor_df
ColumnTypeDimension or Fact?
sensor_idstringDimension — device identity
machine_idstringDimension — machine identity
timestampstringFact — when reading occurred
temperaturedoubleFact — measurable reading
pressuredoubleFact — measurable reading
vibrationdoubleFact — measurable reading

Step 8 — Create Sensor Dimension Table
# Dimension: unique sensor-to-machine mappings sensor_dim = sensor_df.select( "sensor_id", "machine_id" ).dropDuplicates() display(sensor_dim) print(f"Unique sensor-machine pairs: {sensor_dim.count()}")
Step 9 — Create Sensor Fact Table
# Fact: timestamped sensor readings with foreign key sensor_id sensor_fact = sensor_df.select( "sensor_id", "timestamp", "temperature", "pressure", "vibration", "status" ) display(sensor_fact) print(f"Total sensor readings: {sensor_fact.count()}")
💡 Why This Answer? ▶

Why does sensor_fact keep sensor_id but not machine_id?

sensor_id is the foreign key linking each reading to the sensor dimension. machine_id is stored in the dimension (alongside sensor_id) — if an analyst needs machine-level aggregation, they JOIN sensor_fact to sensor_dim on sensor_id. Keeping machine_id in the fact would denormalize it — if a sensor is reassigned to a different machine, every historical fact row would need updating. With the dimension pattern, only one row in sensor_dim changes.

Why is status included in the fact, not the dimension?

Machine status (Running, Warning, Maintenance) changes on every reading — it is an event attribute, not a stable descriptor of the sensor device. Stable device identity attributes belong in the dimension; time-varying measurement attributes belong in the fact. Always ask: "does this value change per reading, or is it constant across all readings for this device?"

Why does Silver use fact_transactions rather than re-reading Bronze?

Part 7 Gold Layer — Aggregated Reporting Steps 11–12 · D1 +
✓ Complete Answer — Steps 11–12

Gold tables are pre-aggregated summaries designed for direct use in dashboards and executive reporting. They are the output of business logic — not raw data, not cleaned data, but answered questions.

Step 11 — Aggregate Transaction Data by Country
from pyspark.sql.functions import sum # Gold: total sales by country — business-level summary gold_sales = transactions_df.groupBy( "country" ).agg( sum("amount").alias("total_sales") ) display(gold_sales) print(f"Countries in Gold: {gold_sales.count()}")
Step 12 — Save Gold Table
# Persist Gold table — read by BI tools and dashboards gold_sales.write.mode("overwrite").saveAsTable( "sales_gold" ) print("Gold table created: sales_gold")
💡 Why This Answer? ▶

Why aggregate at the Gold layer rather than in the dashboard query?

Pre-aggregating in Gold means a dashboard query reads one row per country instead of scanning 500 transaction rows on every page load. As data volumes grow to millions of rows, the performance difference becomes critical. Gold tables are also versioned: if your aggregation logic changes, you can compare the old Gold table to the new one using Delta history before promoting the change to production.

Why does Gold read from transactions_df (Bronze) rather than Silver?

In this lab, Gold is built directly from the loaded DataFrame because Silver and Gold are constructed in the same session. In production, Gold is typically derived from Silver (or a combination of Silver tables) to ensure it benefits from Silver-level cleaning. The architectural rule is: each layer is derived from the layer immediately below it — Gold reads Silver, Silver reads Bronze, Bronze reads source.

What other Gold aggregations would be useful for this retailer?

Common Gold patterns include: monthly_revenue_gold (sales grouped by month), customer_lifetime_value_gold (total spend per customer), failed_transactions_gold (count of failed status by country for fraud monitoring), and sensor_alert_gold (count of Maintenance or Warning readings per machine per day).

Part 8 Delta Architecture & Versioning Steps 13–15 · D1 +
✓ Complete Answer — Steps 13–15

Delta Lake extends Parquet with an ACID transaction log. Every write, update, or delete is recorded as a versioned entry. You can query historical versions and roll back to any point — essential for audit compliance.

Step 13 — Save Delta Table (Explicit Format)
# Save as Delta format explicitly — enables versioning and history transactions_df.write.format("delta") \ .mode("overwrite") \ .saveAsTable("transactions_delta_arch") print("Delta table created: transactions_delta_arch")
Step 14 — Update Records with SQL (Simulated Archival)
UPDATE transactions_delta_arch SET status = 'Archived' WHERE amount < 100;

Run this in a SQL cell (switch cell language to SQL) or use spark.sql() in Python.

Step 14 (Python Alternative) — spark.sql() for Updates
spark.sql(""" UPDATE transactions_delta_arch SET status = 'Archived' WHERE amount < 100 """) print("Low-value transactions archived")
Step 15 — View Table History
DESCRIBE HISTORY transactions_delta_arch;
Expected History Output — Two Versions
VersionOperationDescription
0WRITEInitial overwrite from transactions_df — 500 rows written
1UPDATEstatus set to Archived WHERE amount < 100

To restore the original data: RESTORE TABLE transactions_delta_arch TO VERSION AS OF 0;

💡 Why This Answer? ▶

Why use Delta format instead of plain Parquet?

Delta adds an ACID transaction log on top of Parquet files. This enables: atomicity (writes succeed or fail completely — no partial writes), versioning (every write is a new version you can query or roll back to), schema evolution (safely add columns without breaking readers), and MERGE/UPDATE/DELETE operations that plain Parquet cannot do. For compliance use cases, the history log is the audit trail a regulator asks for.

Why archive by amount rather than by date?

This lab uses amount < 100 as a simple filter to demonstrate the UPDATE operation and produce a visible history entry. In production, archival policies are typically time-based (transactions older than 7 years) aligned with regulatory retention requirements. The mechanism is identical — a WHERE clause targeting the rows to be archived.

Why is time travel important for a compliance audit?

Regulators may ask: "What did your customer records look like on March 15, 2025?" With Delta, you answer: SELECT * FROM transactions_delta_arch TIMESTAMP AS OF '2025-03-15'. Without versioning, you would have to restore from backup — a process that can take hours. Delta time travel answers that question in seconds from a live table.

💡 Why This Answer? ▶

Why is metadata-driven architecture important?

A table without metadata is invisible to governance. OpenMetadata makes every table discoverable by description, owner, and tag. When a compliance auditor asks "which tables contain customer transaction data?", a metadata-tagged catalog returns the answer in seconds — without that catalog, engineers must grep codebases and interview team members.

Why apply ReadOnly tags in OpenMetadata if Databricks already controls access?

Tags in OpenMetadata serve a communication and governance purpose beyond access control. They signal intent to everyone who discovers the table in the catalog: "this table is not meant to be written to." Even if a user technically has write access in Databricks, the tag creates a policy contract that appears in data quality dashboards, lineage diagrams, and audit reports.

What is data lineage and how does it connect these tables?

Lineage tracks the derivation chain: CSV file → transactions_bronze → transactions_silver → sales_gold. In OpenMetadata, you can draw or auto-detect this lineage from pipeline metadata. When sales_gold produces wrong numbers, lineage tells you exactly which upstream table to investigate — you follow the chain backwards until you find the corrupted step.

Reflection Questions & Answers
1. What is the difference between a fact table and a dimension table, and why does dimensional modeling benefit analytics?

A fact table stores measurable business events — each row is a transaction, a sensor reading, or a sale with numeric values (amount, temperature, count). A dimension table stores descriptive attributes of the entities involved — each row describes a customer, a sensor device, or a product with categorical labels (country, machine type, category name).

Dimensional modeling benefits analytics because facts and dimensions can be joined flexibly at query time. Instead of storing country in every transaction row (which wastes storage and creates update anomalies), country lives once in customer_dim. Analytics can then group facts by any dimension without schema changes — add a region hierarchy to customer_dim and every existing query gains region-level grouping automatically.

2. Why is read-only access important for Bronze tables in an enterprise analytics platform?

Bronze tables are the raw source of truth. If analysts could modify Bronze, the pipeline loses the ability to replay: when a Silver or Gold transformation is found to be wrong, you re-run it from Bronze. If Bronze has been altered, you no longer know what the original source data contained.

Read-only Bronze also satisfies governance requirements. Regulators (GDPR, SOX, HIPAA) often require proof that source records have not been tampered with. An immutable Bronze table with Delta history provides that proof — the transaction log records every write and shows that no UPDATE or DELETE has occurred on Bronze rows after the initial load.

3. How does Delta Table versioning support enterprise data governance?

Delta versioning creates an ACID transaction log that records every write, update, and delete as a numbered version. This supports governance in three ways: auditability — you can show regulators exactly what data looked like at any past point using time travel; recoverability — if a bad update corrupts data, RESTORE TABLE rolls back to a known good version in seconds; and pipeline confidence — engineers can run UPDATE operations knowing that nothing is permanently lost because the previous version is retained in the log.

For the retail case study, Delta history lets compliance answer: "Which transactions were archived, when, and by what operation?" — without maintaining separate audit log tables.
