Part 1 Security Concepts Overview Concepts · Reference +
✓ Key Concepts & Definitions

Before implementing access controls, the team must understand the five foundational concepts that govern secure data consumption. Every design decision in this lab traces back to one of these principles.

ConceptDefinitionHow It Applies Here
AuthenticationVerify the identity of a user before granting any accessLogin simulation with username-to-role mapping dictionary
AuthorizationVerify what a verified user is permitted to accessRole check determines which table (admin or analyst view) is returned
RBACRole-Based Access Control — permissions attached to roles, not individual usersAdmin and Analyst roles each have a distinct permitted table set
Least PrivilegeGrant the minimum access required to perform the job, nothing moreAnalyst view excludes salary, SSN — columns not needed for analyst tasks
Secure ConsumptionRestrict how sensitive data surfaces in reporting and queriesColumn masking and view-level restriction prevent raw PII from reaching analysts
💡 Why This Answer? ▶

Why must authentication and authorization be separate?

Authentication answers "Who are you?" while authorization answers "What are you allowed to do?" Merging them creates a security gap: if you only check identity once at login without enforcing per-resource permissions, a verified user can access anything in the system. Separating the two means every data request is evaluated against the user's current role — even if their identity was verified hours ago. In enterprise IAM systems (Okta, Azure AD), authentication generates a token; authorization policies are evaluated at each resource boundary using that token.

Why does RBAC scale better than per-user permissions?

In a per-user model, adding a new analyst means individually configuring permissions for every table, column, and dataset they need. In RBAC, you assign the user to the Analyst role, and they inherit all permissions defined for that role. When a new table is added, you update the role definition once — all role members get the updated permissions automatically. This makes onboarding, offboarding, and audit compliance manageable at enterprise scale.

Column-Level Sensitivity Classification: You cannot restrict what you have not classified. Before any access control is designed, every column must be labeled with its sensitivity tier. Classification is the foundation of RBAC — roles are later granted access to columns based on their classification level, not their names.
💡 Why This Answer? ▶

Why classify columns before building access controls?

Classification creates a shared contract between data engineers, compliance officers, and business owners. Without it, engineers make individual judgment calls about which fields need protection — and those calls diverge. When a new analyst view is requested, the classification tells engineers immediately which columns to exclude without requiring a policy meeting. It also powers downstream automation: tools like OpenMetadata can scan for columns tagged PII and alert when they appear in an unprotected table.

What is the difference between PII and Confidential?

PII (Personally Identifiable Information) is any data that can identify a specific individual — name, email, SSN, date of birth. It is regulated under laws like GDPR and CCPA, which impose legal obligations on how it is stored, processed, and shared. Confidential describes business-sensitive data that is not necessarily personal but must still be restricted — salaries, financials, and trade secrets. Both categories require access controls, but the legal consequence of exposure differs: PII exposure can trigger regulatory fines; Confidential exposure triggers competitive or employment risk.

💡 Why This Answer? ▶

Why restrict at the view level, not the UI layer?

Hiding columns in a reporting dashboard or BI tool only affects what that specific tool displays — anyone with direct database access, API access, or a different BI connection still sees all columns. View-level restriction is enforced at the data store: when an analyst queries employees_analyst_view, the columns are absent from the table schema itself. There is no configuration in any tool that can reveal them, because the columns were never included in the view definition. This is the difference between a cosmetic restriction and a structural one.

Why use saveAsTable instead of just displaying the filtered result?

Persisting the view as a registered table lets the enterprise point BI tools, APIs, and downstream pipelines at employees_analyst_view as a stable, named resource. The analyst role is then granted SELECT on this table and SELECT is denied on employees_admin_view. If you only filter at query time, any analyst who writes their own query against the raw table bypasses the filter. A separate table ensures the restricted schema is the only schema analysts can address.

Admin vs. Analyst Tables: employees_admin_view is the unrestricted source containing all columns including salary and SSN. employees_analyst_view is the restricted derivative. Never allow analysts to query employees_admin_view — the separation must be enforced at the permission level, not by convention or trust.
💡 Why This Answer? ▶

Why maintain separate admin and analyst tables instead of one table with row-level permissions?

Column-level permissions on a single table are supported in some platforms but create operational complexity: every new query tool must respect and enforce those permissions, and misconfiguration in any tool silently exposes sensitive columns. Separate tables make the access boundary structurally unambiguous. An analyst role with SELECT only on employees_analyst_view cannot reach salary data even if the BI tool they use has a configuration bug — the table does not contain those columns at all.

Why is naming the admin table with a "view" suffix important?

Naming both tables with the _view suffix communicates that both are derived consumption interfaces — neither should be modified by analysts directly. It also signals to future engineers that the raw source (e.g., an ingestion Bronze table) is a separate upstream object. This naming convention prevents confusion where someone mistakes the admin table for the raw source and begins modifying it.

# Step 10: Access control logic if role == "Admin": display(employees_df) else: display(analyst_view)
💡 Why This Answer? ▶

What does this simulation represent in a production system?

The Python dictionary maps usernames to roles — this is exactly what an enterprise Identity and Access Management (IAM) system does, just at a larger scale. In production, the dictionary is replaced by a directory service (LDAP, Active Directory) or an OAuth/OIDC provider (Okta, Azure AD, Google Identity). At login, the IAM system issues a token containing the user role claim. Every subsequent data request presents that token, and the authorization layer checks the role claim before returning data.

Why use a role string check rather than a username check?

Checking role instead of username means adding a new admin user requires only adding them to the dictionary with the "Admin" value — the authorization logic does not change. If you checked username == "admin1", every new admin would require a code change. This separation of identity (username) from permission (role) is the core benefit of RBAC over per-user access control lists.

What should replace this dictionary in production?

In a real enterprise deployment, user-to-role mapping is stored in LDAP groups, Azure AD security groups, or an OAuth server. The Databricks workspace integrates directly with these systems — when a user logs in, Databricks checks their group membership and maps it to a catalog-level role. The if role == "Admin" logic is replaced by table-level GRANT/REVOKE statements that enforce access without requiring application code.

Part 8 Data Masking Step 11 +
✓ Complete Answer — Step 11
Step 11 — Mask Email Field
from pyspark.sql.functions import regexp_replace # Mask email -- show first char and domain only masked_df = analyst_view.withColumn( "email", regexp_replace("email", r"(^.).*(@.*$)", r"\1***\2") ) display(masked_df)
Expected Output Example
Original EmailMasked Email
john.smith@company.comj***@company.com
alice@example.orga***@example.org
💡 Why This Answer? ▶

When should you mask data rather than hide it entirely?

Masking preserves business utility while reducing privacy exposure. An analyst who needs to verify that an employee has an email address on file, or who needs to identify email domains for department analysis, can do so with j***@company.com without seeing the full personal identifier. If the column were hidden entirely, analysts would need to request exceptions or escalate to admins for every email-related task. Masking is appropriate when the analyst needs the shape or domain of the data, not the full value.

How does the regex pattern work?

The pattern (^.).*(@.*$) captures two groups: group 1 is the first character of the email (^.), and group 2 is the at-sign plus everything after it (@.*$). The replacement \1***\2 outputs group 1, then three asterisks, then group 2. Everything between the first character and the domain is replaced with ***. The result preserves the domain (business-useful for identifying email providers and departments) while masking the personal username portion.

Why is masking at the DataFrame level stronger than masking in a dashboard?

Dashboard-level masking is a display layer only — the underlying query still returns the full email, and any tool or API that reads the same data source sees the unmasked value. DataFrame-level masking applies the transformation at the data tier: the masked value is what gets persisted to employees_analyst_view. Any tool querying that table, regardless of its display settings, receives only the masked email.

💡 Why This Answer? ▶

Why configure catalog-level policies when Databricks already restricts table access?

Databricks enforces runtime data access — an analyst cannot SELECT from the admin table. OpenMetadata governs discoverability and intent: an analyst should not even be able to see the existence of employees_admin_view or its column metadata in the catalog. Without catalog-level policies, analysts can browse metadata for restricted tables, discover that salary and SSN columns exist, and potentially find indirect paths to that data (e.g., through exports, reports, or legacy pipelines). Catalog policies close that metadata exposure gap.

Why are policies separate objects from roles in OpenMetadata?

The policy-role separation follows the same RBAC principle as Databricks: permissions are defined once in a policy, and roles reference policies. If the AnalystRestricted policy changes (e.g., analysts are now allowed to see department budget summaries), updating the policy immediately affects all users assigned the Analyst role. This avoids the need to modify individual role configurations for every change to access rules.

💡 Why This Answer? ▶

Why do tags in OpenMetadata power downstream governance?

Tags are metadata that other governance systems can read programmatically. A PII tag on the ssn column can trigger automatic alerts when that column appears in an unregistered query, block it from being included in an export job, or require it to appear in a GDPR data subject access report. Data lineage tools trace how PII flows through the pipeline — if ssn is tagged at the source, lineage tracking can flag every downstream table that inherits it, even through transformations.

How do tags support regulatory compliance audits?

When a GDPR auditor asks "where is personal data stored in your platform?", a tagged catalog returns a complete list in seconds: every column tagged PII, every table containing those columns, and every downstream table in the lineage chain. Without tags, answering that question requires manual review of table schemas by engineers — a process that takes days and is error-prone. Tagged catalogs make compliance evidence-gathering repeatable, automated, and defensible.

Reflection Questions & Answers
1. Why is it insufficient to hide sensitive columns only in the reporting layer rather than at the data store level?

Hiding columns in a reporting tool or dashboard is a display-layer control only — it does not restrict what the underlying query returns. Any user with direct database access, API access, a different BI tool connection, or a custom SQL query against the same table will see all columns regardless of what the dashboard hides. This means the restriction is as strong as the weakest interface connecting to the data.

Restricting at the data store level (by creating a view that excludes sensitive columns) ensures that the schema itself does not contain those columns. No matter which tool, API, or query engine connects to employees_analyst_view, salary and SSN are absent from the result set. The restriction is structural, not cosmetic, and cannot be bypassed by switching interfaces or writing direct queries.

2. What is the difference between authentication and authorization, and why must both be implemented for secure data consumption?

Authentication verifies identity — it answers "Who are you?" by checking credentials (password, token, biometric). Authorization verifies permissions — it answers "What are you allowed to access?" by checking the authenticated user's role against a policy. The two operate independently and sequentially: authentication must succeed before authorization is evaluated.

Implementing only authentication creates a system where any verified user can access any resource — the misconfiguration in this case study. Implementing only authorization without authentication means permissions are evaluated for an unverified identity — any user can claim any role. Both must be present: authentication ensures you know who is making the request; authorization ensures their role permits the specific data they are requesting at that moment.

3. How does applying PII and Confidential tags in OpenMetadata support regulatory compliance?

Regulations like GDPR, CCPA, and HIPAA require organizations to know exactly where personal data is stored, who has access to it, and how it flows through systems. PII and Confidential tags in OpenMetadata create a machine-readable record of exactly that information — every tagged column is tracked, every table containing it is cataloged, and data lineage traces how tagged data propagates downstream.

During a compliance audit, auditors ask for evidence of data inventories and access controls. A tagged catalog produces this evidence automatically: a search for PII-tagged columns returns a complete inventory with table names, column names, and associated access policies. Without tags, engineers must manually audit every table schema — a process that is slow, incomplete, and impossible to repeat consistently. Tags make compliance evidence-gathering automated, reproducible, and audit-ready.
